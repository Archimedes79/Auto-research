**What it does** [checked]: the camera branch for BEV map segmentation. Input 256 x 704 per camera. Backbone `SwinTransformer` with `out_indices [1, 2, 3]` (channels 192 / 384 / 768 = strides 8 / 16 / 32), neck `GeneralizedLSSFPN` (in 192 / 384 / 768, out 256, `start_level 0`, `num_outs 3`). The view transform uses the stride-8 map (`feature_size = image_size // 8`, i.e. 32 x 88), LSS-type with `dbound [1.0, 60.0, 0.5]` (118 depth bins), BEV `xbound = ybound = [-51.2, 51.2, 0.4]` (256 x 256), one height cell (`zbound [-10, 10, 20]`), 80 BEV channels, then `downsample: 2` inside the transform (a 128 x 128 map at 0.8 m). The config names the transform `LSSTransform` (the lidar-fed variant `DepthLSSTransform` belongs to the fusion configs, from memory); no depth loss is visible in what I read, so assume depth is learned from the segmentation loss only. Decoder: `GeneralizedResNet` (160 / 320 / 640) + `LSSFPN` to 256 channels. Head: `BEVSegmentationHead` with `grid_transform` from the 0.8 m input scope (+-51.2 m) to a 0.5 m output scope (+-50 m, 200 x 200), focal loss. Classes: drivable_area, ped_crossing, walkway, stop_line, carpark_area, divider (road_divider + lane_divider). Swin-T is initialised from `swint-nuimages-pretrained.pth` (a driving-domain 2D detector init, named in the configs). The ImageNet normalisation constants are used (mean 0.485 / 0.456 / 0.406).

**Results that matter** [checked]: paper Table III (nuScenes val, IoU, +-50 m): BEVFusion camera-only drivable 81.7, ped. crossing 54.8, walkway 58.4, stop line 47.4, carpark 50.7, divider 46.4, mean 56.6; camera + LiDAR mean 62.7; baselines (mean) OFT 42.1, LSS 44.4, CVT 40.2; M2BEV drivable 77.2 and divider 40.5. README checkpoints: `camera-only-seg.pth` 57.09 mIoU, `bevfusion-seg.pth` 62.95, `camera-only-det.pth` 35.56 mAP / 41.21 NDS (the camera-only detector is described as a BEVDet-Tiny variant with a heavier view transform). Latency: 119.2 ms for the full camera + LiDAR detector on an RTX 3090 (Table I), 253.2 GMACs; no latency or MACs for the camera-only segmentation model on any page read; README news mentions a TensorRT deployment at 25 FPS on Jetson Orin (fusion model).

**Transferable technique**: (1) the published reference that does what we propose, image encoder with an FPN output at stride 8 feeding a depth-binned lift, at the same 256 x 704 input; it reaches divider 46.4 IoU with six cameras (the GaussianLSS paper reports divider 38.7, see the existing note 2504.01957; label thickness and protocol are not guaranteed identical, so treat the gap as indicative). (2) The trunk works from a coarse 0.8 m BEV (stride-2 inside the transform) and a learned resampling to 0.5 m in the head; thin dividers are decoded after the trunk, not at the lift. (3) As a teacher: `camera-only-seg.pth` gives six-class BEV logits for any nuScenes frame, so the front sector can supervise a small student (cheaper than DualBEV's detection-only weights, which have no map output). (4) A driving-domain (nuImages) init for the backbone is part of the recipe; no ablation of it was seen.

**Cost and fit**: Swin-T has 28.3M parameters and 4.5 GMACs at 224 x 224 (timm card); at 256 x 704 that is about 16 GMACs for the backbone (derived; window attention does not scale exactly), plus FPN and the 118-bin depth/context head: not a 5-16 GFLOPs part, comparable in weight to our current frozen DualBEV image side. For us the useful artefacts are the config values (stride 8, 256 channels, 118 bins, 0.8 m BEV) and the checkpoint as a teacher, not the code (mmdet3d fork, spconv-era dependencies, no CPU path).

**Doubts**: six-camera model, no front-only number; no stride or resolution ablation found on the pages read; depth supervision of the camera-only variant not confirmed; checkpoint size and weight licence not on the page; the README mIoU (57.09) differs from the paper (56.6); repository archived.
