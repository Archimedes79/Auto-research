- **Statement:** a route head that reads the builder's beam nodes with differentiable positions, and with validity and link weights as new inputs, lets the route loss improve the builder where the same loss through the assembled graph did not (three negatives).
- **Re-opens a closed question** (`closed_questions.md` row 7). Its re-open conditions (route loss not saturated on the training frames, builder not frozen at the start) were already met by E214 / E232; the new reason is a new mechanism: node tokens with differentiable positions, validity and links.
- **What is known about the old path** (`p18_joint.py:150-177`): the head receives `xy` and `cp` as numpy arrays from the assembled graph, `keep` / `pi` is never an input of `RouteXNet.forward(tok, xy, cp, sd, mask)`, and the token is `M @ h[src]`. So the only route-loss path into the builder is through `h`; since `h` is a function of the whole builder, some route gradient reaches seeds and ray read-out indirectly. How much is not measured; gate G1 measures it.
- **Other explanations of the three negatives, not excluded:** the failure-frame stream (`--real_fail 1 --share 0.5`; the failure-trained head alone lifts route success by +0.15 ... +0.37 over the base head, E232.c0 against the base, far above the effect tested here), seed noise (E232 one seed per arm, E214 two; both lie inside the seed spread), the route loss weight against `lam`, the fp16 grad scaler.
- **What has to be built (the head changes; it is not a re-wiring):**
  1. `pos_i` enters `RouteXNet` through `fourier2d(xy)` and the position encoding (smooth, a real gradient) and through the bilinear sampling of the SD raster and the maps (differentiable, local to a few cells).
  2. `cp` (cross-section) is built by the numpy `TK.cross_section(V, edges)` from assembled vertices; a torch version from `pos`, parent and children of the beam nodes is new code.
  3. **New head inputs, zero-initialised so that the start equals the base head:** `pi_i` (as a learned scalar feature) and a link attention bias between linked nodes. `mask` is a boolean key-padding mask for SDPA (`MLayer`, `p10_net.py:239`), so a float bias is new code in `MLayer` / `XLayer` / `RouteXNet`. Without these two inputs validity and links get no route gradient: the loss weight `pi_i * valid_i` is **stop-gradient** (otherwise the route loss falls by lowering the validity of nodes the head gets wrong, which costs lanes found).
  4. The route target stays non-differentiable: the label is `route_heat_train.npy` at the node position (numpy indexing, with the map faults of `RTR.draw_cell`, as `p18_joint.py:165-171`), masked to nodes within a cutoff distance of a ground-truth lane point (value in the detail plan). Risk: nodes can move to please the head instead of improving the lane; the position-drift measurement and the lanes-found guard are there to see that.
  5. The read-out: node logits to the vertices of the assembled graph (validity-weighted mean over the nodes that make up a 4 m vertex), then E232's piece aggregation, threshold and `route_success`; the consumer input is produced the same way. `FastRoute` and its CUDA graphs stay bound to the old signature (arms b, n); the new head has no fast path (more than 768 nodes falls out of its buckets).
  6. The old head applied to raw beam nodes at step 0 is **not known to be as strong** as on 4 m vertices (different density and count, beam selection on detached validity): gate G0 below measures it.
- **Streams and controls:** all trained arms use E232's stream: real failure frames (`--real_fail 1 --share 0.5`), builder loss weight `lam 1`, 4800 steps, the same optimiser and learning-rate schedule (the stem at 0.3x as in `p18_joint.py:112`). Arm c differs from a only in the route-loss path into the builder; E232's arm c detached only `h`, this one is stricter. a - c measures the route gradient, not builder fine-tuning. **The train / evaluation shift** (training on raw beam nodes, evaluation on assembled vertices) is measured on arm c: the same trained head evaluated under the old read-out (assembled vertices as input) and the new one (nodes). Arms b and n are sanity rows only.
- **Not comparable to E232 numbers:** the start is `e123_D7_r3_j1` (E232: `r3_f1`, temporal off both), the head has new inputs, the read-out is new for a and c. Compare a with c of this experiment only; the E232 numbers (a: night 0.701 / blur 0.803 / three cameras off 0.569; c: 0.737 / 0.839 / 0.569) are context.
- **Chain scored and headroom:** the chain without the map net, as E232. The best chain (E220, with the map net and failure-trained heads) already reaches 0.83 - 0.91, so the headroom is in the base chain; nothing is said about the best chain until it is repeated there.
- **Prediction:** a - c = +0.05 route success in at least two of the three types. E232 observed a - c = -0.036 / -0.036 / 0.000 with one seed. Under the null (no effect) with a 2-seed mean difference of SD 0.04 - 0.05 (assumed from the stated route-head seed spreads, 0.05 - 0.09 under failure), one type reaches +0.03 with probability 0.23 - 0.27 and at least two of three types with probability about 0.13 - 0.18, before the sign and bootstrap conditions; those conditions lower it. This is a calculation under an assumed SD, not a measurement; the first seed pair replaces the assumption.
- **Decision rule:** KEEP if the rule of section 0 holds; CUT if a - c <= 0 in all three types in both seeds (a fourth negative closes the joint line and updates the closed-question row); otherwise TIE, take the cheaper arm (c); INCONCLUSIVE (seeds disagree) means the third seed, not an adoption.
- **Gates before any training run (measured with `evaluation/drivers/e2e_gradient_report.py` extended to the route loss alone):**
  - **G0:** the base head applied to the raw beam nodes of `e123_D7_r3_j1` (no training) against the same head on assembled vertices: route success on 250 VAL frames; the gap is the size of the train / evaluation shift and decides whether the node read-out is usable at all.
  - **G1:** (1) a "before" table, per module group, of the route-loss-only gradient through the old `p18_joint` path; (2) the same for the new path; the route-loss gradient norm of the seeds, ray read-out and link groups in the new path must be at least 5 % of those groups' builder-loss gradient norm and larger than in the old path; (3) a finite-difference check that the gradient on `pos_i` through the SD sampling and `fourier2d` is nonzero and has the right sign; (4) a unit test that fails when the soft path is replaced by the old hard one, and one that checks `pi_i` and the link bias receive a route gradient only in arm a. The junction head is not in G1 (the token design does not read its heat). If G1 fails the code is wrong; that is a bug, not a result.
- **Cost:** coding about 4 - 5 days (differentiable cross-section, the two new head inputs, the read-out, the joint trainer wiring, the tests). GPU about 5 - 6 h wall: E232 trained two arms of about 2070 s concurrently and evaluated for 5336 s for the pair (about 2670 s per arm); this card has four trained runs, each evaluated under the new read-out, a and c also under the old one, plus the n / b sanity evaluations, and the attention over raw nodes is slower than over vertices.
- **Kill criterion:** G0 shows the node read-out loses more than 0.05 route success against the vertex read-out at step 0 (the design is then wrong, redesign); G1 fails; at one third of the steps a checkpoint of each arm is evaluated on 250 VAL frames and compared with arm c at the same step and with n: Q falls by more than 0.010 or lanes found by more than 0.02 against c; non-finite loss; any arm running longer than 1.5 times E232's training time (about 3100 s).
- **Inputs:** ready: the builder checkpoints, the SD library, `RouteXNet`, `p16_interface.py` (contract), `e2e_gradient_report.py` (G1 base), the failure-frame stream of `p18_joint.py`, `route_success`.
