**What it does** [checked]: Radar points are projected into every camera view with their depth and voxelised into camera-frustum pillars (v = 1, radar has no elevation); PointNet + sparse conv + SECOND/FPN (8x downsampled canvas) gives per-frustum-cell radar features and a radar OCCUPANCY (sigmoid, not softmax, because occupancy is not one-hot). The image context is weighted by BOTH the estimated depth distribution and the radar occupancy, convolved, height summed, voxel-pooled (average) to BEV. Multi-modal feature aggregation (MFA): multi-modal deformable cross attention (6 layers, 8 heads, 4 points), optionally on only the top-k BEV queries ranked by max(depth, radar occupancy).

**Results that matter** [checked, nuScenes val, Table 5]: depth only 43.9 NDS / 33.2 mAP; depth + radar occupancy (RVT) 52.1 / 44.8 (+8.2 / +11.6); radar occupancy replacing the depth distribution 33.6 / 24.3 (much worse). Cost (i9 + RTX 3090, batch 1, FP16): MFA 21.01 ms dense, 4.96 ms with 4096 sparse queries (-76.4 %, on a 256 x 256 BEV, some accuracy loss); whole detector 27.9 / 20.4 / 7.2 FPS for R18 256x704 / R50 256x704 / R101 512x1408; repo table 29.4 / 22.7 FPS for R18 / R50.

**Transferable technique**: (1) the radar enters the lift as a likelihood multiplying the camera depth distribution (a product, not a replacement: the replacement result shows radar alone is too ambiguous); (2) sigmoid occupancy; (3) average pooling after height sum. This is the Cartesian/frustum version of option B's `c_rad x p_rad` and of our camera pull, and it comes with a measured cost for the attention that Mirko may want to compare against a conv-only fusion: 5 ms at 4096 queries on a 3090 FP16.

**Cost and fit**: radar encoder is a SECOND-class sparse-conv net (not tiny); radar voxelisation in frustum coordinates needs a CUDA op (the repo has an `ops` folder and `gen_radar_pv.py`); the RVT idea itself is two gathers and a product.

**Doubts**: detection (NDS / mAP), not segmentation; no per-attribute radar ablation read; no polar variant (frustum / Cartesian only); the page does not say which 21.0 ms setting (layers, BEV size) the dense MFA number belongs to beyond "256 x 256 BEV"; single runs.
