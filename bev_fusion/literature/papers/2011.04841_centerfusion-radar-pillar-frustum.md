**What it does**: A CenterNet-style image detector finds object centres. Each radar point (x, y, z, ego-compensated vx, vy; 3 sweeps = 0.25 s) is expanded to a fixed pillar of 0.2 x 0.2 x 1.5 m because radar height is unreliable. A 3D RoI frustum built from the 2D box and the estimated depth selects the pillars (closest one wins; frustum lengthened by 20 % at test time). Inside the object's 2D box three heatmap channels are written (normalised depth, vx, vy) and concatenated to the image features for secondary heads (depth, rotation, velocity). RCS is not used (checked on the page).

**Results that matter** (nuScenes val, Table 3, relative to the camera baseline NDS 0.328 / mAP 0.306 / mAVE 1.426): pillar expansion alone +15.4 % NDS, -13.1 % mAVE; frustum association alone +25.9 % NDS, -48.1 % mAVE; both +34.5 % NDS, -61.9 % mAVE (the text says 35.5 %). The velocity gain is the largest one: the radar Doppler channels carry the benefit.

**Transferable technique**: (1) fixed-height pillar instead of a z value; (2) radar attributes written as dense maps aligned to the camera view (depth, vx, vy) so a conv network can use them without a point encoder; (3) the radar information is gated by an image hypothesis (frustum), which suppresses clutter. For a BEV lane system the frustum becomes a ray or corridor; the heatmap write is the same as a rasterised radar BEV with channels (range, vx_comp, vy_comp).

**Cost and fit**: nearly free (a rasterisation); the cost is that the frustum needs a first-stage detector, which we do not have for lanes. Static lane evidence in radar is weak (see SN14), so the Doppler channels mainly help moving objects.

**Doubts**: baseline is a weak 2020 camera detector (NDS 0.328); the large relative gains do not transfer to strong baselines (CRN, RCBEVDet gains are smaller in absolute terms). No FPS on the page. No RCS and no uncertainty modelling beyond the pillar size.
