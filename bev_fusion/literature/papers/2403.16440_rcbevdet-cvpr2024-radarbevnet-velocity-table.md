**What it does** [checked]: RadarBEVNet (dual-stream radar backbone, RCS-aware BEV encoder; accumulates multi-sweep radar points with RCS and Doppler speed as point features) and a Cross-Attention Multi-layer Fusion module on top of a BEVDepth-style camera branch; the camera stream accumulates BEV features of previous frames, concatenates them with the current frame and adds a two-block BEV encoder; no dedicated velocity branch is described. Ablation: temporal information on the camera-only BEVDepth baseline +4.4 NDS / +5.4 mAP; temporal supervision +0.4 NDS, -0.3 mAP.

**Results that matter** [checked, nuScenes val ResNet-50 256 x 704, one table]: NDS / mAP / mAVE / FPS: BEVDet C 39.2 / 31.2 / 0.909 / 15.6; BEVDepth C 47.5 / 35.1 / 0.428 / 11.6; SOLOFusion C 53.4 / 42.7 / 0.252 / 11.4; StreamPETR C 54.0 / 43.2 / 0.295 / 27.1; CRN C+R 56.0 / 49.0 / 0.344 / 20.4; RCBEVDet C+R 56.8 / 45.3 / 0.220 / 21.3. Test (V2-99): 63.9 NDS / 55.0 mAP / 0.259 mAVE, while camera-only SparseBEV (0.246) and StreamPETR (0.243) have a slightly LOWER mAVE: radar does not give the best test-set velocity error. RTX 3090, batch 1, FP16. The text's "14.7 % / 37.5 % lower mAVE vs SOLOFusion / CRN" does not match its own table (about 12.7 % / 36 % by the table values).

**Take-away for the SOA question**: the leaders get mAVE 0.22-0.30 from stacked ego-aligned BEV history plus regression; camera-only temporal methods (SOLOFusion 0.252, StreamPETR 0.243-0.295) are as good as camera + radar at this metric: Doppler as a mere input channel does not buy a clear velocity advantage over history.

**Doubts**: mAVE is evaluated at matched boxes only, so it says nothing about unmatched or small objects, or about a dense field.
