# splits - the scene lists of the training splits (scene names only)

A split is one json file: `{"about": ..., "gt": <autogt version the caches were checked against>, "train": [scene names], "val": [scene names]}`. No sample, token or path is in it; the data it names (caches, GT) stays in `../data/` (derived, not in git; how to rebuild it for a split: `../data/README.md`). The lists of the official nuScenes TEST split are not part of these files.

A config says `"split": "large"` instead of 510 scene names. `python -m trainsuite start` passes the composed config through `training/splits.py resolve` (project.json: `trainsuite.resolve`), which replaces the key by `train_scenes` / `val_scenes`, so the config the trainer reads and the `runs/<id>/config.json` it writes hold the exact lists: a run is pinned to the lists, not to the file. A config with inline lists (all stored configs) works as before; a split and inline lists in one config are refused. The preset `small` (400 steps) is a training length, the split `small` is data: `--preset small --set split=small` is the short bug-finding run.

| file | train / val scenes | what |
|---|---|---|
| `small.json` | 60 / 10 | subset of `large` for short bug-finding trainings (400 - 1000 steps, probe, timing): every cache exists, nothing is built. 2,283 train and 378 val samples |
| `large.json` | 428 / 82 | the baseline split: nuScenes parts 1 - 6, exactly the lists of `training/configs/t16_full.json` (the scenes of `t16.full_s0`; the old `data/scenes_parts1_6.json` is the same) |
| `xl.json` | 700 / 82 | more data: `large` + the 272 train scenes of parts 7 - 10, the same 82 val scenes (the lists of `training/configs/t17_data.json`, so a run is read against `large` on the same val frames). Needs `--set feature_cache=data/cache/all/cam_feats --set feature_cache2=data/cache/all/cam_feats_bevfusion`. The plan's "700 / 150" is not what t17 holds: the 68 val scenes of parts 7 - 10 are downloaded, but t17 kept the 82 on purpose |

`gt` is `v8` in all three: the autogt store (`data/autogt/c643a7539d`) holds the GT of all 850 trainval sequences, and the trainer's GT cache (signature `0.5_4_6a7aa7864a`, which `autogt/versions.csv` maps to v8; v9 is the same GT) was counted against the lists on 2026-11-03: `small` complete; `large` all 16,289 train samples and 1,673 of 3,109 val samples (the rest is written when an evaluation first reads it); `xl` 26,690 of 26,730 train samples. A new GT version means that check again and a new `gt` value in a new file.

**How `small` was chosen.** The scenes of `large` whose caches are complete (both feature shards, the front image, the GT cache entries and the radar cache entries of every sample with a previous and a next keyframe; all 428 train scenes, but of the 82 val scenes only 5 Singapore one-north and 11 Boston ones: the val frames are cached when an evaluation reads them). Per city the scenes are sorted by scene number and m of them taken evenly spaced (index `round(i * (n - 1) / (m - 1))`): train m = 15 for each of Boston seaport, Singapore one-north, Queenstown and Holland Village (252 / 122 / 35 / 19 scenes); val m = 5 for Boston and one-north (the 82 val scenes of `large` lie in these two cities only). The throw-away script is not kept; the rule above reproduces the file from the cache inventory.

**Use.** `python training/splits.py names small` lists the scenes of a split, one per line (the format of `training/gt_scenes.py names` and `autogt --scenes-file`). `python training/splits.py manifest runs/<id>` writes `runs/<id>/manifest.json` (split name found from the lists, counts and hashes, GT, commit, card) and `python training/splits.py split-json runs/<id> results/<id>` the `split.json` of a result package. A new split is a new file here and a line in this table; `tests/test_splits.py` pins the three files against the stored configs they were taken from.
