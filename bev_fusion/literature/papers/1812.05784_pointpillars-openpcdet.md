**What it does** [checked]: x-y plane divided into pillars; each point is decorated to 9 features (x, y, z, reflectance, offsets to the pillar mean of the points (3), offsets to the pillar centre (2)); PointNet layer (linear, BN, ReLU) then max over the points of the pillar; scatter to a C x H x W pseudo-image; multi-scale 2D backbone with upsampling and concatenation; SSD-style head. KITTI lidar-only: about 62 Hz, 105 Hz with a 0.28 m grid; 16 ms on a GTX 1080 Ti, encoder 1.3 ms; learned encoders beat fixed encoders, especially at large bin sizes.

**OpenPCDet nuScenes configuration** [checked, raw files]: cbgs_pp_multihead.yaml uses voxel size [0.2, 0.2, 8.0] m, 20 points per voxel, up to 30 000 voxels, PillarVFE with one 64-filter layer and absolute xyz on; the dataset config lists five point features (x, y, z, intensity, timestamp) and MAX_SWEEPS 10. So the timestamp (time lag) already enters the pillar point features as a plain channel (for lidar sweeps); how it is computed is not in the config.

**Transferable technique**: pillar = hard assignment of each detection to ONE cell with offsets-to-centre as features; the learned density replaces the hard assignment by soft weights over neighbouring cells, and the offset-to-centre features become the (dr, dphi) offsets to the sensor-relative cell. The RC-BEVFusion radar encoder (already collected) is a PointPillars variant, so a port can start from OpenPCDet's PillarVFE and swap the scatter.

**Cost and fit**: trivial; the point is to have the pillar baseline with identical heads for the ablation hard-bin vs density.

**Doubts**: lidar, not radar, in the paper; the sparse radar situation (few points per pillar) makes max-pooling over a pillar nearly the identity, so the gain of a learned encoder over a rasterised map is smaller than for lidar (inference, RC-BEVFusion note has no per-attribute ablation).
