# Evaluation

One place for how results are measured. Rule: **do not write a private metric - use or extend these**, compare only on identical frames, run the self-tests after touching anything here (`tools/maintenance/run_all_tests.sh`).

## Evaluate a model: one command

```
wsl bash tools/env/_py14.sh evaluate.py --list
wsl bash tools/env/_py14.sh evaluate.py champion --compare control
wsl bash tools/env/_py14.sh evaluate.py recall --asm fork_prune=0.3 --tag p03
wsl bash tools/env/_py14.sh evaluate.py --golden check --cached-only     # layer 1: every golden number reproduced (also in run_all_tests.sh)
wsl bash tools/env/_py14.sh evaluate.py --golden check --fresh-only      # the network path: champion re-inferred on VAL250 without the cache (idle GPU)
```

`evaluate.py <name>` takes a name from `../models/registry.json` (checkpoint + config + the standard assembly settings), runs it on VAL (873 frames; `--split test` only with a `--test-id` logged in `TEST_USAGE_LOG.md`) and writes `runs/eval/<name>/<split>.json` with all metrics, the settings, the cache file and the code commit. Network outputs are cached once per checkpoint, split and inference setting (`~/exp_gcar_b123/eval_cache/`; `cache_paths`: the file name holds run, M, K0 and a digest of every other `set` field, so a new setting never re-scores an old cache), so assembly settings are re-scored on the CPU in about a minute; `--subset val250` takes its frames from that cache too (only `--fresh` or a missing cache runs the network; only a whole split computed on the GPU is written, atomically). A registry entry of kind `union` (E264) names `members` (builder entries) whose trees are joined per frame (`p16_infer.union_raw`) and assembled once; each member is read from its own cache, the members must share the ground truth, and the card's `info.members` records their entries. The cards also carry `R@1_far_inner` / `R@1_far_ring` (and `P@1_*`): the far bin split at max(|x|,|y|) = 45 m (E266). `--compare <name>` adds the paired scene bootstrap. A card also records the training `seed` of its run (the run card in `runs/e123_ladder/cards/`, when it has one) and `protocol.gt_sha`, a digest of the ground truth of the frames it was scored on: `../../autoresearch/tools/decide.py` pairs the arms by the seed and refuses cards of one comparison whose protocol differs or is missing on one side, so cards written before this field (2026-11-01) need a re-evaluation (a cached one takes about a minute; it overwrites `runs/eval/<name>/val.json`, the path the experiments read, so check with `git diff` that the metrics did not move) or `evaluate.allow: ["protocol"]` in the experiment file. An arm that lists several different models of the same seed (every model before E24 has seed 0) cannot be paired by seed: that experiment declares `"pairing": "position"`. A new model gets a registry entry, not a new evaluation script. `golden.json` holds the golden numbers (one entry per registry name on VAL from the cache, plus the champion re-inferred on the 250-frame subset `--subset val250 --fresh`); `--golden check` reproduces them or exits 1, `--golden write <name>` changes an entry (only together with a ledger row that says why). Network timing stays in `drivers/p18_latency.py`. The per-loop drivers below are kept for reproducing old numbers.

Headline metrics (see `PROTOCOL.md`): **Q** at <= 14.3 vertices per 100 m, **topo F1** (connectivity), **lanes found**, **R@1 far** (beyond 40 m), route success, ms per frame; S stays for comparison with the history; FL and dup_frac as checks.

Every card of `evaluate.py` declares the direction of each of its metrics (`"better": {metric: "lower" | "higher"}`, also in the compare block; from `sparse_lanes/sparse_metrics.py` `better()`: lower for false length, vertices per 100 m, vertices per frame, duplicates, higher for the rest, none for counts; since 2026-10-31, D24): `../../autoresearch/tools/decide.py` takes each metric's direction from the cards it compares. A new lower-is-better metric goes into `LOWER_IS_BETTER` there, not into the tools.

## What the checks say (2026-10-25, `evaluate.py`, VAL 873 frames, paired over 22 scenes)
- `evaluate.py` reproduces the stored cards exactly (champion with fork pruning S 0.769 / F1@1 0.870 / J 0.409 / lanes found 0.695; without pruning S 0.746 / J 0.265; recall variant Q 0.740 / lanes found 0.767).
- The new metrics respond where S and Q are blind (`METRIC_RESPONSE.md`): broken lanes (60 % broken: topo R 0.69, F1 0.996, Q 0.995), reversed direction (topo F1 0.004), parallel duplicates (dup 0.34 at 30 %, ground truth 0.011).
- Champion - control: Q -0.002 [-0.011, +0.006] (tie), topo F1 -0.022 [-0.032, -0.011], lanes found -0.105, R@1 far -0.102 [-0.117, -0.087]. Fork pruning lifts topo F1 by +0.021; the recall variant buys lanes found +0.072 and R@1 far +0.063 at the same topo F1. **The open gap to the control is coverage at range and connectivity, not J.**

## What the checks said (2026-10-24)
- The metrics respond as they should to controlled errors (shift, dropped / false / duplicated lanes, cut forks, simplification, reversed direction) - and show the blind spots of S: parallel duplicates and travel direction are nearly invisible, sparsity below 14.3 vertices per 100 m is not rewarded (Sp capped).
- On real predictions the evaluation reproduces the stored history (control S 0.725 vs stored 0.724, champion 0.746 vs 0.746).
- The champion beats the control in S by +0.021 [+0.011, +0.031] (paired, scenes resampled) - **but only through sparsity**: at equal sparsity (Q) it is 0.036 worse; the loss sits in J (-0.143) and lanes found (-0.105). The next experiments are judged by Q at vertices per 100 m <= 14.3, J, lanes found, route success, ms per frame.
Details: `METRIC_RESPONSE.md`, `examples/RESULT.md`.
