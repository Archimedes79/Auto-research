**Autocast op lists** [checked, docs 2.9, CUDA, written around float16]: runs in the low precision: matmul, mm, bmm, addmm, conv1d / 2d / 3d, conv_transpose, linear, GRUCell / LSTMCell / RNNCell, prelu. Runs in float32: layer_norm, group_norm, softmax, log_softmax, exp, log, pow, sum, cumsum, norm, cdist, cosine_similarity, cross_entropy, binary_cross_entropy_with_logits, l1_loss, mse_loss, smooth_l1_loss, nll_loss, kl_div and more. "Promote to the widest input type": addcdiv, addcmul, atan2, bilinear, cross, dot, grid_sample, index_put, scatter_add, tensordot (if any input is float32 everything is cast to float32). The page does NOT say whether the CUDA lists hold for bfloat16, nor whether bf16 needs a GradScaler (all GradScaler text is about float16 underflow).
- consequence for our splat [my inference, from the list]: positions, weights and mass tensors must be created in float32; with float32 coordinates `grid_sample` / `scatter_add` / `index_put` are promoted to float32 even when the features arrive in bf16; BatchNorm / LayerNorm / softmax / losses are float32 anyway. A bf16 coordinate has 7 explicit mantissa bits: spacing 0.25 m at 32-64 m (memory arithmetic, not on a page), as large as half a cell at 0.5 m, so no coordinate, pose, velocity-times-dt or mass tensor goes through a bf16 cast.
- Ampere (RTX 3060) has bf16 Tensor Cores (memory); BevAD 2603.15185 trains in bf16 (checked); the amp recipe page states a 2-3x speed-up "on Tensor Core architectures" for its float16 example without measured numbers.

**channels_last** [checked, memory-format tutorial]: NHWC strides for 4D tensors; convolution and BatchNorm via cuDNN, pointwise ops keep the format; "over 22 %" gain for ResNet-50 training with AMP on Tensor Core GPUs (NVIDIA apex scripts) and 8-35 % on Volta for a model list; convert once with `model.to(memory_format=torch.channels_last)` and the input likewise; ops without support return contiguous output and cost a permute. Our 1 x 1 conv MLPs and 3 x 3 trunk benefit; the custom splat/gather ops work on contiguous tensors, so the format change belongs at the conv blocks only (check by profile).

**torch.compile** [checked, PyTorch 2.x page]: 163 open-source models on an A100: 43 % faster training on average (weighted 0.75 x AMP 51 % + 0.25 x float32 21 %), works on about 93 % of the models; the page states that on a desktop GPU such as a 3090 the speed-ups were lower, that dynamic shapes are limited, that graph breaks block the speed-up, and that compile time grows (especially `max-autotune`). For us: custom indexing code with data-dependent shapes (top-K candidates, variable numbers of radar detections) will break graphs; compile the fixed-shape trunk and the heads only, after a 20-step warm-up, and treat any gain as a measurement on the 3060.

**Activation checkpointing** [checked, 1604.06174]: memory O(sqrt n) for an n-layer net at the price of one extra forward pass per mini-batch; example 1000-layer ResNet: 48 GB to 7 GB with about 30 % more running time. The StreamPETR and BEVDet configs checkpoint the image backbone and the decoder layers (`with_cp=True`, see RECIPES note). For us the frozen camera heads need no activations at all (`torch.no_grad`); checkpoint the K-source window and the trunk if the batch does not fit.

**Doubts**: the op lists were read for float16; check the bf16 behaviour by a three-line test in our environment before relying on it; speed-up claims come from A100-class measurements; a 3060 has 12 GB and far lower memory bandwidth than the cards in these claims, so the percentages do not transfer.
