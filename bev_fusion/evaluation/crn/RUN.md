# RUN.md - CRN export, the commands in order (from the bev_fusion folder, in WSL; nothing here was run on the GPU)
`CRNPY=~/miniconda3/envs/crn/bin/python`, `GCARPY=~/miniconda3/envs/gcar/bin/python`, `OUT=~/work/CRN/outputs/t26_crn`. Through `run.py` (`AR_PROJECT=../bev_fusion`) only the GPU steps matter; the CPU steps are cheap checks.
0. CPU, no GPU: `$CRNPY evaluation/crn/crn_export.py --dry-run` (40 s: all links, 10,236 images + 10,236 radar files; ends with the command) and `--check-load --limit 50 --out $OUT/check` (30 s, CPU: strict checkpoint load, sample 0 read; the model build reads the cached torchvision ResNet-50, no download).
1. CPU pipeline check on the whole chain (no network): `$CRNPY evaluation/crn/crn_export.py --oracle --out $OUT/oracle` (45 s), `$GCARPY evaluation/crn/crn_convert.py $OUT/oracle/results_nusc.json $OUT/oracle/rec.pkl` (40 s; prints the GT version / signature; stops on a mismatch with the live GT), then `$GCARPY evaluation/crn/crn_gates.py overlay $OUT/oracle/rec.pkl $OUT/oracle/overlay.png`. Expected: GT v13 `0.5_4_a107e0b4e8`, 1620 frames of 43 scenes, 37,230 boxes, every GT box of the sector hit in the 20 frames (100 of 100); `front_compare` of it against the GT as detections gave mAP2 0.987 (scratch script, not kept): the ceiling of the label differences.
2. GPU smoke (gate b, part 1; one GPU slot, 50 samples, expected about 1 min with the 30 s model build, memory unmeasured: the record expects 3 - 5 GB at batch 1): `$CRNPY evaluation/crn/crn_export.py --limit 50 --workers 2` (TF32 off -> `$OUT/tf32_off_n50`), read the printed peak memory and ms per sample.
3. GPU, TF32 on, the same 50 samples: `$CRNPY evaluation/crn/crn_export.py --limit 50 --tf32 --workers 2` (-> `$OUT/tf32_on_n50`). Then CPU: `$GCARPY evaluation/crn/crn_gates.py tf32 $OUT/tf32_off_n50/crn_dump.pkl $OUT/tf32_on_n50/crn_dump.pkl` (gate b: PASS = largest centre difference <= 0.1 m, no box lost). Optional floor: a second TF32-off run into another `--out` against the first = run-to-run noise.
4. CPU: `$GCARPY evaluation/crn/crn_convert.py $OUT/tf32_off_n50/results_nusc.json $OUT/tf32_off_n50/rec.pkl --partial`, then `$GCARPY evaluation/crn/crn_gates.py overlay $OUT/tf32_off_n50/rec.pkl $OUT/tf32_off_n50/overlay.png --n 20` (gate a: look at the picture: boxes on the cars, ticks along the driving direction; the share of GT boxes hit).
5. GPU, the full run (`t26.ref_crn`; expected 5 - 8 min per the record, the 2 workers decode 24 JPEGs per sample): `$CRNPY evaluation/crn/crn_export.py --workers 2` (TF32 off, all 1706 samples -> `$OUT/tf32_off`; peak memory and ms per sample in `crn_dump.pkl` meta).
6. CPU, gate c: `$CRNPY evaluation/crn/crn_devkit_gate.py $OUT/tf32_off/results_nusc.json --light` (1 min, peak 1.9 GB; without `--light` the devkit loads the whole trainval tables, about 8 GB, unmeasured) -> PASS = mAP within 0.473 +- 0.05 (also NDS, car and pedestrian AP). On the oracle json (step 1) it prints FAIL with mAP 1.0000, NDS 0.9497: that is the apparatus check (run with `--light` tables; never run on the whole trainval tables), not a verdict.
7. CPU, the record for `front`: `$GCARPY evaluation/crn/crn_convert.py $OUT/tf32_off/results_nusc.json $OUT/crn_front.pkl --expect-signature a107e0b4e8` (40 s), then `bev_suite.py front REF SYSTEM crn=$OUT/crn_front.pkl --x-max 50 ...` with our networks evaluated on the same 1620 frames (`--scenes` of the 43; the frames and the GT signature are in the pickle's meta and checked by `front`).
If a gate fails (card): the object row is read against DualBEV only and the verdict is "maps only". The score floor of the conversion is `--min-score 0.05` (the DualBEV export's rule; CRN's own decode keeps 0.01).
