## 1. Card text
### 1.1 The question and why
Does the delivered lane graph get better when the whole lane head B' (the pyramid included) learns from the loss on the graph, with the pyramid's own pixel loss removed? DESIGN.md R1 (D55: "a loss on the output reaches every module") names the frozen pyramid as an open exception; R6 says stage 2 (S4) did not gain over a frozen B' (E372: s4 - z topo F1 -0.0003 / +0.0049) but trained only the node head (0.099 M parameters). The pyramid is 95 % of B'; its maps were shaped by pixel losses towards GT lines, centres and road areas, not towards what the token head needs. This card measures what the token loss does to it.

### 1.2 Mechanism (E2E, D55)
- **Path of the gradient:** the token head's loss -> the token inputs (tok, pos, dirv, e, e_raw, s, uout, uin, flags; `live_inputs=True` as S4) -> B''s node head -> the pyramid outputs the node head reads (`qnodes.py` NodeHead.forward): `feat2`; `feat1` and `feat05` (pooled, and sampled bilinearly at the pulled node position: differentiable); both `road2` channels; `centre1` channels 0 and 6 - 11 -> the whole pyramid trunk. NOT read by the node head: `lines05` and `centre1` channels 1 - 5 (without the pixel loss they get no gradient: `lines05` has no gradient at all, so AdamW skips it and it stays exactly as it was; the rows 1 - 5 of `centre1` get a zero gradient inside a tensor that trains, so AdamW's weight decay 1e-4 shrinks them: both are off the delivered path, reported, and may be dropped from the network later, not here).
- **Still NOT end to end, named:** GaussianCaR (frozen, its features cached: unfreezing it needs the raw camera / radar inputs, out of scope); the top-512 index choice (argsort on the detached existence: the named budget); the labels (from the detached live tokens); the allowed-pair gate, the 8 m short / long split; the four read-out thresholds.
- **Normalisation:** GroupNorm only in the pyramid and the node head (`head.py`, `pyramid.py`, `qnodes.py`), no BatchNorm, no dropout: the forced eval mode of `LiveSource` is harmless.
- **The risk the arms separate:** without the pixel loss and (arms n, e) without the node loss, nothing but the token loss holds the node existence and positions; the top-512 choice reads the existence, so the token set itself can drift (the moving-label risk of E372, larger here). p keeps B''s node loss as an anchor; n measures dropping the anchor without the pyramid; the coverage and token-count kills guard all arms.
- **Out of scope, named:** a trainable pyramid WITH its pixel loss on (it would separate 'pyramid trainable' from 'pixel loss removed', but `LiveData` does not load the dense pixel targets: a large build, not needed for the owner's question).

### 1.3 Controls and read-outs (named before any run; VAL 873, TEST never touched)
- **c** (the matched control) continues S4 for the same 3000 steps from the champion's head AND node head (`b_state`), pyramid frozen: the same start, data order (head seed of the champion run), schedule, clip, read-out. **n** drops the node anchor with the pyramid frozen. **ref** = the champion's stored live dump and cards (v1.3: no run, section 0); reported against it: c - ref and arm - ref per seed, and a seed where c < ref - 0.01 on topo F1 is flagged 'degraded control' (an arm's GAINS on such a seed is reported with the flag; critic should-fix 12).
- **Noise (v1.3, critic should-fix 3):** the frozen-pyramid path is deterministic (E392's s4_c against e372_s4: every paired difference exactly 0), so for c and n a difference between two arms of one seed has no noise of the run itself; with the pyramid trainable (p, e) the backward of the bilinear sampling into feat1 / feat05 may use atomic adds on the GPU, so p and e need not be bit-reproducible (v1.3b, critic 4 should-fix 6; the re-gate of e shows it); what varies is the training path. The interval used is the paired 95 % scene bootstrap of each score card (`paired_vs_ref_run`: lo / hi per metric; half-width on topo F1 about 0.004, larger on junction F1); the spread between seeds seen so far: E372 s4 - z -0.0003 / +0.0049, E392 junction differences about +-0.008. No seed twin of c (0.25 GPU h) fits the night; the two seeds are the replication.
- **In sample (v1.3, critic should-fix 8):** VAL 873 is the set every token card since E365 was read on, and the choice between p and e is made on it: every number of the candidate is in-sample. TEST is not touched; adoption and a TEST read are the owner's own recorded decisions.
- Every arm: a LIVE VAL dump at bs 4 with its exported `b_state` (`jtoken_eval.py dump --live`), scored at the fixed D115 cell (short 0.3 / long 0.2 / keep 0.6 / none gate off), the paired scene bootstrap against c and against ref of the same seed (frames paired). **Which B' ran (proven, the base = e372_s4_s<S>'s `b_state`):** p / e: the pyramid AND the node head differ from that start and equal the run's export; c / n: the node head differs from that start, the pyramid equals it.
- **Reported, not judged:** the relative change of the pyramid's output features (feat2 / feat1 / feat05, 100 VAL frames: the 'in structure only' measure of 1.4; `evaluation/pyr_change.py`, built v1.3, section 6) and the pyramid's relative weight change ||W_end - W_start|| / ||W_start|| (all pyramid tensors; the same tool), the gradient-norm share of the pyramid, the update size per group, B''s node loss in n / e, s / step and reserved memory, the coverage and token-count curves, ms per frame (the network is unchanged in shape: inference should equal the champion's 16.2 ms; one quiet check of an adopted arm only).

### 1.4 The verdict (by hand, written before any run; per arm p, e, n against c, at D115, per seed)
Per seed and arm, D = arm - c, each with the paired 95 % interval [lo, hi] of the score card `..._live_vs_e393_c_s<S>.json` (v1.3: the intervals are part of every branch, critic should-fix 3); the guards read `..._live_vs_e372_s4_s<S>.json` (arm - ref):
- **VOID** (on a seed; v1.3, critic B4a): the arm or c of that seed has no valid score - not run (cut by time, section 6), a timeout, a crash, an OOM, a missing dump, a resume or roll-back that broke the pairing - or c's own kill fired. A kill of the ARM itself is not VOID but LOSES.
- **LOSES** (on a seed): the arm's kill fired; or topo F1 D < -0.01 with hi < 0; or junction F1 D < -0.01 with hi < 0; or a guard against ref fails (topo F1, F1@1.0 or lanes found: arm - ref < -0.01 with hi < 0).
- **GAINS** (on a seed): not LOSES, topo F1 D >= +0.010 with lo > 0, junction F1 D >= -0.01, the guards against ref hold.
- **HOLDS** (on a seed): neither VOID, LOSES nor GAINS.
**The arm's verdict, in this order:** **NOT RUN** = VOID on both seeds; **E2E-LOSES** = LOSES on both seeds; **INCONCLUSIVE** = LOSES on one seed and HOLDS-or-GAINS on the other, or VOID on one seed and anything on the other (the missing seed is run in a later window; a third seed needs its own B' and cache: named cost); **E2E-GAINS** = GAINS on both seeds; **E2E-HOLDS** = the rest (both seeds HOLDS-or-GAINS, not both GAINS).
**The pyramid claim of e (v1.3, critic B4b):** e drops the node anchor AND trains the pyramid, so e's E2E-GAINS counts as 'the pyramid learns from the token loss' only if also e - n topo F1 >= +0.010 with lo > 0 on both seeds (card `runs/e393_e_s<S>/..._live_vs_e393_n_s<S>.json`); otherwise e's result is labelled **'anchor effect, not the pyramid'** (or **'not separated: n not run'** when n is VOID on a seed, or **'not separated: n killed'** when n's own kill fired on a seed - then no `_vs_e393_n` card exists, and dropping the anchor alone failed, which is no evidence against the pyramid) and R1 is not reworded on it. p - c is the pyramid's effect with the anchor kept (c keeps the anchor), so p needs no such bar.
**The candidate (only p or e; c and n never; v1.3, critic B4c / B4d):** the qualifiers are p with E2E-GAINS and e with E2E-GAINS AND its pyramid claim. Both qualify: **p** if p - e topo F1 >= +0.010 with lo > 0 on both seeds (card `runs/e393_p_s<S>/..._live_vs_e393_e_s<S>.json`), else **e** (both satisfy R1 - an auxiliary loss is allowed - so the anchor is kept only when it pays). One qualifies: that one. None qualifies: no candidate. An arm with E2E-HOLDS is **reported only, no change proposed** (a tie with c is never adopted; the cheaper network stays). The candidate goes to the owner, who decides the champion change (DECISIONS.md); nothing is adopted by this card alone, and its numbers are in-sample (1.3).
**'In structure only':** if the candidate's pyramid OUTPUT barely moved - the relative change of the features the node head reads, ||F_end - F_start|| / ||F_start|| over `feat2`, `feat1`, `feat05` on the same 100 VAL frames, below 1 % (the mean of the two seeds) - its result is labelled 'in structure only' (the pyramid is trainable but its output barely changed) and R1 is not reworded on it. (Second look: a weight-change floor would not fire, since Adam's step noise alone moves the weights more than 0.5 % over 3000 steps; the weight change stays reported.)
**Reading of the decomposition (reported):** e - n = what the pyramid learns without the anchor; n - c = dropping the anchor alone; p - c = the anchored pyramid.

### 1.5 Prediction (a guess, before any run)
e - c topo F1 **+0.003** (window -0.02 to +0.02), p - c +0.004, n - c -0.002; junction F1 about equal. Outcome of arm e (v1.0, before the gate; v1.3 names INCONCLUSIVE): E2E-HOLDS 50 %, E2E-GAINS 15 %, E2E-LOSES 20 % (drift of the token set without an anchor), INCONCLUSIVE 15 % (a split or a VOID seed: a killed control, a cut by time); 'in structure only' about 30 % (lr 1e-5, 3000 steps). Seen since (not a new guess): the gate's arm e moved the pyramid's output by 0.0059 after 50 steps (`pyr_change.py`, 20 frames), so 'in structure only' after 3000 steps is now unlikely. Reasons: S4 on the node head gained nothing measurable; the pyramid was trained on dense GT maps that already encode the lanes; the token loss is far sparser than the pixel loss; the frozen foundation features cap what any head can see.
