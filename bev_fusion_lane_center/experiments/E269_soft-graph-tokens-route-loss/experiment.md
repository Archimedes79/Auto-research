## 1. Card

- **Statement:** letting the route loss move the node positions (a gradient through the head's position encoding and the SD-map sampling) improves failure-half route success over the detached control; if it does not, the position path is closed and the larger design E270 is not worth building.
- **Re-opens a closed question** (`closed_questions.md` row 7). Its re-open conditions were already met by E214 / E232; the reason is a new mechanism: a gradient path to node positions, which the old path did not have.
- **What is known about the old path** (`p18_joint.py:150-177`): the head `RouteXNet.forward(tok, xy, cp, sd, mask)` receives `xy` and `cp` as numpy arrays of the assembled, resampled vertices; the token is `M @ h[src]`; so the only route-loss path into the builder is through `h`, a function of the whole builder.
- **G1(1) measured 2026-11-01** (`e2e_gradient_report.py --route --run e123_D7_r3_j1 --n 2`; 2 TRAIN frames, CPU float32, builder in eval mode, head `p16_f2hr_route_s0`, clean frames: route loss 0.154, builder loss 2.421; indicative, two frames only):
  - the route loss does **reach** the builder strongly through `h`: gradient norm against the builder loss's own, per group: seeds 7.26 vs 8.34 (cosine 0.51, aligned), stem 3.34 vs 2.20, pyramid projections 2.79 vs 1.21, context 0.69 vs 0.15, child tokens 0.98 vs 0.16, ray read-out 1.06 vs 1.22; on the node tokens `h` itself the route gradient is 20 times the builder's (0.180 vs 0.009);
  - except for the seeds group the two gradients are **nearly orthogonal** (cosines -0.06 ... +0.05; over all groups 0.41, carried by the seeds group); no strong conflict, no help either: the route gradient mostly pushes the shared stem and token features in directions the builder objective does not ask for;
  - **exactly zero**: node positions, node validity `pi`, link logits, the junction head, the rescoring layer, the link head, seed validity, the stem's seed and direction heads (34 tensors).
  - Consequence: the premise "the route loss cannot reach the builder" was wrong; what is missing is the position / validity / link path, which E269 adds for positions. A second explanation of the three negatives gains weight: a loud, near-orthogonal route gradient on the shared features (up to 6 times the builder's own on the child tokens and 20 times on `h`) at `lam 1`. **Open for the detail plan:** a third arm d = arm c's wiring with the route gradient on `h` scaled down (for example x0.1) would test that explanation at the cost of two more trainings; not in the rule, decided by Mirko or the planner.
- **Design of the proxy:** keep the head input exactly as in the base head (vertices, tokens `M @ tok_old`, `cp`) so the forward values equal the base head's, which means no train / evaluation shift, `FastRoute`, E232's evaluation and the n / b rows stay valid. Add the gradient path with a straight-through term on the vertex position: `xy_st = xy + (pos[src] - pos[src].detach())` for vertices with a source node (the `has` mask), so the route loss reaches `pos[src]` through `fourier2d` and the SD sampling inside the head with identity Jacobian. `cp` stays numpy in the proxy. The label stays non-differentiable (`route_heat_train.npy` at the vertex, `RTR.draw_cell` map faults, `kind == "n"` rule, as `p18_joint.py:165-171`). Risk: the positions can move to please the head instead of improving the lane; the drift measurement and the lanes-found guard are there to see that.
- **What the proxy does not test:** validity and link weights (they need the new head inputs of E270), the node read-out. A CUT closes only the position path.
- **Other explanations of the three negatives, not excluded:** the failure-frame stream (`--real_fail 1 --share 0.5`; the failure-trained head alone lifts route success by +0.15 ... +0.37, E232.c0 against the base), seed noise (E232 one seed per arm, E214 two), the route-loss weight against `lam`, the fp16 grad scaler. The two arms share the stream, so the stream cannot explain a - c.
- **Streams and controls:** E232's stream and recipe for both arms: real failure frames, builder loss weight `lam 1`, 4800 steps, optimiser and schedule as `p18_joint.py` (stem at 0.3x, line 112), start `e123_D7_r3_j1` (E232 started from `r3_f1`, so compare a with c of this experiment only; E232's a / c rows are context: a 0.701 / 0.803 / 0.569, c 0.737 / 0.839 / 0.569). Arm c is E232's own control (`h` detached, builder trained on its own loss), re-run from j1, 2 seeds.
- **Chain scored and headroom:** the chain without the map net, as E232. The best chain (E220) already reaches 0.83 - 0.91; nothing is said about it.
- **Null and power:** with a 2-seed mean difference of SD 0.04 - 0.07 (the route-head spreads of `PROTOCOL.md`: up to 0.03 clean, 0.05 - 0.09 under failure), one type reaches +0.03 under the null with probability about 0.23 - 0.33 and at least two of three with about 0.13 - 0.26 if independent; the types share seeds and the start head, so they are positively correlated and the chance is higher, before the sign and interval conditions. Power against a true +0.04 is low: the likely outcome is TIE. The value of the proxy is the gradient evidence (G1) and a cheap closing or opening of the position path, not a precise effect size. A calculation under assumed SDs, replaced by the first seed pair.
- **Decision rule:** KEEP: the rule of section 0 holds, then write E270 (validity, links, node read-out). CUT: a - c <= 0 in all three types in both seeds (closes the position path; the joint line is closed only after E270 or by Mirko). Otherwise TIE: take the cheaper arm (c); INCONCLUSIVE (a seed disagrees, an exact 0 counts): the third seed, not an adoption.
- **Order of work and gates:**
  1. **G1(1), now, no new code:** the route-loss-only gradient through the old `p18_joint` path per module group (`e2e_gradient_report.py` extended): does the route loss already reach seeds and ray read-out via `h`, and how strongly? This decides how much the proxy can add.
  2. Build (about 1 - 2 days): the straight-through term, an arm flag in `p18_joint.py` (shared code: `ar-critic` code pass before the first run), the per-frame route-success record and scene bootstrap script, position-drift output.
  3. **G1(2 - 4) on the proxy path:** (2) the route-loss gradient on `pos` is nonzero in a and zero in c; (3) a finite-difference check of its sign through `fourier2d` and the SD sampling (the raster is thin lines, the gradient is local to a few cells); (4) a unit test that fails if the straight-through term is removed. A failing G1 is a bug, not a result. A stated floor for (1) vs (2): the route-loss gradient norm on the seeds group must not fall, and the position gradient must be at least 5 % of the position gradient of the builder loss (a first guess, adjusted after G1(1)).
  4. Run 4 trainings (a, c x 2 seeds) and evaluate with E232's path; read the rule.
- **Cost:** about 5 slot-hours: training 4 x about 2070 s (concurrent pairs, as E232) plus evaluation 4 x about 2670 s (E232: 5336 s for two arms), one read-out only; n and b are not re-evaluated. About 3 h wall on two slots. The machine lock (D19) applies.
- **Kill criterion:** G1 fails; at one third of the steps a checkpoint of each arm on 250 VAL frames: Q falls by more than 0.010 or lanes found by more than 0.02 against c at the same step; non-finite loss; any arm running longer than 1.5 times E232's training time (about 3100 s).
- **Inputs:** ready: the builder checkpoints, the SD library, `RouteXNet`, `p16_interface.py`, `e2e_gradient_report.py`, the failure-frame stream, `route_success`. To build: see step 2. Launch through `run.py` with planned ledger rows (`ledger.py add`) and the rule of this card; TEST never.
- **Follow-up E270 (not scheduled):** the full soft-node design: `RouteXNet` applied to the beam nodes with a differentiable cross-section, a zero-initialised `pi` input and link attention bias (new code in `MLayer` / `XLayer` / `RouteXNet`, `mask` is a boolean padding mask today), the node-to-vertex read-out (`assemble` exports only the best node per vertex, `src`; a validity-weighted mean needs `vid`, shared numba-duplicated code), the optimiser groups for the new parameters, and gate G0 as a diagnostic (the base head on raw nodes against vertices, numpy, computable on day 1 of E270). Its cost is 4 - 5 days of coding and about 8 GPU-h (eight evaluations at about 2670 s). Written only after a KEEP here.

Pass 2 REVISE (the first revision's head interface did not exist). Pass 3 REVISE (no route-success bootstrap exists, rule wording differs from `decide.py`, G0 order and threshold, read-out plumbing missing, null range, cost, a cheaper proxy exists); this version is the proxy the third pass proposed.
