# 2409.18737 MemFusionMap: fixed-lag working memory of 4 warped BEV frames with an overlap heatmap

**What it does**: Online vectorised HD-map construction. A working-memory buffer holds the BEV features of the last T_WM=4 frames (fixed lag: add the newest, drop the oldest). Each is warped into the current frame by the ego transform with grid sampling. A temporal overlap heatmap, starting at all ones ("unseen"), is warped with zero padding for out-of-bounds cells and incremented by 1 per step; a small conv block with a sigmoid turns it into 32 channels. Fusion: concatenate heatmap channels, the 4 memory features (4 x 256) and the current feature (256), then a dilated conv block (dilation 2, 2) and LayerNorm. Everything stored is static map content; there is no moving-object path.

**Results that matter** (mAP, new splits, R50, 24 epochs): nuScenes 60 x 30 m StreamMapNet 34.1 vs 38.0; nuScenes 100 x 50 m 22.2 vs 27.6; Argoverse2 60 x 30 m 58.3 vs 60.6; 100 x 50 m 51.5 vs 54.3. 15.1 FPS vs StreamMapNet 15.3 FPS on nuScenes at 30 m; MapTracker 11.6 FPS and 40.3 mAP at 72 epochs. No memory measurement on the page; it stores 4 maps plus a heatmap, against one latent state for StreamMapNet.

**Transferable technique**: the overlap / age heatmap as an input channel (the net knows which cells carry old information and which are fresh); fixed-lag buffer instead of an infinite recurrent state, so no error accumulates. Both are local to the BEV and cost almost nothing at 0.5 m.

**Cost and fit**: 4 x 256 channels at the BEV size, a dilated conv fusion, essentially free in FPS (15.1 vs 15.3). Camera-based BEV encoder, not used by us.

**Doubts**: Vector map task, camera only; the gain against StreamMapNet is not separated into memory size vs heatmap; no moving-object consideration (not needed for map classes); no ablation numbers read for the heatmap alone.
