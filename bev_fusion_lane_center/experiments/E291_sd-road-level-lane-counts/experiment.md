## 1. The input (what is in it, what is not) and the step 0 numbers
Built on the lane side from the lane GT, by location (`jgt.junction_gt(g)["arms"]`, computed in `QData.__getitem__` for TRAIN and VAL frames; the staged data path puts the arm list into the batch, padded, with ONLY the fields `c` (centre), `t` (heading into the junction), `n_in`, `n_out`; `spread_in`, `spread_out` and the zone are NOT copied). **What it really is (critic finding 2):** `n_in` / `n_out` are the numbers of clustered GT END points of an arm (1.5 m / 40 degree clusters of connector-run starts and ends), `c` and `t` are means of GT end centroids and headings: a fan-out lane counts once, a lane cut by the window is absent, a short run is absent; this is not a lane tag of a road map (a real `lanes` tag counts lane pieces; `sd_lib.build_sd` of this project does that, as a road raster, without an arm table: not reused because the pair head needs positions per arm, and the nuScenes map API gives no per-direction count). So **the 0 % row is an oracle on the end targets and the arm geometry**; the report says so; a real-tag variant is a follow-up. Not in the table: connectors, lane ids, successor / predecessor / left / right relations, lane index, dividers, crossings, stop lines, the pair identities. **The corruption model (what a real map does wrong), a pure function of (frame token, zone, r), per frame (a scene-constant shift would need the ego pose; `sd_lib.scene_pose_error` is not used):** each arm's count (per direction) is wrong with probability r: replaced by a random count in {0, ..., 5} different from the true one (a gross error, not only +-1; a +-1 read-out is added, table only), and 15 % of the arms (in b's training and in the unknown read-out) are marked UNKNOWN (count 0, flag 1: the unknown flag and the absent flag are the SAME channel); the arm centre shifts by up to 2 m and the heading by up to 5 degrees (iid per frame); an arm is dropped with probability r / 3 (a road missing in the map); a frame with no junction GT (`jg is None`) gets an empty table: every keypoint absent. The 20 % junction dropout is OFF at read-out (the "0 %" row has no absent maps). **Step 0 (CPU, no GPU, before anything is trained; the ceiling for the gain):** on the 873 VAL frames with the stored E312 dumps (`runs/e312_p_s*/ends_val.pkl`) and the `junction_gt` arms of the same frames: per arm and kind, the number of REAL keypoints (peaks of the heat, `valid & real`) within 6 m of the arm centre and heading-aligned against `n_in` / `n_out`: the shares of arms with deficit (found < n), exact, surplus (found > n), and the GT pairs lost behind a deficit (a pair head cannot add a missing end) and the false pairs behind a surplus; **the gain a count can give is bounded by these shares**; result in this card before the build starts (section 3).

## 2. Design
- **The input, differentiable and gated (D88):** per keypoint of the pair head (entries and exits) the features `[n_arm / 4, unknown / absent flag, distance to the nearest arm axis / 20 m, heading agreement (cos), (the keypoint's rank among the arm's keypoints by lateral offset) / max(n, 1), (real keypoints found in the arm - n) / 4]` through a small MLP (`6 -> 16 -> 1` gate logit and `6 -> d` features) added to the keypoint token before the SetBlocks as `token += sigmoid(g) * f`; `g`, the output weights of `f` and their bias are initialised so that the term is ZERO: **the model starts as E312 (checked with the E312 checkpoint loaded, `strict=False`)**; the module lives INSIDE `JEnds` so that the trainer's parameter set contains it. **Real peaks only (critic finding 3):** `JEnds.forward` injects GT end cells as keypoints in training (`gt` given, score 2.0) and not at evaluation; the "found" and rank features use `valid & real` (as `rank_matrix` does) and the count compared is kind-specific (entry keypoints against `n_in`, exit keypoints against `n_out`); a test proves the features are identical with and without the GT injection on a frame with no real peak. A keypoint with no arm within 6 m is absent (features 0, flag 1). Batch-wise torch (cdist to the padded arms, same-arm masks), no host loop.
- **Named hard steps on the input side (D88; critic finding 7):** the nearest-arm `argmin`, the 6 m presence gate, the rank sort, and the DETACHED keypoint positions: the gradient of the prior path stops at the keypoints, so the map cannot shape the heat in this card (a follow-up: a soft association by a softmax over the arms, zero parameters). The output side is unchanged (the delivered graph's named steps stay).
- **Arms and read-outs:** c = E312 stored + the recipe twin (flag off); a trained clean (+ 20 % absent), b trained with corrupted counts (as above); each of a and b read at: clean (0 %), 10 %, 30 %, +-1, **U (all counts unknown, geometry kept)**, **S (the table of ANOTHER frame, rate 0)**; each read-out as a dump into its own run directory `runs/e291_<arm>_<run>_<readout>/` (a copy of `model.pt` and `config.json` and `ends_val.pkl`, written by the staged `jends_eval.py dump --prior-noise r --prior-mode ...`; `qends_eval.py score` reads `runs/<run>/ends_val.pkl` and is frozen: it is called on those directories with unique `--tag`s, so no stored card is overwritten); snapped (`--thr 0.1 --snap`) and unsnapped (`--thr 0.1`) cards for each.
- **Why two arms and many read-outs, not a training run per noise level (default):** the questions "what does a clean map give" and "what does a wrong map cost" are read-outs of two models. Attribution: a and b both have the gate; the robustness of b is attributed to the CORRUPTED TRAINING, the contrast a-at-30 % against b-at-30 % is the measurement of it.
- **What it needs in code (staged copies, new files where possible):** the arm table in the batch (staged `lane_gt_data.py` / `qjunction.py`), `training/grid/jprior.py` (new: the corruption, the features, the gate; imported by the staged `jends.py` with a `prior` flag, default off = bit-identical to E312), `jends_train.py` flags `--lane-prior --prior-noise {0, mix}`, `jends_eval.py dump` flags, the leak and identity tests, the analysis code of the splits, `temp/e291/start_arms.sh` (exports `BFLC_SIG=1.0`; the other environment variables of the E312 launch are checked from its run record: `BFLC_RASTER` defaults to legacy, which matches). **Staging mechanics:** `jends_train.py` inserts the real folder into `sys.path` at index 0, which shadows PYTHONPATH: the launcher is the meta-path finder of `temp/e347/stage_launch.py` (E347's), `temp/e347/run_staged.sh` sets `CUDA_VISIBLE_DEVICES=""` (CPU only), so a GPU variant `temp/e291/run_staged_gpu.sh` is built; after the first start the run's tag is checked for `temp/e291/stage`; the GPU slots depend on D102 (open) and D57 (lane work first).
- **Prediction (numbers, a guess, not derived; written before the run):** clean map (b, G): **+0.008 topo F1** snapped; the U read-out about **+0.002** (the geometry alone gives little); a at 30 % wrong **-0.02**; b at 30 % wrong **-0.003**; the gate norm falls with the noise. **Power (critic finding 4):** the stored E312 seeds differ by 0.004, so a single run against the stored control has an SD of about 0.004; with a true effect of +0.010 the probability that both seeds pass +0.01 is about 0.25, and R passes with probability about 0.45 at a true -0.003: the card is a MEASUREMENT read through the pooled interval, the recipe twin and the U read-out, not a threshold gate; a TIE with an interval that excludes the band's upper edge is the likely outcome and an honest one.
- **The discussion the numbers feed (Mirko's question):** PROS: the count per direction is cheap and nearly always in a road-level map; it says how many entries / exits an arm has (a missed far lane, a duplicate); it costs no compute (a table lookup). CONS: maps have gross errors (construction, new markings, wrong tags), a wrong count is trusted by a network that learned from a clean map (a at 30 % shows the size), the count says neither WHICH lane nor WHERE (no connections) and a stale map misleads; the gate and the corrupted training of b are the E2E answer (learned doubt) instead of a rule; and the clean row here is an oracle, the real gain with a real tag is smaller (step 0 bounds it).
- **Not claimed:** anything about lane-level maps (stay out: Mirko's correction), an exact-map upper bound as a RESULT (the clean row is labelled an upper bound), TEST (not used), the maps head as a consumer of the prior (a follow-up), real OSM tags of nuScenes (the table is built from the lane GT and corrupted by a model of map errors).
