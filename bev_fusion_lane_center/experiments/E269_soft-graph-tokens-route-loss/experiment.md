## 1. Card
| | |
|---|---|

- **Statement:** a route head that reads the builder's beam nodes directly (position, token, validity, link weights as differentiable inputs) lets the route loss improve the builder where the same loss through the assembled graph did not (three negatives).
- **Re-opens a closed question** (`closed_questions.md` row 7: "does a route loss through the builder beat continued route-head training? no, three times"). Its re-open conditions (route loss not saturated on the training frames, or a builder not frozen at the start) were already met by E214 / E232; the new reason is a new mechanism: soft node tokens.
- **What is known about the old path** (read in `p18_joint.py:150-177`): the route head receives `xy` and `cp` as numpy arrays from the assembled graph, `keep` / `pi` is never an input, and the token is `M @ h[src]` with `M` the node-to-vertex resampling. So the only route-loss path into the builder is through `h`; since `h` is a function of the whole builder, some route gradient reaches seeds and ray read-out indirectly. How much is not measured; gate G1 measures it. What the old path cannot do: move the positions, change the validity or change the link weights because of the route loss.
- **Other explanations of the three negatives, not excluded:** the failure-frame stream (`--real_fail 1 --share 0.5` in E214 / E232; the failure-trained head alone lifts route success by +0.15 ... +0.37 over the base head, E232.c0 against the base, which dwarfs the effect tested here), seed noise (E232 is one seed per arm, E214 two; both results lie inside the seed spread), the route loss weight against `lam`, and the fp16 grad scaler.
- **Design:** the head is `RouteXNet` (CNN plus cross-attention over the whole SD map, 3 self-attention layers; initialised from the base head, so it starts as strong as arm b's body and keeps its global map context), applied to the beam nodes instead of the assembled vertices: `xy_i = pos_i` (differentiable), token `h_i`, the cross-section from the parent edge geometry, `keep_i = pi_i`, and the link probability as the attention bias between linked nodes. Loss: route BCE at the nodes, weighted by `valid_i` times `pi_i` **with stop-gradient on the weight** (otherwise the route loss can fall by lowering the validity of nodes the head gets wrong, trading lanes found for route loss; the guards below would catch it only on clean frames), masked to nodes within a cutoff distance of a ground-truth lane point (value fixed in the detail plan; E232's target came from `route_heat_train.npy` at the vertex with the map faults of `RTR.draw_cell`, the same target source is used). The vertex-level route flag of the delivered graph is read from the node logits after the network by a validity-weighted mean over the nodes that make up each 4 m vertex; the consumer input is produced the same way. This is a train / evaluation shift (training on raw beam nodes, evaluation on assembled, resampled vertices): it is named here as a risk and measured by arm b against arm n.
- **Streams and controls:** all arms train on the same stream as E232: real failure frames (`--real_fail 1 --share 0.5`), the builder loss at the same weight (`lam 1`), the same steps (4800), optimiser and learning-rate schedule. Arm c differs from a **only** in that the route-loss path into the builder is cut at the node inputs (positions, `h`, `pi`, link weights detached) while the builder keeps training on its own loss; E232's arm c detached only `h`, this one is stricter. a - c therefore measures the route gradient, not builder fine-tuning. Arm b names what the new head costs or gains against the deployed failure-trained head; arm n gives the start values the guards refer to.
- **Not comparable to E232 numbers:** the card starts at `e123_D7_r3_j1` (no recursion, 192 / 96) where E232 started at `e123_D7_r3_f1`, the head body is new code on nodes, the builder learning rate here is 0.3x for the stem as in `p18_joint.py:112` (the earlier draft said the whole builder; corrected). Compare a with c, b and n of this experiment only.
- **Chain scored and headroom:** the chain without the map net, as E232 (E232 arms: night 0.70, blur 0.80, three cameras off 0.57). The best chain (E220, with the map net) already reaches 0.83 - 0.91, so the headroom for this effect is in the base chain; the result says nothing about the best chain until it is repeated there.
- **Prediction:** a - c = +0.05 route success in at least two of the three types. The earlier draft predicted +0.03, equal to the threshold; the seed spread (0.05 - 0.09 under failure, `PROTOCOL.md`) makes a 2-seed mean difference uncertain by about 0.03 - 0.05, so the prediction is set above the threshold and the rule also demands equal sign in both seeds. The probability of passing under the null (no effect) is computed from the E214 / E232 spreads in the detail plan and written into the summary.
- **Decision rule:** KEEP if the rule of section 0 holds; CUT if a - c <= 0 in all three types in both seeds (a fourth negative closes the joint line, and the closed-question row is updated); otherwise TIE, take the cheaper arm (c); INCONCLUSIVE (seeds disagree) means the third seed, not an adoption.
- **Gate G1 (before any training run), measured with `evaluation/drivers/e2e_gradient_report.py` extended to the route loss alone:** (1) a "before" table: the route loss alone through the old `p18_joint` path, per module group; (2) the same for the new path; the route-loss gradient norm of the seeds, ray read-out and link groups in the new path must be at least 5 % of those groups' builder-loss gradient norm and larger than in the old path (a stated floor, not just "nonzero"); (3) a finite-difference check that the gradient on `pos_i` through the bilinear SD sampling is nonzero and has the right sign (the SD raster is a thin-line image, so the gradient is local to a few cells; the sampling must see a wide enough neighbourhood); (4) the junction head is not in G1 (the token design does not read its heat); (5) a unit test that fails when the soft path is replaced by the old hard one. If G1 fails the code is wrong; that is a bug, not a result.
- **Cost / kill criterion:** coding 2 - 3 days, about 3 GPU h. Kill: G1 fails; Q falls by more than 0.010 at one third of the steps; lanes found falls by more than 0.02 at one third of the steps; non-finite loss.
- **Inputs:** ready: the builder checkpoints, the SD library, `RouteXNet`, `p16_interface.py` (contract), `e2e_gradient_report.py` (G1 base), the failure-frame stream of `p18_joint.py`. To build: the node-input adapter for `RouteXNet`, the soft target with the distance mask, the joint trainer wiring, the node-to-vertex read-out for the metric and the consumer.
