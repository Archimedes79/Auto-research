# can22-minimalcycles Minimal-cycle topology supervision for a local road network

- title: Topology Preserving Local Road Network Estimation from Single Onboard Camera Image
- relevance: 1
- summary: CVPR 2022 DETR-style head: Bezier lane centrelines from one front camera, a pairwise MLP on query embeddings for which curve continues into which curve, and an auxiliary minimal-cycle cover target that fixes the order of intersections. The pair head is a plain recipe: BCE with positives weighted 3, plus an endpoint pull loss; the cycle target adds only +0.1 connectivity F on nuScenes and +3.2 on Argoverse, and the paper has no junction-only pair metric. Partial code, no licence, offline cycle extraction.

**What it does** (checked: paper full text via ar5iv https://ar5iv.labs.arxiv.org/abs/2112.10155, code files below): From one front image (448x800) a DETR-style decoder with 100 curve queries predicts directed lane centrelines as Bezier curves with 3 control points, an existence class, and per-query association features. Which curve continues into which is a classifier on every ordered pair of matched queries (concatenated features, one logit), trained with BCE against the successor matrix of the map (nuScenes map API outgoing lane ids over lane and lane_connector tokens). A second set of 100 cycle queries predicts, per minimal cycle, a membership vector over the curve slots plus 5 BEV-boundary slots, an existence flag and a centre; a minimal cycle is a closed polycurve whose inside no other curve crosses, and its set of member curves ("cover") fixes the order of intersections along each curve (the paper's Lemma 3.1 and Corollary 3.2.1, not re-derived by us). At test time the connected curves are merged so that end points coincide (a rule step).

**Results that matter** (checked, paper Tables 1-4 as extracted from the full text; Tables 1 and 2 were read twice with identical numbers, Tables 3 and 4 once; deltas are our arithmetic): nuScenes, transformer variant without / with the minimal-cycle branch: connectivity F (C-F) 55.2 / 55.3, minimal-cycle F (MC-F) 62.0 / 62.5, detection 59.9 / 60.2, intersection-order edit distance (lower is better) 0.800 / 0.776. Argoverse: C-F 54.9 / 58.1, MC-F 57.4 / 58.5, detection 60.1 / 64.2, order 0.893 / 0.883. The Polygon-RNN variant gains much more in C-F (24.5 to 49.9 on nuScenes) but starts from a weak baseline and the paper does not isolate why. 11 FPS without batching including association steps, GPU not stated.

**Transferable technique** (K id not registered): (1) pair head recipe: node or query embedding, ordered-pair concatenation, MLP to one logit, BCE with positives x3, supervised only on matched nodes; (2) endpoint coupling `loss_end_match`: positive pairs pull the end of i to the start of j (2 x L1 distance), negatives get a hinge with margin 0.05 in normalised units (about 2.5 m on a 50 m extent, our arithmetic); (3) cycle covers as an auxiliary set-valued target for global consistency, only worth it if pairs stay below the oracle after cheaper fixes; (4) fork/merge targets `start_con_matrix` / `fin_con_matrix` (shared start / shared end) exist in the code but have loss weight 0 in the shipped script.

**Why it performs** (paper ablation, checked): only the with/without comparison of the cycle branch (Tables 1 and 2); no ablation of the pair-loss details, of the positive weight or of the endpoint term. The paper argues that predicting cycles is more accurate than a recurrent intersection-order head (TR-RNN: order 0.791 / RNN-order 0.939 on nuScenes). For the transformer variant the gains are small on nuScenes (every F-score within 0.5 points except the order distance, -0.024) and larger on Argoverse (detection +4.1, C-F +3.2, our arithmetic from Tables 1 and 2); the paper does not say which part of the cycle branch carries it.

**Cost and fit**: pair head is negligible (MLP over at most 100x100 ordered pairs); the paper states the cycle branch adds negligible parameters to the transformer. The expensive parts are offline: cycle extraction (slow, scene intervals via `interval_start/end`, or the author-provided `nusc-polygon-dicts.zip`) and Hungarian matching of curves and cycles, both tied to query slots, which our dense-node head does not have. Front camera only, 50 m x 50 m BEV at 0.25 m, one dataset family we also use; no radar, no map prior. Our estimate: pair-head port 0.5 to 1 day, GT cycles from our own lane graph 1 to 2 days, cycle head 2 to 3 days; the gain for our junction F1 is unknown and the paper's own C-F gain for the transformer on nuScenes is 0.1.

**Doubts**: (a) C-F is global over all curves, not per junction; no junction-only pair metric, no oracle-pairs study. (b) Single runs, no seeds or intervals in the text read. (c) MC-F and order are metrics that the cycle loss trains for, so they likely favour it. (d) Baselines are the authors' earlier STSU variants and PINET only. (e) The paper gives no optimizer, schedule or loss weights; the code gives them (train_tr_nusc.py: AdamW lr 1e-5, weight decay 1e-4, StepLR 50, clip 0.1) but config defaults.yml says lr 0.1 and 200 epochs, so they disagree. (f) Released code is partial: polygon targets are placeholders in dataset.py, parts of the metric code are commented out, cluster paths are hard-coded, known bugs (see code.md). (g) The paper text calls the curves lane centrelines; dataset.py builds them from lane plus lane_connector tokens, which matters for junctions and which the paper text we read does not say.

**Does not answer**: which entry lane goes to which exit lane as a dedicated target or metric; any soft or differentiable assignment (matching is under no_grad, the final merge is a rule); multi-camera, radar or BEV-feature inputs (the backbone is perspective, calibration enters only as BEV positional encoding); uncertainty of pairs; conditioning on an SD map.
