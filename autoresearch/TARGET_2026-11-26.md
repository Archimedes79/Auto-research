# Autoresearch, target design (proposal, revision 2 of 2026-11-26)

**Status: a proposal for the owner. Nothing here is built or decided.** Today's system is described in `README.md` and `METHOD.md`. Revision 2 comes from a review of revision 1 against the code, the records, the folder layout and the git state (own measurements, an analysis of the recent verdicts, an independent adversarial review). What changed:
- **Cut the existing tools down, do not build a second system next to them.** Revision 1 planned a new package of ten modules in 3,000 lines; that number was a wish. The gates in `run.py`, `decide.py` and `guard_hook.py` exist because of incidents and are tested with the real tools: they stay and get a seam.
- **No new formats.** The card block and the metric card have schemas today; revision 1 invented new ones.
- **Why the judge is not used is now known** (section 1); the first step repairs exactly that.
- **The TEST log and the grants file stay.** The idea in between (permission as a column of `DECISIONS.md`, the use only in a run record) would replace a protected register by an unprotected file, change a table that three tools parse, and it did not fit "winner + control" (two TEST runs of one design).
- **Nothing for other machines is built before one exists:** worker seam, executor and machine file are step S5.
- **New:** folder layout (section 4) and git (section 5).
- **The owner's answers of 2026-11-26** (what a broken guard means, the lane score, no second machine yet, a cloud prototype later, easy to extend to data shards on ranks) are in sections 6, 7, 10 and 12.

## 2. Principles
1. **Cut down, do not rebuild.** A proven file stays. New code only for what is new: the worker seam, the executor, steps, the result path.
2. **One fact, one place.** A copy is made once, at the close, and never kept in sync.
3. **A run executes a commit.** What is neither in the snapshot nor a linked data folder does not exist for the run.
4. **Workers compute, the controller judges.** The evaluator does the statistics, the judge only applies the rule to numbers it finds. The unit is the run: how many machines or ranks compute one run is hidden inside it.
5. **One experiment: one question, one comparison, one folder, one tag, one ledger row.**
6. **Built when needed.** Server parts are written when the first such machine exists.

## 3. Architecture
```
 OWNER  orders, decisions
   |
 CONTROLLER (today's PC) ------------------------------------------------------------------
   agents    lead (plans a round)   conductor (one per experiment)   reviewer (fresh eyes)
   records   PROBLEM  DESIGN  DECISIONS  HANDOVER  ledger   experiments/<id>/ (card, runs)
   tools     experiment.py check -> run.py (gates, snapshot) -> decide.py (rule) -> commit_paths.py
   gates     guard_hook.py (protected files)   testgate.py (TEST)   package.py, clean_temp.py (deleting)
 ------------------------------------------------------------------------------------------
        | executor: the snapshot as an archive + (experiment, arm, seed)     ^ run.json, result.json
        v                                                                    |
 WORKER (an account laid out like today's WSL home; the PC itself is the first one) -------
   worker.py   unpack the snapshot -> link the heavy folders -> GPU slot, RAM gate
               -> the steps of the arm -> heartbeat, kill rule, timeout, resume
   problem     trainer and evaluator; the evaluator writes result.json with the paired interval
   stays here  logs, checkpoints, dumps
 ------------------------------------------------------------------------------------------
```
A problem plugs in with three things: a runnable command per arm, an evaluator that writes `result.json`, and score and guards in `project.json`. On one PC there is no separate worker: `run.py` does both halves, as today. A worker is installed once per machine and has one slot store per machine; it is never run from a snapshot, so an old experiment cannot decide about GPU slots.

## 6. Contracts: today's formats, small changes
**Card block** (`schemas/experiment.schema.json`), for new cards:
1. An arm is runnable: a `command` with `{seed}`, or `steps` (commands in order, each with its `resources`, today `{gpus: 0}` or `{gpus: 1}`; section 10 says why not a flag). The launcher writes a done mark per step after exit 0 and a restart continues at the first step without one: a cut output is never taken for a finished one, and a CPU step holds no GPU slot (both learned in `jarm.py`). Prose is refused. Today 69 of 173 arms since E350 look like a command.
2. Run ids are derived (`E396.<arm>_s<seed>`). `run_ids`, `cards` and `names` are no longer listed: results are found at the fixed path.
3. Score and guards of the problem are the default rule; a card lists only what differs.

**`result.json`** is the metric card of `schemas/card.schema.json` at a fixed path: pooled `metrics`, split, frames, one `compare.paired` block per reference run (difference, interval), computed by the problem's evaluator with the one bootstrap (`Evaluation/stats.py`), and the provenance block (evaluator hash, frame hash, data hash) that BEV cards carry and none of the 321 lane cards does.

**`run.json`** as today, without the copies of hypothesis and rule (they are in the card of the snapshot), plus machine, environment hash and the hashes of declared inputs.

**`project.json`** stays. New keys: `score` and `guards` (protected), `links` (the heavy folders the code expects inside the checkout: `runs`, `data/cache`, ...). The machine keys (`gpu_slots`, `ram_mb`, `gpu_settle_s`, `gpu_max_mb`) move to a file per machine when a second machine exists (S5), not before.

**The scores.** Lane (the owner, 2026-11-26): `topo_F1` with guards, gain bar 0.010. Proposed guards, with the bars the cards since E350 use most: `junction_F1`, `F1@1.0`, `lanes_found` and `dup_frac` 0.010 each, `vert100_dp` 1.0 and at most 14.3 vertices per 100 m (`PROBLEM.md`); a speed bar is a clause of only one card and is still to be set. The best three (`keep3.json`) are ranked by Q today and would be ranked by the score. BEV: `board7`, the mean of seven keys its `keep3.json` already ranks by (band 0.02); assumed, not asked.

**Diagnostic runs** (`run.py --no-card`: 81 of 137 BEV rows, 102 lane rows) stay as they are: a run record and a ledger row, never a verdict.

Existing files are used, not replaced: `keep3.json` (best three), `data/NuScenes/manifest.json` and the lane's `data/rebuild.json` (data by hash and how to rebuild), `tools/env/environment_gcar.yml` (environment).

## 7. Judge and scores
| case | verdict |
|---|---|
| a listed run is missing, failed or was killed | none (incomplete); a kill may name its verdict in the card |
| results not comparable: split, frames, evaluator, data or resources differ (unless the card says that is the question), or the runs come from machines of different classes (section 10) | VOID |
| gain above the band, interval above zero on every seed, all guards hold | KEEP |
| the same gain, a guard broken | TIE, "not adopted: guard ..." |
| loss beyond the band, interval below zero | CUT |
| inside the band | TIE (the cheaper variant stays) |
| anything else | INCONCLUSIVE (add a seed) |

Today `decide.py` cuts on any guard miss (its line 436); the lane cards since E358 say a guard blocks a KEEP and does not cut. **The owner (2026-11-26): not adopted, and the result and the reason are logged.** So the ledger row and the result block of such an experiment say TIE, the gain with its interval, and which guard broke, by how much, against which bar; all gains that were not adopted are then one filter of the ledger. Clause forms to add, each seen at least twice in the sample: an absolute bar (no reference), several references, named read-outs of one run, a kill with a verdict. Not built: labels per seed with an ordered list, bars derived from an earlier stage, normalised scores. Such a rule is judged by hand, with a reason, and counted. Better: split the programme, a stage gate is its own experiment and ledger row. The reviewer sends back a card whose rule the tool cannot apply unless it says why.

**Product score:** one per problem, a primary metric that counts only while the guards hold; no weighted sum. **Research score** per round, never a verdict: gain of the best network per GPU hour, share of tool verdicts, prediction hits, failed runs. Many machines mean many comparisons: a second confirmation split becomes necessary before that.

## 10. Server environments
**A worker is a Linux account laid out like today's WSL home:** the same interpreter path and the same data paths, so no code changes (`server.md`, rows 2 and 7). It receives the snapshot as an archive, so it needs neither git credentials nor a clone. Only `executor.py` knows how to reach it: `submit` (send the archive, start `worker.py` detached), `status` (read `run.json`), `stop` (a stop file), `fetch` (copy the two json files). The worker itself is installed once per machine and updated by the controller; every run on a machine goes through its one slot store.

| level | landscape | executor | data | who queues | to build |
|---|---|---|---|---|---|
| 0 | one PC | none: `run.py` as today | in place | the slots of `run.py` | S3, S4 |
| 1 | PC and one Linux box | ssh | copied once | slots on the box | S5 |
| 2 | several boxes, rented GPUs | ssh | per box | controller picks a box per seed pair | the choice of the box |
| 3 | cluster with Slurm | `sbatch` calls the same worker | shared file system | Slurm (the worker skips its slot gate) | a submit command |
| 4 | elastic cloud | a platform (SkyPilot, Kubernetes) | object store to local disk | the platform | an adapter, a container from the environment file |

**Data: copy or rebuild, never mixed.** A copy has the same bytes. It is checked against a list of files with sizes and content hashes, made once at the copy (the raw data has one, `data/NuScenes/manifest.json`; the caches have none, and today's checkpoint hash reads only the first and last 4 MB of a large file). Its results compare with the controller's. Today a missing GT store is rebuilt without a question (up to 600 minutes, BEV `project.json`); on another machine the launcher says so before the start. A cache rebuilt on other hardware (features from a GPU forward pass) is a new data version: every arm of a comparison, the control included, must use it. Sizes named by the data READMEs: lane 28 GB raw and 54 GB features plus further caches (2026-10-24), BEV a 26 GB camera feature cache. What one experiment needs is not measured.

**Rules**
- The controller connects to workers, never the reverse. Workers hold no language-model key and no GitHub credential. Agents run on the controller.
- A new machine first repeats a stored run. If the numbers agree within the seed spread it joins the class of the controller: quality numbers inside a class compare and a stored control may be reused; across classes the verdict is VOID. Speed is measured on one reference machine only, with all its slots taken.
- The holdout split runs only on the controller. Whether the lane caches keep its scenes in separate files is not checked; until then such files are not copied.
- A run that needs another run's checkpoint runs on that machine.
- A run's result counts only after its final checkpoint is in a second place the owner controls: the controller's store, or for large ones a bucket, recorded by address and hash. A machine that dies must not take the only copy with it (hard rule 5). A rented machine is released only after that.
- The lead is woken by a `status --wait` that returns when a run changes state, not by file monitors.

| failure | what happens |
|---|---|
| connection lost, controller asleep | the run goes on; the next status fetches it |
| worker process or machine dies | old heartbeat: stalled; a restart resumes from the checkpoint, same machine, same snapshot |
| machine gone for good | run failed; its seed pair runs again elsewhere |
| a linked folder or declared input is missing or has another hash | refused before the GPU is used |
| kill rule or time limit | stopped; no `result.json`, so no verdict unless the card names one |

### Large-scale training: data shards on ranks (the owner, 2026-11-26; not scheduled, it starts on the owner's word)
The owner wants no second machine for now and later a prototype of cloud operation. The system shall be easy to extend to a context where data shards are distributed onto ranks for large-scale training.

**Two kinds of "several computers".** (a) Many small runs side by side, one GPU each: the sections above. (b) One run that many ranks compute together (ranks: the processes of one distributed training, one GPU each, on one node or many). Kind (b) lives inside a run. Card, snapshot, result, judge, ledger and git do not see it: the contract is (snapshot, experiment, arm, seed) in, `run.json` and `result.json` out, whoever computes.

**Today** no code trains with more than one process: `trainkit` takes one device, 12 lane and 3 BEV training files name `cuda` directly. The BEV feature cache is already stored as one shard per scene with an index file.

**Fixed now, so that the extension stays small** (design only, nothing to build):

| point | rule | why |
|---|---|---|
| resources | an arm or step declares `resources`: today `{gpus: 0}` or `{gpus: 1}`, later nodes and GPUs per node; the number of ranks follows from it | no format change later; the launcher never assumes that a run is one GPU slot |
| command | the problem's command does not know how it is started; the executor puts the rank launcher of the site in front (`torchrun`, `srun`) | the same card runs on the PC with one rank and on a cluster with many |
| data | a dataset is a manifest: its shards with size and hash, and a root that every site resolves for itself (a folder, a parallel file system, a bucket). Which rank reads which shard is computed by the training code from the manifest, the number of ranks, the seed and the epoch; it is never typed and never stored per rank | the data stay where the compute is; the split over ranks can be repeated |
| run folder | one per run; only rank 0 writes log, status, heartbeat, checkpoints and the done flag; a stop request reaches every rank; a rank that dies fails the run | the run-folder contract of `Training` holds, so status, health and watch work unchanged |
| run record | also holds the number of ranks and nodes, the hash of the manifest and the batch size in effect | the facts that change a result |
| comparing | the arms of one experiment use the same resources, unless scaling is the question of the card | another number of ranks is another effective batch size |
| checkpoints | stay in the store of the site, recorded by address and hash | too large to copy back |
| who queues | the scheduler of the site; the launcher runs without GPU slots of its own (`run.py` without `--gpu`, the third way of `server.md`) | no second scheduler |

What changes when it is built: `trainkit` gets a loop that knows its rank (wrap the model, split the shards, write as rank 0 only, pass the stop request on): the largest piece. A problem's loader reads shards by the manifest; its evaluator may run on many ranks but writes one `result.json`. Launcher and executor turn `resources` into the rank launcher or the submit command of the scheduler. Card, judge, ledger, git and the gates do not change.

A prototype in three stages:

| stage | where | what it shows | needs |
|---|---|---|---|
| P0 | this PC: a third, tiny problem (the minimal example of `trainkit`, a small public dataset), two ranks on the one GPU or on the CPU, shards from a local folder | rank 0 writes alone, the split of the shards repeats, stop and resume work, the judge sees an ordinary run; and every place where the tooling assumes nuScenes or the WSL home | nothing from outside |
| P1 | one rented machine with several GPUs, reached by ssh; the shards are fetched there from a bucket | the snapshot as an archive, data that never touch the PC, checkpoints by address | an account, a budget, the OK for remote actions and installs (hard rule 6) |
| P2 | several nodes under a scheduler | the submit command, a shared store | a real need |

Not lane or BEV for the prototype: it shall test the system, not 100 GB of caches and a compiled environment. Expensive runs also change the method: fewer seeds are affordable, so kill rules and the early look at a run weigh more, and the confirmation split is needed sooner.

## 11. The hard rules
Enforced by the same code and the same files in every step: TEST by `testgate.py` with the protected TEST log, in `run.py` and in the lane evaluator (the result of a TEST run lies with its experiment like every result; permission and the register of uses stay in the log); protected files by `guard_hook.py` with the grants file; verdict runs by `run.py`; the rule fixed before the run by the card's hash in the run record (`card_sha`), now also by the card inside the snapshot; deleting only by `package.py` and `clean_temp.py`; the owner's decisions by `DECISIONS.md` and the hold marker. New refusals: a remote worker refuses the holdout split; a machine is not released while a checkpoint is unsecured.
