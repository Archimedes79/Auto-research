# E357 - T0 of the token design: the ground-truth nodes as tokens, ONE pair head predicts every edge (lane links and junction links), between rule controls and the GT edges

Card of 2026-11-15 20:00, version 2 of 20:10 after the first critic pass (REVISE: junction F1 does not measure the junction links; the GT piece ids in the read-out flatter the head; the rule control was trivial in the junction; the outcome classes overlapped; the loss weights that decide the result were not written down; a PASS is largely predicted by E283). Written by the Spurmitte chat that Mirko addresses as "Fable" on his go of 2026-11-15 (D105, verbatim: "Ja, T0 vorbereiten"; D84 point 6 is lifted for this stage only). Stage T0 of the design card E355 (section 7). Status: card; code in progress; no run.

**The one question.** The token design E355 rests on one new claim: a SINGLE pair head on a single node set can decide every edge of the graph, the lane links and the junction links entry -> exit, so that the second node family (keypoints), the snap and the wiring are not needed. B had that code and could not learn its junction part (junction F1 0.123 / 0.118; 0.271 / 0.249 with the hard close-node step). T0 isolates the claim from the node problem: the nodes are GIVEN (the ground-truth node table of B's code on the 2.5 m lattice), only the edges are learned.

**What a result can and cannot say (written before the run).** A PASS is largely predicted and is not news by itself: E283 found that a geometry-only classifier on EXACT GT ends reaches pair precision 0.94 / recall 0.95 on VAL (0.88 / 0.84 with the junctions held out), and that the pair recall falls from 0.78 to 0.41 to 0.25 as the ends become noisy, missing and false; 747 of 825 VAL junction frames show a junction that TRAIN also shows, so a PASS may be partly memory. And "types not given" is only formal: in the GT node table an entry is a node without a near successor, an exit one without a predecessor, and event nodes sit at exact event positions, so the node set itself encodes the junction. So: **a PASS says "one head connects a node set that encodes the junction", which is the precondition of T1 and no more; a FAIL is the informative outcome** (the design stops cheaply); and the number that says most about what follows is the DEGRADED read-out (17 % of the nodes removed, B's node recall), reported with it.

**What is given and what is not.** Given to the head, per frame: the positions and headings of the GT nodes (about 145 - 155 per frame at 2.5 m; padded to the batch maximum from the data), and the frozen features of B's pyramid sampled at the node positions (in-sample on TRAIN, as for every head on B's pyramid; seed S uses the pyramid `runs/e273_p_s<S>`, so the seed couples pyramid and head). NOT given to the head: the node flags, the piece or section ids, anything of the junction GT maps. Training uses the TRAIN rows only; the scored model is the final one (step 3000), nothing is chosen on VAL.

**The verdict, written before the run (by hand, label "by hand: oracle-node replay"; this text is the rule of record; the JSON block is a proxy with a far lower bar and `decide.py --write` is never run on it).** Numbers: `qgraph_eval.score_frames` on the 873 VAL frames inside the lattice context, threshold p >= 0.5 fixed here. **The read-out of record has NO section ids** (every node `section` = 0: the read-out cuts at branches by itself), for all arms alike: with the GT piece ids a false link at a mid-piece node is inert (the read-out wires a link across sections only at the end of a chain), which would flatter the head; the GT-section read-out is reported next to it and used for the reproduction check. Two gate metrics:
- **G1, the whole graph:** topo F1 of p against the BEST rule (lo / lo_near / lo_all) and hi: gap share g1 = (p - best rule) / (hi - best rule).
- **G2, the junction links at pair level** (junction F1 is NOT used: it counts points of degree three or more within 3 m and does not see which entry is joined to which exit; E283: true pairs 0.300 against all candidate pairs 0.294): the F1 of precision and recall of the predicted long links (chord above 8 m, p >= 0.5) against the GT junction links (the long links on a connector path, the definition `conn_long` of the E346 tool).
Order of reading, exhaustive: **FAIL first:** on both seeds g1 < 0.5, or on both seeds junction-link F1 < 0.50. **Then PASS:** on both seeds g1 >= 0.5 AND junction-link F1 >= 0.75. **Else INCONCLUSIVE:** one refinement round, named now (the junction links get zone / core as auxiliary token outputs and as evidence), then the same rule, and INCONCLUSIVE again counts as FAIL. A gate metric whose anchors are closer than 0.10 (hi - best rule on topo F1) is void and named. A PASS proposes stage T1 to Mirko (D105: his word again); a FAIL stops the token design before T1 (D106 keeps the system we have).

## 1. Card text
- **Statement:** given the right nodes and no types, one pair head recovers at least half of what separates the best link rule from the true graph and joins the junction pairs with an F1 of at least 0.75.
- **Mechanism:** the pair head of the junction layer ranks entry -> exit pairs well on its keypoints (AUC 0.930 on the maps' own features, 0.974 for the E284 head among true ends); a lane link is an easier pair of the same kind; the set blocks let the tokens of one arm see each other.
- **Inputs:** read-only (E343 freeze: imported, never edited): `qtargets.node_table` / `fit_long_scales` / `decode`, the lattice at run time (module constants `QT.N`, `QT.RES`, set and asserted in the main process and in every data-loader worker; the cache key holds the lattice and the lane GT signature), `qformat` (a flat list of node-index pairs with p, long, a, b), `qgraph_eval.readout` / `score_frames` / `val_frames` (lattice-free, except that the scorer's own `nodes` block calls `node_table` and is therefore not reported), the cached features (read directly: `QData`'s item path renders 2 m grid targets), `jmaps.JModel.load_base` (the frozen pyramid), `jends._hermite / _bezier_s / _sample`, `qlinks.SetBlock`, `qendnet._dual_softmax`. **Not ready:** arm l25 of E356 (the same ceiling on 873 frames) is running in the lane experiments chat's chain; it is compared with hi when it exists and its absence is named; the mandatory check is the 2.0 m reproduction of E346's l2.
- **To build, NEW files only:** `training/grid/jtok.py`, `training/data/lane_tok_data.py` (cache under `runs/e357_cache/`), `training/train/jtok_train.py`, `evaluation/jtok_eval.py` (`ctl` with the three rules, hi and `--check`; `dump`; `score` with both read-outs, the link tables and `--drop 0.17`), `training/grid/test_jtok.py` (the geometric features equal `JEnds`'s on the same pairs; a GT edge list through the writer scores like `oracle_prediction`; the rules on a hand-made frame; the share of TRAIN GT links outside the allowed gate, with the 0.5 % stop; a gradient reaches the token encoder; permuting flags and piece ids leaves the logits unchanged; pad / mask invariance; the lattice constants inside a worker).

- **Not claimed:** anything about predicted nodes, duplicates, spacing, ends as types (T1 - T2 of E355); a comparison with E324 s; TEST.
