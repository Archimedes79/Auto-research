# P0: one small problem through the whole tool chain (plan of 2026-11-26)

**Status (2026-11-26): P0.1 - P0.5 are built** in `examples/toy/`, since the evening of 2026-11-26 in `../problems/toy/` (step S0 of `INTEGRATION_2026-11-26.md`, which supersedes this plan where they differ; its `README.md` has the commands, the result of the first experiment and the list of frictions); P0.6 and P0.7 are not. Differences from this plan: the splits are in the data manifest (no `splits.json`), the ignore rules are a file inside the toy (the root file is untouched), no commit has been made, and the code is about 1,000 lines with tests instead of 650. The owner's order: build simple first and for P0, plan the tool use for ground truth, debugging, training, running, evaluation and reporting (numbers, pictures, compute time), say what is general and what belongs to a problem, keep it extensible, and propose a folder layout. The long-term design is `TARGET_2026-11-26.md`; this page is its first step.

## 1. What P0 is
One tiny third problem, `autoresearch/examples/toy/`, that goes through every activity on this PC, on the CPU, in minutes: ground truth, training, running, evaluation, verdict, report; then the same training on two ranks with data shards.

Why it is the right first step:
- **Every suite has a toy of its own, none goes through all of them.** `trainkit/selftest.py` (a net and a loss), `Evaluation/adapters/minimal.py` (about 70 lines: a disc in noise, a threshold "network", IoU) and `adapters/toy.py`, the synthetic run folders of `Training/selftest.py`, the throw-away project of `tools/selftest.py`. P0 is the missing chain test with the real tools.
- **It measures instead of assuming.** The toy uses the general tools as they are. Every place where they need nuScenes, a BEV grid, a GPU or the home folder shows up as a friction; that list is the work list for the general code (and for steps S1 - S4 of the target design).
- **It touches no running work.** Steps P0.1 - P0.5 add one folder and two ignore lines (the toy's `runs/` and its data store) and change no existing code.
- **It stays.** Afterwards the toy is the end-to-end test of the system and the template for "plug in a problem".

Not in P0: other machines, the executor, the worker split, new formats, any change of the lane or BEV code, a rebuild of `GtGenerator`, one shared Runner, one shared report builder.

## 2. The toy problem
A scene is a disc that drifts through a 32 x 32 image for a few frames; the raw frame is the disc in noise; the truth is the disc mask; the network is a small convolution net that segments it; the metric is IoU, the score of the problem. It is the learnable form of `adapters/minimal.py`. It has everything the real problems have, in small: raw data in shards with a manifest, a ground-truth step with a signature, scenes for the paired comparison, pictures that mean something, a forward pass to time, and settings to vary (loss weight, width) for a real experiment with two arms and two seeds. Raw data are made by code from a seed: no download, and any machine can make the same bytes.

## 3. Tool use per activity
| activity | who, when | general code (exists today) | the problem supplies | output |
|---|---|---|---|---|
| ground truth | conductor, before the first training; a step without GPU | only the pattern of `GtGenerator`: one class, one command per method (`generate`, `have`, `check`, `view`, `selftest`), a store named by the signature (hash of generator code and options) with an `index.json`; a second run writes only what is missing | the generator (raw shard -> truth shard), its known-answer test, how truth is drawn | `data/.../gt/<signature>/<shard>` + `index.json` |
| training | conductor; `Training check`, then `Training run` -> `run.py` (card, snapshot, record) | `trainkit.fit` (schedule, clipping, EMA, checkpoints, resume, stop request); `Training` composes the config from presets | `net/` (prep, model, loss), `training/train.py` (config fields, step function), presets `smoke` and `small`, the `training` block of `project.json` | `runs/<run>/`: `log.jsonl`, checkpoints, `config.json`, `.done` only for exit 0 |
| debugging | conductor, cheap first: (1) known-answer tests of data, truth and metric; (2) preset `smoke` through the whole chain; (3) over-fit one shard; (4) `Training health / watch --enforce / plot / compare`; (5) probes and taps; (6) the worst frames of the evaluation as pictures | `Training` health, kill rules, curves; the hooks of `trainkit`; `Evaluation` taps, probing, `find_worst`, `qual debug` | which probes, which taps, the smoke preset | text and json, a curve picture, `kill.txt`, debug pictures |
| running | a step after training | the pieces in `Evaluation` (`runner.py`: call order, `results.py`: the stored set); the Runner itself exists only in `bev_fusion/runner/` (236 lines) | `runner/`: checkpoint + frames -> predictions, named in `evaluation/evaluation.json` | `<run>/eval/results/<id>/frames/*.npz` + `manifest.json` |
| evaluation: numbers | a step; then `decide.py` on the controller | `Evaluation`: `run`, `score`, `compare`, `make_card`; a metric returns additive counts per frame, the engine sums them; `stats.py` is the one paired scene bootstrap; outlier search | `evaluation/adapter.py`: Source (scenes, frames, load), Subject (predict), Task (metrics); `describe()` with the truth signature and the evaluator hash | the metric card (`schemas/card.schema.json`) with the paired block |
| evaluation: pictures | the same step, or on demand | `qual frame / random / videos`, the render code, the video writer | views: a page of panels per frame (input, truth, prediction, error) | png, an html index, mp4 in the run's store |
| evaluation: compute time | the same step; timing only on a quiet machine | `Evaluation.time` and `get_cost`: `cost.py`, `count_ops` (operations per module), `quant timing`, `quant pareto` | `Subject.ops()` and `benchmark()`, where the timed path starts and ends | `timing.json`: ms per frame (median, p90), parameters, operations; the protocol with it |
| verdict and records | controller, at the close | `experiment.py check`, `decide.py`, `ledger.py`, `commit_paths.py` | the card, score and guards in `project.json` | verdict in the ledger, the result block, one commit |
| reporting | conductor, after the verdict; a fresh reviewer before it goes out | `reporter` (`new / build / check / pack`: values filled from result files, a number check, refuses a report without a drawing), `archdraw.py`, `run_report.py` (one page per run), `plots.py` | `report.json` and its text parts; `training/architecture.json` | html with: question and verdict, the drawing, the numbers with control and interval, pictures, **two cost tables**: inference (ms per frame, parameters, operations) and the experiment (hours per arm from the run records, steps per second, share of waiting for data, against the card's budget) |

One front door: a problem names its commands in `project.json` (today the `training` block with `check`, `train`, `prepare` and `package.split_record` already work this way). P0 adds the rest in the same form (`gt`, `predict`, `evaluate`, `report`), so a card's arm lists only settings and the default steps of the problem run: truth check, train, predict, evaluate.

## 4. General, data set, problem
| layer | holds | test of belonging |
|---|---|---|
| general (`autoresearch/`) | launching and records, judge, gates; the training engine; watching a run; evaluation engine, statistics, rendering, cost; the report builder | it needs only the contract files below and runs the toy without a change |
| data set service (`GtGenerator/`, `data/NuScenes/`) | what one data set is and what its truth is; shared by the problems on that data set | it knows the data set, not the network |
| problem | what the data mean and what "right" means: targets, model, loss, decoding, metric, views, score and guards, the story of the report | everything else |

The contract files are the whole interface between the layers; a new problem writes the same files and no general code changes:

| file | written by | read by |
|---|---|---|
| shard manifest (`data/manifest.json`: shards with size and hash; the root comes from one setting) | the data tools | training, running, evaluation; later the split over ranks |
| truth store index (`index.json` with the signature) | the generator | training, evaluation |
| run folder (`log.jsonl`, checkpoints, `.done`, stop files) | the trainer through `trainkit` | `Training`, `run.py` |
| stored predictions (`manifest.json`, one file per frame) | the Runner | evaluation |
| metric card, `timing.json`, the picture index | the evaluation | `decide.py`, the report builder |
| `run.json`, the experiment card | `run.py`, the conductor | judge, ledger, report |

Today the general packages still know their first users. The 20 places found (the list goes into the toy's README as the start of the friction list), the ones the toy will hit first:
- `tools/provenance.py` names `data/autogt`, the nuScenes manifest and the `gcar` interpreter; `autoresearch/config.json` names the lane problem as default.
- `Training`: the progress prefix and the health thresholds follow the BEV trainer (`runs.py`, `health.py`); the prepare check means "GtGenerator have" (`api.py`); `compose.py` resolves splits the BEV way.
- GPU gates read `nvidia-smi` and count "unreadable" as "not free" (`run.py`, `Training/cli.py`, `Evaluation/quantitative.py`).
- `Evaluation/comparison/boxes.py` holds a nuScenes metric in the shared core.

Built more than once (not touched in P0; the toy shows which copy is the general one): timing three times (`Evaluation/cost.py`, `bev_timing.py`, the lane's `jtiming.py`), the operation count twice, the quiet-GPU gate twice, html report builders three times (`reporter`, the BEV `build_report.py`, the lane weekly builders), number checks twice, the truth store twice inside `GtGenerator`. The lane problem has no trainkit trainer, no Runner and no `evaluation.json`, so the `Evaluation` class cannot run on it.

## 5. Extensibility
| to add | what one writes | general code changes |
|---|---|---|
| a problem | a folder in the layout of section 6 and its `project.json` | none |
| a data set | a manifest and a generator with the store contract | none |
| a metric, a view, a probe | one class or function in the problem's `evaluation/` or `training/` | none |
| a report | `report.json` and its parts | none |
| more ranks | `resources` of the arm; the split of the shards is computed | none after P0.6 |
| another machine or a scheduler | a site entry: how to reach it, its data root, its rank launcher | the executor (step S5) |
| a new ability of the engine | a hook of `trainkit` | only when no hook fits |

Rules that keep it so: the layers talk through files and command templates only; no general file asks which problem it serves (a setting or an adapter object carries the difference); a second copy is allowed, the shared part is extracted when the third user appears and the toy counts as a user.

Three guards, as tests (P0.7): the toy end to end inside the selftest; no module of `autoresearch/` imports a problem or `GtGenerator` at load; the general packages name no data set, with today's places as a named list that may only shrink (the way `net/tests/test_net_layering.py` holds its exceptions).

## 6. Folder layout
```
autoresearch/
  METHOD.md  README.md
  tools/           controller: launch, records, judge, gates, git, clean-up
  trainkit/        training engine (with P0.6: ranks and shards)
  Training/        watch and judge a run from its files
  Evaluation/      numbers, pictures, cost for any network; adapters/minimal.py is the template
  examples/toy/    the reference problem: chain test and template
  agents/  templates/  schemas/  history/
reporter/          the general report builder (top level today; it belongs to the system, not moved in P0)
GtGenerator/  data/NuScenes/      data set services
<problem>/         bev_fusion, bev_fusion_lane_center
```
A problem, one folder per activity, the same names everywhere (the toy uses exactly this):
```
<problem>/
  README.md  project.json        (a real problem also: PROBLEM.md DESIGN.md HANDOVER.md CLAUDE.md)
  data/         manifest.json, splits.json; the heavy store is a setting or a link, never in git
  gt/           the truth this problem makes itself (a problem on nuScenes names GtGenerator instead)
  net/          prep/  model/  loss/
  training/     train.py, configs/, presets/ (smoke, small), probes, architecture.json
  runner/       checkpoint + frames -> predictions
  evaluation/   adapter.py (metrics, views, timing), evaluation.json
  reports/      report.json + parts per report
  experiments/  <id>_<slug>/: experiment.md, runs/, own code
  tests/        known answers; the smoke through the chain
  runs/         heavy outputs, not in git
  temp/
```
The two real problems keep their folders; nothing is renamed. Where they differ today: process records (`experiment_execution/` in the lane, `records/` and `plan/` in BEV), report builders (`reports/build/`, `results/build/`), tests (`tools/maintenance/`, `tests/`), splits (inside `net/prep/frames.py`, `splits/`), the Runner (none, `runner/`). New folders of a real problem follow the layout above.

## 7. Build order
| step | what is built | existing code touched | done when |
|---|---|---|---|
| P0.1 data and truth | raw scenes from a seed as shards with a manifest; the truth generator with its store; known-answer tests | none | a hand-made scene gives the expected mask; a second run writes nothing; a changed generator gives a new signature |
| P0.2 training | `net/`, `training/train.py` on `trainkit`, presets; started with `Training run` through `run.py` | none | a run folder with log, checkpoints and done flag; `Training status / health / plot` read it; stop and resume equal the uninterrupted run |
| P0.3 running and evaluation | the Runner, the adapter (numbers with the paired block, views, timing) | none | `Evaluation run` writes the card; the metric passes its known answers; pictures and `timing.json` exist |
| P0.4 one experiment | a card with two arms and two seeds through `run.py`, `decide.py`, the ledger, one commit | only what the toy proves necessary, each with a test | the tool gives the verdict; the friction list is written |
| P0.5 report | the experiment's report with `reporter` | none | `reporter build --strict` and `check` pass; both cost tables are filled from files |
| P0.6 ranks and shards | `trainkit` learns its rank (a small helper: rank, number of ranks, wrap the model, split the shards, write as rank 0 only); the toy trains with two ranks under `torchrun` on the CPU | `trainkit` (shared: a critic pass; one rank stays bit for bit, the BEV equivalence test stays green) | the split is disjoint, complete and the same on a repeat; stop and resume work with two ranks; the judge sees an ordinary run; the run record holds ranks and manifest hash |
| P0.7 guards | the three tests of section 5 | the selftest | green |

Sizes, estimated: the toy about 650 lines with tests; the rank helper about 250 with tests. Checked on this PC: `torchrun` is installed, torch 2.8 offers the `gloo` (CPU) and `nccl` backends, one GPU, 12 CPU threads. P0.1 - P0.5 can run beside trainings (CPU, seconds); P0.6 changes shared code and waits for a moment when no training uses `trainkit`.
