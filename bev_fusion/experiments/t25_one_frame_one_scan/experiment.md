## 1 Card
- **Question.** The network gets ONE camera frame and ONE radar sweep per step and carries its past only as feature state. Does that keep the quality of the t21 pair-P4 design with 0.5 s of accumulated radar, at the same training budget, and which part (the recursive camera, the single sweep, the radar memory) costs or gives what?
- **What exists, and what is not isolated.** Camera: `cam_buffer recurrent` (t21 arm R). R against P4 on the stored cards (`runs/t21_rec_s0b/eval/card.json` against `runs/t21_pair4_s0/eval/card.json`, VAL 1000): `detf` mean mAP 0.4101 against 0.4154 (-0.0053), `det` mean mAP 0.3405 against 0.3453 (-0.0048), centre-field velocity EPE 1.1364 against 1.0911 (+0.045); against the window control R lost on `det` mean mAP -0.0060 [-0.0115, -0.0002], drivable IoU@0 -0.0037, vehicle seg IoU@0 -0.0059, road_divider IoU@1 -0.0126, vehicle `ave_skill_moving` -0.0113, pedestrian AP@1 -0.0114 (`experiments/t21_one_frame_temporal/compare_rec_vs_ctl.txt`). The t21 summary says the velocity loss is "consistent with" the halved time baseline of the motion block, not isolated; the fix list of the t21 card (move the fused state with the motion field, longer clips, sharper kernel) was never tried. Radar: the 0.5 s accumulation at point level; the radar memory (`window_memory` + static gate) was probed once on the small set (t16, `training/configs/t16_full.json` `_about`) and learned nothing there because it had no past radar frame; the t19 draft (tag `archive/cards-before-delete-2026-11-04`) expected a TIE and "low prior": the heads answer to radar only weakly (maps 17 %, objects 9 % change without detections).
- **Hypotheses.** (H1) The camera part (R) costs about what t21 measured (-0.005 `detf` mAP, +0.05 velocity EPE) and no more on this GT; that is the share of the margin the camera already uses. (H2) One sweep alone (A1) loses detection where the radar matters: pedestrians and objects with few points (29 % / 64 % have a point); the camera carries the rest. (H3) The radar memory (A2) recovers part of it, but the static gate keeps movers out of the memory (the Doppler of a crossing mover vanishes, `tests/test_radar_memory_ghost.py`), so exactly the classes that lose under one sweep, pedestrians and moving vehicles, are carried only by the one-step past path through a velocity head that has never had a gradient: a TIE between A1 and A2 is a real possibility and is a valid result (then the cheaper arm A1 is the finding: the radar memory does not pay).
- **Prediction (written before the run; VAL 1000, dt 0, seed 0, DELTAS against the retrained control of the same seed on the same GT; the stored control values on GT v9 are `detf` mAP 0.4154, `det` 0.3453, lane IoU@0.5 0.4366, velocity centre EPE 1.0911 and are not the reference).** R: `detf` mAP -0.005 (-0.010 .. 0.000). A1: `detf` mAP -0.025 (-0.040 .. -0.015), pedestrian AP@1 (`detf`) -0.04 or worse. A2: `detf` mAP -0.015 (-0.030 .. -0.005), i.e. A2 - A1 about +0.010 (the A2 claim is smaller than the A1 loss because the movers are gated out). Lane rows, drivable area: no move beyond the band (the camera carries them). Velocity (centre-field EPE of moving objects): the field comes from the motion block, which reads the camera BEVs and the raw radar raster of the CURRENT call (`batch["radar"]`, `rad_temporal` has no path into it): A1 and A2 equal within training noise, both about the R value plus the effect of 5.6 times fewer Doppler points (unknown, not predicted). The JSON `prediction.value` -0.005 is R's, the pass line for the camera part; the A2 and A1 predictions above are in the decision table.
- **Go / no-go before any GPU hour (CPU, 246 VAL frames, as the t24 read-out).** The stored P4 checkpoint scored with the current code (a) as is, (b) with the radar zeroed, (c) with the newest sweep only at inference (no training). (b) bounds the dynamic range: if zero radar costs less than 0.02 `detf` mAP, the A1 prediction (-0.025) is impossible and the question is smaller than assumed (then the card is rewritten around the camera part). (c) is the cost of one sweep before any adaptation.
- **Design.** Four arms, one training at a time, the same schedule and the same GT: warm start `runs/t20_base_s0` (EMA, made on GT v9), 1500 steps, batch 2 x accumulation 3 (the recursive arm peaked at 8.2 GB at batch 2; batch 3 was estimated at 12.7 GB, over the 11 GB kill line; the control uses the same batch so that arms are matched), `n_cam 3` / `cam_stride 2` in the recursive arms and `n_cam 2` / `cam_stride 4` in the pair control (a pair batch takes two frames: the previous frame is 1/3 s back, as t21 P4; the recursive arms are the t21 R recipe), GT v13 / l6 (signature `a107e0b4e8`). The v13 GT cache of the trainer (`data/cache/gt`) was built on 2026-11-14: 32,449 files (val 5,719 + train 26,730), 71 minutes at 0.25 s per sample, not hours; the live front signature (`python -m GtGenerator key bev_fusion`) is a107e0b4e8 @ 39f45900, the cache's. **Named deviation, found on 2026-11-14:** `python -m Training check` refuses every arm ("the GtGenerator that would be imported differs from v9 (6a7aa7864a) ... pin v9") because the warm-start run's `gt.json` is v9, and the Training class has no way to pass `--expect-gt` (it is an option of `training/startable.py` only; there the tag lookup `autogt/v13` finds no tag, so the identity check is vacuous). The v9 base is fine-tuned on v13 labels in every arm (matched; a larger adaptation than in t21). Radar window: the radar encoder of the warm start saw 0.5 s of points; with one sweep it sees 5.6 times fewer: the first 200 steps are expected to lose; the schedule is not lengthened. Order by code readiness: ctl, R, A1 (no new code beyond configs), then A2.

## 2 Detail plan (the coding step; for `ar-coder`, then a critic pass)
1. **Dataset** (`training/nuscenes_dataset.py`): option `radar_per_frame` (default False; the default path stays bit-identical; the window is the dataset's `radar_window`, set to 0.09 s in the one-sweep configs and carried by `TrainConfig.radar_window`, default 0.5): `item["radar_seq"]`, one radar dict per camera frame of the window (index 0 = current), each with the newest sweep of each of the five radars not after THAT frame's camera time, moved into the ego frame of that frame (`_radar` with that frame's camera sample_data); `collate` stacks them with the batch index; `batch["radar"]` stays the current frame's. Hard test: `radar_seq[0]` equals the `radar_window=0.09` radar of the same sample; the mean number of points INSIDE the grid (x 0..60 m, |y| < 26 m) per keyframe on mini lies in 40..70 (the study measured 54; the item holds all five radars' points without a grid mask).
2. **Model** (`training/model.py`): with `cam_buffer recurrent`, `rad_temporal window_memory` + `rad_static_gate` and `radar_seq` in the batch, the shared recurrent loop (`_moves` + `_recur`, which replace the old `_unroll`) runs the radar branch per frame next to the camera branch: encode the frame's sweep (radar block), step the radar temporal block with past = [(previous fused radar BEV, ego chain)] like the camera, state `state["rad"]`, buffer `buf["rad_fused"]`, write mask of the memory per frame (`radar_hits` / `radar_static` of that frame's sweep). **Zero-start residual:** the radar features that go to the fusion are the encoder's features + `rad_mix`(block output), `rad_mix` a zero-initialised 1x1 conv (a scalar gate would stay almost closed: Adam moves a parameter by about the learning rate per step), so the A2 network at step 0 equals A1 bit for bit (test). At step 0 the block itself gets no gradient; `rad_mix` does, and the block follows from step 1 (the critic measured block gradients about 1e-5 from step 1 on a tiny model; whether it opens enough in 1500 steps is what the arm shows). `forward` fuses the newest frame's camera and radar outputs as today; the radar side loss reads the newest frame only. `advance` (stream) takes the same path, so a stream of one frame + one sweep per step works. All existing configs: identical outputs. `check_config` refuses `radar_per_frame` without `cam_buffer recurrent` and a radar recursion without `radar_seq`.
3. **Plumbing of the new batch key** (each a place where a key not listed is dropped, left on the CPU or not mirrored): `train.py` `to_device` (moves only the "radar" dict today), `collate_clips`, `augment.py` `flip_batch` (mirror `radar_seq` too; test with `flip_aug`), `interface.py` (INPUTS), the per-frame Precompute radar maps, `TrainConfig` / `make_datasets` (`radar_per_frame`, `radar_sweep_age`/window; the evaluation adapter builds datasets through `make_datasets`, `stream_drift.py` hard-codes `n_cam=3, cam_stride=2`: reported, not edited here), the radar cache key.
4. **Tests** (`tests/`): (a) stream = batch: 6 frames with their sweeps through the batch path and through one-frame stream steps give the same output and state; (b) gradient reaches the radar block, the radar memory's velocity head and write gate in A2; (c) step-0 identity: A2 output = A1 output; (d) the default path unchanged (existing tests green); (e) `check_config` refusals; (f) a flipped batch mirrors `radar_seq`; (g) the four configs pinned (`name`, `_about` and the listed keys only).
5. **Configs** `t25_ctl.json`, `t25_rec_r.json`, `t25_rec_scan.json`, `t25_rec_scan_mem.json`, derived from `t21_pair4.json`.
