**What a green suite does not prove.** It proves that the code does what its tests say, on the fixtures and the real frames they use; it does not prove a number. Every number in this report comes from a stored card (`check_numbers.py` lists any decimal number of the text that no source holds), and the numbers of the champion were reproduced by the same read-out on two seeds.

**Known failures, named.** One check is red: the selftest of the autoresearch tools (launcher, git tag, ledger, schedule, decide; `autoresearch/tools/selftest.py`, line 211) fails its assertion "the command's pid and process group are in the record right after it started". It failed in the full run and failed again when the lane chat re-ran it alone on the final tree (2026-11-18 13:21 - 13:41). It is not a load flake and not a wrong record: the test polls for 10 seconds for the record of a started command, but a launch takes 23 - 29 s on this host (three measurements: 29.0 / 26.1 / 26.1 s real, 1.3 s user, 4.4 s sys; a profile puts about 21 of 26 s into `hash_code` -> `code_files`, a directory walk over about 23,600 directories of the code tree on the Windows drive, called twice per launch). A diagnostic run shows the pid and the process group in the record after 23.6 s, so the record is correct. It is not fixed today; follow-up (chapter 13): raise the window of the test to 60 s and prune the walk (`temp/`, `_to_delete/`). The test is not part of the lane code. The script's own exit code in the log reads 0 although a FAIL line stands in it (the last line of the script decides it): the log, not that code, is the result.
