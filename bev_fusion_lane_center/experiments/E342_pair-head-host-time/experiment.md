## 1. Part A (CPU, measured 2026-11-14 16:10, installed by commit 27fee60b at 21:48 after two critic passes of the patch): `jgt._groups` vectorised
`rank_matrix` (`JEnds.forward`, order rule on) copies the keypoints to the host (a full GPU sync), groups the valid ends of each kind by single linkage (`jgt._groups`: heading within 25 degrees, 6 m along / across) and ranks them inside a group (`jgt._ranks`), then moves five small tensors back; named hard bookkeeping, no gradient (D82). On the 3 300 (frame, kind) sets of the E312 seed 0 and 1 VAL dumps (`runs/e312_p_s<S>/ends_val.pkl`, 13.0 valid ends per set on average, at most 32): **the python loop 0.80 ms per set, the vectorised version 0.095 ms (8.4 times faster)**, groups plus ranks 1.09 ms against 0.37 ms per set (ranks alone 0.30 ms). **Labels (the critic's run on the installed text):** 0 mismatches on 3 322 non-empty real sets of the E312 VAL dumps (3 300 with n >= 2 and 22 with n = 1; the dump holds 3 492 sets, 170 with n = 0), `JEnds.rank_matrix` bitwise equal on 1 746 frames, 0 mismatches on 20 000 random clustered float32 sets and on 3 304 real float64 GT sets of the loader path, and on an adversarial suite (exact-boundary grids, degenerate rows, chains and shuffled paths up to 32 ends, f32 and f64). **Limit of 'bit for bit':** in float64 the labels are identical on every tested input, but the arithmetic is not bit-identical at inputs that sit exactly on a threshold (OpenBLAS ddot uses FMA: 1 ulp differences in the dot product and the norm; on 40 000 constructed pairs at exactly 25.0 degrees +-3 ulp, 498 / 529 differ in the angle test; real data sits there with a probability of about 1e-15); the old float64 result is itself CPU- and BLAS-dependent at that knife edge. The selftest in `jgt.py` compares with the loop kept as the oracle and pins the edge semantics (boundary `<=`, a zero heading, float32 headings with self-dot above 1, a shuffled path of 32 ends): it is an equivalence test, so it passes with the old code too. **Speed by set size** (the critic's loaded box, old -> new per set): 2 ends 15 -> 53 microseconds (slower), 3 ends 56 -> 79, 4 ends 89 -> 61, 13 ends 1 488 -> 88, 32 ends 10 700 -> 141; groups 1.17 -> 0.105 ms, groups plus ranks 1.91 -> 0.63 ms, one `rank_matrix` call 5.5 -> 2.6 ms per frame. Per frame (both kinds): about 2.2 ms before, 0.75 ms after = **-1.4 ms of the 17.09 ms** (8 %); a bigger gain than any single MAC saving of the maps head. The loader calls the same function for every GT frame: a little less host time in training, nothing in the numbers.
**Prediction (a number):** -1.4 ms per frame on the CPU part of the forward (the measured time of `rank_matrix`'s groups); on the idle GPU the same, because the work is the host's. Code: `training/grid/jgt.py` (`_groups`, selftest), README row; no other file (committed 27fee60b).
**Mixed versions (stated, as the critic asked):** the E317.g_s1 training and the evaluation jobs that were running at 21:48 keep the old code in memory; later chain stages (post_pair, E318.u, E319, the reads) and every run that starts after 21:48 use the new one; the outputs are identical (above), and each run's `lcr/<id>` tag shows the code version it started from. ## 4. Finding (2026-11-14 23:50, from the lane lead's question why the GPU is idle): the training step is limited by the loader's CPU work, and the number of workers does not change the batches
- **Observation (lane lead, 23:31):** GPU utilisation about 15 % over 12 s (0 % with peaks to 100 %, 30 - 58 W); the two E334 trainings' main processes sit at 13 - 17 % CPU, the six data workers (3 per job, `--workers 3` default of `jends_train.py`) at about 95 % each; 12 cores, about 44 % idle; E318 / E345 wait for the two run.py slots. The step (about 2 s) is bound by the host: the loader's per-frame work and the pair head's host bookkeeping (part A), not by the GPU.
- **Test (`temp/loader/loader_identity.py`, CPU, `wsl bash tools/env/_py14.sh temp/loader/loader_identity.py --nb 20 --seed 0`, result `temp/loader/identity_0.txt`):** the first 20 batches of `LD.loader("train", bs=8, shuffle=True, map_mode="train", pixels=False)` with the flags of `jends_train.py` (junction, pscale, ppts) after `trainer.seed_all(0)`, run with workers 3 twice, 6, 0 and (D101) 4 (every field compared, NaN padding equal to NaN). **Every field that the pair stage reads is bit-identical in all four runs, and so is the sample order:** `x`, `ent`, `ext`, `ent_m`, `ext_m`, `pairs`, `pdrv`, `pscale`, `ppts`, `jz`, `jheat`, `jdir`, `jpaint` (a grep of `jends_train.py`, `jends.py`, `jmaps.py` shows that these are all the batch keys it reads), and also the B-target fields (`exists`, `flags`, `offset`, `dirv`, `lk`, `lk_long`, `lk_scale`, ...). **The only fields that differ are the simulated map** (`map_*`, `kmask`, `piece_map`, `piece_road`, `tmask`, `map_ids`, `map_roads`), and they differ even between two runs with 3 workers: `make_map(..., rng=np.random.RandomState())` in `map_mode="train"` is UNSEEDED (OS entropy; the 5 % map errors of the training), so they are not reproducible with ANY worker count. **Which stages read them:** B's training and its gates (`training/grid/qassign.py`, `qgraph.py`, `training/train/qgates.py`, `evaluation/qgraph_timing.py` (removed on 2026-11-21, git history): the assignment head and the map pieces), so every B training arm carries this non-reproducibility regardless of workers or seeds; the pair stage and the maps stage (`jends_train.py`, `jmaps_train.py`) read none of them. The number of workers therefore changes no number of any pair-stage or maps-stage run (the maps trainer uses the same loader class with `pixels=a.joint`, the same sample order and the same deterministic fields).
- **Workers 4 (the number the owner chose, D101):** against workers 3 every field the stage reads is bit-identical, only the simulated-map fields differ (the same set as the repeat with 3 workers; `temp/loader/identity_w4.txt`). **Speed under the load of the box (two trainings running):** per batch of 8 about 2.4 - 2.5 s with 3 workers, 1.8 s with 4, 1.4 - 1.8 s with 6, 4.8 - 5.5 s with 0 workers: the loader is the step. **Consequence (D101):** `--workers` is not a recipe parameter; every NEW chain stage and run start uses `--workers 4` (a single job and two jobs alike, never 6); the not yet running start scripts of E319 (`temp/e319/start_maps.sh`, `start_pairs.sh`) were changed from 3 to 4 (the chain scripts and `temp/e330/recipe.sh` that are running or sourced are not touched; arms of a card whose control ran with 3 workers are not disturbed by this: the inputs are bit-identical).
- **What the loader computes that the pair stage never reads:** each item builds B's targets (`QT.node_table`, `grid_targets`, `link_array`, `fit_long_scales`) and the simulated map with its piece targets (`MS.make_map`, `piece_targets`, `road_targets`) next to the junction GT, the pair scales (a grid search, about 0.15 s per frame) and the connector polylines. The real fix (derived-data cache and a pair-only item path, bit-identical in every field the stage reads) is the card E349.
