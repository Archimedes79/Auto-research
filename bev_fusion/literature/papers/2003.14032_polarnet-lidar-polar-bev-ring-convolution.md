# 2003.14032 PolarNet: polar BEV grid with ring convolution (lidar segmentation)

| | |
|---|---|

| groups | A1 radar decoder: 2 (polar-domain CNN with a map back to the points; ablation against Cartesian BEV and spherical projection) |
| code / licence | https://github.com/edwardzhou130/PolarSeg, BSD-3-Clause (LICENSE file on the repo page, checked); PyTorch, needs torch-scatter |

**What it does** [checked]: Points are binned by (azimuth, radius) from the sensor with the full z column per cell; a simplified PointNet (FC-BN-ReLU, max pool) gives the cell feature; the cell grid is treated as a ring (leftmost and rightmost columns connected, "ring convolution" = circular padding in azimuth) and processed by an ordinary 2D segmentation network; the polar prediction is read back to every point by its cell index (a gather, no interpolation).

**Results that matter** [checked, SemanticKITTI val mIoU, 256 x 256 x 32 grid, Table 3]: spherical / Cartesian BEV / polar BEV: SqueezeSeg 31.8 / 42.6 / 42.2; ResNet-FCN 41.6 / 49.2 / 52.5; DRN-DL 43.4 / 46.7 / 51.2; ResNet-DL 41.6 / 50.4 / 53.6. Polar wins on three of four backbones (+3.3 to +4.5 mIoU), loses 0.4 on the weakest. Test: PolarNet 54.3 mIoU, latency 0.062 s (GPU not named), 14 M parameters; U-Net on Cartesian BEV 50.7.

**Transferable technique**: the pro-polar argument is point density per cell, which is exactly the radar case (azimuth error constant in bins). The ring padding is irrelevant for a 130 deg field of view. A point-to-cell gather by index (no interpolation) is the "hard" read-back; our fixed table does better.

**Cost and fit**: all plain PyTorch; fine for the polar image of one radar.

**Doubts**: lidar density, not sparse radar; the ablation is one grid size; mIoU on segmentation (no object extents), PolarStream shows the opposite sign for detection.
