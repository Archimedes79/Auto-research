# 2305.14018 Sparse4D v2 - recurrent propagation of instances: only the anchor is moved, the feature is copied

**What it does**: each instance has an anchor (3D box + velocity), an anchor embedding and an instance feature. To go from t-1 to t only the anchor is projected: A_t = Project(A_{t-1}), the embedding is recomputed from the new anchor E_t = anchor-encoder(A_t) and the feature is copied unchanged, F_t = F_{t-1}. For a box the position is advanced by velocity x dt and then rotated and translated by the ego motion; size is copied, yaw and velocity are rotated. High-confidence instances are carried on (600 temporal + 300 single-frame anchors of 900).

**Results that matter** (RTX 3090, R50, 704 x 256, from Table 1 as returned): Sparse4D v1 (multi-frame sampling of T frames) FPS 21.5 / 12.6 / 9.0 / 6.1 and memory 424 / 614 / 792 / 1149 MB for T = 1 / 3 / 5 / 9; v2 (recurrent) 19.4 FPS and 432 MB for every T. Temporal vs no temporal fusion: NDS 0.414 to 0.539, mAP 0.341 to 0.439 (Table 3, Exp. 1 vs 5). NO matched NDS comparison of recurrent against window sampling is given.

**Transferable technique**: the recurrent state is a list of originals with a pose and velocity; each step multiplies a transform onto the coordinates only. This is the instance-level analogue of our `chain_positions`; the cost is O(1) in history length where the window costs O(T). It also answers how to keep moving content sharp in a recurrent scheme: do not store it as a rasterised feature map.

**Cost and fit**: needs a sparse-query detector. For a dense map the transferable part is the update rule, not the network.

**Doubts**: velocity is predicted per instance and its error grows the anchor error over many steps (not studied on the page read); no recurrent-vs-window accuracy at equal frames.
