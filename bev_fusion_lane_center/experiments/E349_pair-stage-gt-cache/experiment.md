## 1. What the profile says (corrected) and what the stage reads
- **Measured (2026-11-14 23:45, `temp/loader/profile_items.py`, 24 items, one process, cProfile, workers 0, CPU):** 0.97 s per item (0.75 - 0.84 s unprofiled, load dependent: the ratio is what matters). By callee, per item: `fit_pair_scales` 0.39 s (the grid search of the fitted handle scales, `qjunction.py:36`), `junction_gt` 0.33 s, **`fit_long_scales` 0.15 s (B's long-link scales; the pair stage never reads it)**, `node_table` 0.03 s and the remaining B targets, the lane GT load 0.02 s, `end_table` 0.015 s. The 0.29 s of shapely `buffer` inside `junction_gt` is `z["shp"].buffer(8.0).contains(Point)` at `jgt.py:184`, evaluated for every (arm, zone) pair (the critic: it is NOT the growing of the connectors into the zone and core); hoisting the `buffer(8.0)` once per zone is bit-identical (the critic's probe: all pair and map keys identical, 0.84 -> 0.46 s per item) and helps every uncached consumer (the evaluation dumps, B). It is landed as its own small commit with an equality test (E349a) and does not replace the cache (`fit_pair_scales` and the B-only parts remain). The 4-worker batch of 1.83 s is the step (the training step of about 2 s; `experiments/E342_pair-head-host-time/experiment.md` section 4: batches are bit-identical for every worker count).
- **What the stage reads (grep of `jends_train.py`, `jends.py`, `jmaps.py`, `qendnet.py`, the critic's list):** always `x`, `ent`, `ext`, `ent_m`, `ext_m`, `pairs` (`jends.py:311-312, 386-387`, `qendnet.py`); `pdrv` only with `driven_w > 0`; `pscale` only with `--scales`; `ppts` only with `--geom-w`; **`jz`, `jheat`, `jdir` and `jpaint` only through `jmaps_loss`, i.e. with `--e2e` (all recent arms) and in `jmaps_train.py`**. It does NOT read B's targets (`exists`, `flags`, `offset`, `dirv`, `sstart`, `piece`, `uout`, `uin`, `tier`, `vis`, `ztier`, `lk`, `lk_long`, `lk_scale`) nor the simulated map (`map_*`, `kmask`, `piece_map`, `piece_road`, `tmask`: unseeded, E342 section 4). `jmaps_train.py --joint` (`pixels=True`) needs the pixel targets (`g05`, `events1`, `lines_*`, `road2`): the pair-only path REFUSES it (an assert), as it refuses `zone`, `sparse` and `pixels=True`, never silently dropping a field.
- **Why the maps are not cached (the blocker of the first version):** `jgt.fields` reads `BFLC_SIG` (the heat sigma: every pair-stage chain exports 1.0, E314 used 0.7, the loader default is 1.5) and `jgt.fill_poly` reads `BFLC_RASTER` (`jends_train.py --raster exact`); the critic's probe on 12 TRAIN frames: `BFLC_SIG=1.0` changes `jheat` and `jdir` in 12 / 12 frames, `BFLC_RASTER=exact` changes `jz` and `jpaint` in 12 / 12 frames. A map cache built under one environment would be silently wrong for every arm run under another, and no build-time check can see it. **So the cache holds only what does not depend on the environment**: per frame the junction GT object `jg` (zones and cores as shapely polygons, arms, pairs: pickled), `ent`, `ext`, `pairs`, `pdrv`, `pscale`, `ppts` (the dtypes and the empty cases of the uncached item, e.g. `ppts` (0, 16, 2): `collate` reads `b[0]["ppts"].shape[1]`), and the maps are rasterised at load by the UNCHANGED `jgt.fields` / `qjunction` fill with the paint sidecar re-read (about 5 ms per frame by the profile). The cache is then tens of MB, not 6 GB: it stays in the project's `data/pair_cache/<GT signature>/` (fast local files, not in git; no D: placement and no link needed; D40: only `package.py` may delete it; the recipe is the builder in git).

## 2. Design
- **Builder** `training/data/prep/pair_cache.py` (promoted code: a test, a README row; the model is `junction_paint.py`): for every frame of `train` (and `val_clean` for tests only; the choices are exactly these two) it calls the SAME functions as `QData.__getitem__` for the cached part (`QEND.end_table`, the junction GT of `QJ.junction_targets`' first half, `QJ.fit_pair_scales`, `QJ.pair_polylines`) and writes one file per frame atomically; one `manifest.json` (the GT signature of `lane_gt.signature()`, the sha256 of the source files of the producing functions `qjunction.py`, `jgt.py`, `qends.py`, the numpy / shapely versions, the field list with dtypes). Four workers, `nice -n 10`, resumable (an existing file is kept after a load check), at most the RAM the box has free (the build is about 26 minutes for 8 414 frames at 0.75 s per item on 4 workers, and the two running trainings slow down meanwhile: stated). A manifest that differs is refused (rebuild into another folder).
- **Loader** `QData(..., cache=dir)` and `loader(..., cache=dir)` (`cache` is an argument ONLY, never a `DEFAULT_*` class attribute: `jends_eval`, `jmaps_eval`, `jwiring`, `jheat_replay`, `jprune_probe`, `qgraph_timing`, `qgates` build their own `QData` or call `LD.collate` and stay uncached and unchanged): default `None` = every running and every stored command line bit for bit; with a cache the item reads `x` (as now) and the cached geometry, rasterises the maps with the current environment, skips `node_table`, `grid_targets`, `link_array`, `fit_long_scales`, `make_map`, `piece_targets`, and `collate` stays the unchanged function (it pads the per-frame arrays; the pair-only item carries the keys of the stage, `collate`'s B-field loop is guarded for the keys that are absent). The loader REFUSES a cache whose manifest signature or code hashes differ from the current ones and never falls back silently; a `revalidate` mode re-checks a sample and re-stamps the code hashes after an edit that does not change the geometry code.
- **Trainers:** `jends_train.py` and `jmaps_train.py` get `--cache DIR` (opt-in; the chain scripts pass it; no flipped default: a default-on cache would make a new chain stage fail at start after any edit of a hashed file).
- **Controls (written before the build):** (1) ITEM IDENTITY: the reference is the uncached `QData.__getitem__` itself (not the builder's own function): ALL 8 414 TRAIN frames (a second pass of about 26 minutes), key SETS, dtypes, shapes and values compared with `np.array_equal` (NaN equal to NaN), for the pscale x ppts combinations the chains use, under both environments (BFLC_SIG 1.0 and 1.5 x BFLC_RASTER legacy and exact: a cache built once must give the uncached item under every one), plus a synthetic frame for the branches no sampled frame hits (`jg` is None, no pairs, `npair != len(jg["pairs"])`: 2 % of the frames have no junction, none of 150 sampled hit the mismatch branch); (2) BATCH IDENTITY: the first 50 collated batches for seeds 0 and 1, cached against uncached, every key the stage reads, key sets and padding included, a batch built from the rare frames; (3) LOSS: a CPU, single-thread forward and loss on 20 identical batches with fixed weights, cached against uncached, bit-equal (no GPU slot; the identical-batch result makes any GPU run redundant for the inputs; a GPU run is not part of this card: the logged loss of a 200-step run is not observable per step (`log_every=100`) and GPU runs differ from each other by more than 1e-4); (4) REFUSALS and MUTANTS: another signature, a changed code hash, a truncated file, a missing frame, `--joint` / zone / sparse / `pixels=True`; a hand-corrupted cache file must be caught by the verifier; the default-off items must equal HEAD's, with the old `collate` kept as an oracle in the test (there is no test of `collate` today); (5) TIMING: steady state (the first batches and the iterator creation dropped; `loader_identity.py` counted them), median of at least 40 batches, control and variant in the same process, blocks A B B A.
- **Prediction (numbers):** per item 0.97 s -> about 0.06 s; loader per batch with 4 workers 1.83 s -> about 0.3 s (-1.5 s, hit window +-0.3); the training step about 2.0 s -> about 0.5 - 1.0 s (the main process sits at 13 - 17 % CPU and the GPU is busy about 15 % of 2 s, so the floor is probably 0.3 - 0.5 s plus the pair head's host work of E342; measured on the next arm that uses it, E348, not part of the rule).
- **Risks named:** the cache is bound to the GT signature (a GtGenerator edit changes it: a rebuild of about 26 minutes; the loader refuses the old one); the paint sidecars are re-read at load (not keyed by the signature: `make` skips existing files: a known weakness of the existing code, not made worse); B's training (unseeded simulated map) is not touched; a bug in the cached path would change every later arm: the identity checks under both environments are the guard.
- **Not claimed:** anything about a model, TEST, or B's loader; the step time (measured later); that the cache helps the dumps (E349a helps them).
