# E374 - S3: the E365 token head with a cross-attention to SD-MAP tokens (road-level polyline samples with direction and lane count, simulated map errors), against the same head without it

Card of 2026-11-17 (system clock), version 1 (a fresh critic pass follows before any build; the step 0 of section 1 was measured before this text, CPU only, nothing trained). The third stage of Mirko's design (D113): grid -> nodes -> pruning -> self-attention -> cross-attention to the past (S2, E368) -> **cross-attention to the map** -> node classification. D88 / D113 point 2: no rule step, rule-step systems are never a bar. **Mirko's correction of 2026-11-11 stands and is the first design rule: the LANE-level map of E273 carries exactly the connections a real SD map does not have (successors, predecessors, left / right / opposite, lane index), so it must not feed a head; the S3 block reads ROAD-level information only.**

**The question of S3:** does ONE cross-attention block (the tokens of the frame attend to map tokens = samples of the road centre lines every 2 m with position, direction, the number of lanes of the road and the road kind; a frame without a map attends to a learned 'none' key only) lift the E365 head, trained on corrupted maps, over the same head without it? **What is known before the card (the honest starting point):** E291 gave the junction pair head a GT-derived road-level lane-count table, trained with corrupted counts: the measurable gain with a CLEAN table was at most +0.0035 topo F1, about +0.001 of it the count; the head ignored wrong counts (harmless) and did not exploit right ones. Here the map enters at the TOKENS (every token can look at the road under it), not at the junction ends; the expectation stays small, and the step 0 below says why: **the simulated map is derived from the GT lane pieces, so even a clean read of it is an optimistic bound.**

## 1. Card text
- **Statement:** a head that can look at the road under every token decides weak and false tokens somewhat better than the same head without the map: topo F1 +0.003 (window -0.006 to +0.015) over the control on VAL, both seeds, with realistically wrong maps.
- **Mechanism:** a lane graph lies on roads; a token far from any road centre line, or at an angle to the road direction, is likelier false; the lane count and the kind (connector) say how many parallel lanes and whether a junction is there.
- **Step 0 (measured 2026-11-17 06:30, CPU, VAL 873 frames of B' seed 0, tokens as in E368 step 0; `temp/_session_scratch_d113/step0_map.py`, to be promoted into `lane_map_data.py potential`): the map of `map_sim.make_map` (every 2 m along the pieces; mean 293 tokens per frame, max 680; 14 pieces and 7.4 roads per frame), `distance` = to the nearest map sample, `aligned` = |cos| >= 0.8 between the token heading and the map tangent.** Within 3 m of a map sample and aligned (exact map / `error` map): novel weak tokens 0.945 / 0.893; duplicate weak 0.992 / 0.935; **false weak 0.666 / 0.607**; delivered true 0.996 / 0.956; **delivered false 0.849 / 0.768**; the median distance of false weak tokens is 1.74 m (exact) against 0.82 m for novel ones, with the `error` map 1.71 against 1.12 m. **Reading, with its limits:** the map separates the false tokens that lie off the road (about a third of the false weak tokens are farther than 3 m from any sample, and of the delivered false ones about 15 - 25 %); it does not separate a false token ON the road (a duplicate offset sideways, an object on the lane) from a true one. And **the map is derived from the very GT lane pieces that define 'true': an exact map is an oracle for 'near a lane', the `error` mode (a shift of 1 - 2 m) removes about a third of the margin** (novel 0.945 -> 0.893, false 0.666 -> 0.607).
- **The map tokens (new, `training/data/lane_map_data.py`; ROAD-level fields only, a leak check refuses anything else):** per map sample: position / 50 (+ its Fourier code), unit tangent, the lane count of the piece (`pfeat[:, 3]` x 4, i.e. 1 - 5), the kind (lane / connector / mixed one-hot, `pfeat[:, 0:3]`), the arclength fraction. **NOT given:** lane index, number of successors / predecessors, the open flags, the adjacency tensors (succ / pred / left / right / opposite), the piece / road ids, `part_ids`, the dropped list, anything of the GT piece of a node. The map table of a frame has a fixed key set (`pos`, `tan`, `count`, `kind`, `frac`, `valid`) asserted by the loader (the E291 kill (1)); at most 768 samples per frame (the maximum measured 680; asserted), padded and masked. Corruption: TRAIN = the `train` mode of `map_sim` drawn per sample by a generator seeded with (training seed, frame token, a per-epoch counter: reproducible), VAL = the `error` mode (fixed per frame), the controls as above. The map is a per-frame INPUT like the tokens: cache extension = none (the maps are built on the fly from the lane GT store by the loader workers, about 5 ms per frame; a test pins the equality of the built map with `map_sim.make_map`).
- **The module (`training/grid/jmap.py`, new, separate from `jtoken.py`; the same pattern as E368's `jpast.PastBlock`):** `MapBlock(d, heads)`: pre-norm, q from the token states (LayerNorm), k / v from the map tokens' own embedding (an MLP of the fields above -> d, LayerNorm), ONE learned none key per head, a bias MLP(7 -> 32 -> H) of the relative geometry between a token and a map sample (cos / sin of the angle between the token heading and the map tangent, the offset along / across the TOKEN heading / 20, the distance / 20, the lane count, the kind), padding masked, zero-initialised output projection (the block starts as the identity), 4 heads of 16; parameters about 25 k. No state, no recursion: the map is the same for every step of a scene, the block is a static prior. The hook in `jtoken.py` (the owner: Fable): `map_block=None` called after layer 2 as `map_block(x, pos, dirv, valid, maps)`; defaults bit for bit unchanged.
- **Not claimed:** anything about a REAL SD map (the map here is a GT-derived simulation: the gain is an upper bound on what a real map could give, the loss under errors a lower bound only for the simulated error types: gross errors of the real world (a wrong road, a missing road, a stale map) are covered by `gross`, `S`, `U` only), TEST (never touched), the lane-level assignment of E273 (a different job: it keeps its own map tokens), the combination S2 + S3 (a later card with the E368 / E374 results in hand).
- **Inputs:** ready: the E365 caches and head, the lane GT store, `map_sim.py`, the E371 seed twins as the noise reference. To build (the lane chat): `lane_map_data.py` (map tokens, leak check, loader on top of `lane_ptok_data`, `potential`, fixture), `jmap.py` (+ tests with mutants), `jmap_train.py` (a thin trainer on `jtoken_train`'s loop; or the `--map` flag if the owner prefers), the read-outs with the map controls in `jmap_eval.py`. To agree with Fable: the hook after layer 2, the slot plan, the id (E374 is the next free id at 06:30).
