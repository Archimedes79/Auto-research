# Research repository (workspace root; the folder name is free: no file in it depends on it)

Four folders live here: `autoresearch/`, `bev_fusion_lane_center/`, `bev_fusion/` and `datasets/NuScenes/`. One git repository holds the code and text of all four (whitelist in `.gitignore`; of `datasets/NuScenes/` only the README and `tools/`, never data); `wsl/` is not in git.

- `autoresearch/` - the general research system: method (`autoresearch/METHOD.md`), agent roles (`autoresearch/agents/`, installed into `.claude/agents/` by `autoresearch/tools/install_agents.py`), templates, prompts and tools (launcher with a git tag per run, ledger, schedule, decisions, checks, cleanup). Problem-independent.
- `bev_fusion_lane_center/` - the problem it is applied to: lane-centre-line graph from camera + radar, attached to an ADASIS-like SD map (tag prefix `lcr`). Its frame is `bev_fusion_lane_center/PROBLEM.md`; its rules, layout and commands:

@bev_fusion_lane_center/CLAUDE.md

If the line above was not expanded, read `bev_fusion_lane_center/CLAUDE.md` and `bev_fusion_lane_center/HANDOVER.md` first.

- `bev_fusion/` - a second problem: a camera + radar BEV system (plan, `training/`, `autogt/`, `evaluation/`, runs, experiments, literature); managed by `autoresearch/` since D23 (2026-10-31: `bev_fusion/project.json`, tag prefix `bf`; trainings start through `run.py`, which calls `temp/train/run_ar.sh` (it trains from the run's snapshot commit and passes on the exit code; `run_cfg.sh` always exits 0) - the start line is in `bev_fusion/records/README.md`; the tools need `AR_PROJECT=../bev_fusion`, the default problem is the lane one); duplicating code from the lane project is allowed. See `bev_fusion/README.md`.
- `datasets/NuScenes/` - description and download / check tools of the raw nuScenes data shared by all problems (README and tools in git, the data never). The raw data itself is on D: (`D:\Auto-research\NuScenes`); derived data (GT, additions, caches) belongs to the problem's project folder on C:. Existing code reads the WSL views `~/data/nuscenes_full` / `~/data/nuscenes` (symlinks to both places). See `datasets/NuScenes/README.md`.

**Hard rules and defaults** (all problems; `autoresearch/METHOD.md`): only six things are hard - (1) TEST only with a logged row under Mirko's recorded OK; (2) protected truth files only under a decided D<n>; (3) a run that feeds a verdict goes through `run.py` (a diagnostic run may use `--no-card` and never feeds a verdict); (4) a verdict comes from a rule written before the run, or is labelled "by hand: <reason>"; (5) data, checkpoints and untagged scratch are never deleted; (6) Mirko's decisions only when recorded, mail / shutdown / downloads / installs / remote only when allowed, other chats' jobs, running scripts and uncommitted files untouched. Every other rule in these CLAUDE.md files, the templates and prompts is a default: when it does not fit the case, do the sensible thing, write in the record what you did differently and why, and keep it away from where a number comes from, the TEST split, data, other chats' work and Mirko's decisions. When a hard rule is in the way, stop and ask.

## Git: what goes in, when to commit, when to push (rule of 2026-11-01, asked for by Mirko)
- main holds only long-lived things: code in a code folder (`training/`, `evaluation/`, `autogt/`, `tools/`, `tests/`, `autoresearch/`) with its test and README row, and text records (cards, summaries, result files, ledgers, decisions, plans, run records, model configs). Never: data, checkpoints, caches, binaries, logs, generated tables or json, files over 1 MB, third-party code
- scratch (anything in a `temp/` or `_to_delete/` folder) is not committed by hand and not put into main by "commit the working tree". What ran is kept by the run's tag (`run.py`, `clean_temp.py` commit through a temporary index and tag; main is not touched). A one-line wrapper around a command is not kept at all: the card carries the exact command
- a script stops being scratch when it is used a second time, when a card, report or run record names it as how a number was made, or when other code imports or launches it. Then it moves into a code folder with a test and a README row, in the same commit, and the card cites the command of the suite (example: `bev_suite.py front`, promoted from a temp script). `autoresearch/tools/check_git.py --used` lists the scratch that is already used (the work list); a new script that is needed twice is promoted at the second use, not later
- commit: one finished unit (a tool with its test, the records of an experiment: card or summary + result file + ledger row, a decision), own paths only (a temporary index when other chats work in the checkout), `check_git.py --paths <the paths>` clean, the folder's tests green, shared code through a critic pass
- push: only when main is a state others can rely on (a reviewed unit finished, or the end of a work session) and only when asked or when a standing instruction says so; never with failing tests, scratch or forbidden files in the unpushed commits, or the records of a run half written. Before each push `git fetch` and `check_git.py` (it lists the unpushed commits, which include other chats' commits: read them); only commits are pushed, uncommitted files stay; no force push, no history rewrite
- control: `python autoresearch/tools/check_git.py` (exit 1 on staged scratch or forbidden files and on unpushed commits that add them; it counts the untracked scratch that `git add -A` would sweep in and lists the scratch that something points at). Legacy: the files of `temp/` folders tracked before this rule (history is not rewritten) were cleaned up on 2026-11-01 at Mirko's word: the `.gitignore` now ignores `temp/` (the launcher's snapshot adds the scripts of the scratch folder by force, so a run's tag still holds them), the scratch that nothing points at left the tip of main (`git rm --cached`, the files stay on disk), the scratch that records or imports point at (`check_git.py --used`) stays tracked until it is promoted
- the best three networks (standing instruction of Mirko, 2026-11-01): each problem keeps its best three networks, one slot per checkpoint (`autoresearch/tools/keep3.py`; the record `keep3.json` lies next to the ledger). Their checkpoints stay complete, every other checkpoint may be slimmed or archived, never deleted. When a network comes into the three (the written rule: beats the weakest by more than the band, with a KEEP row of the ledger or "by hand: <reason>"), commit its text records (own paths) and push, after `git fetch` and `check_git.py`

Other things in this folder: `wsl/` is the Ubuntu disk image of the WSL distribution (registered with WSL: do not move, rename or delete, never in git); the scripts and the move log of the folder migration of 2026-10-24 are in `bev_fusion_lane_center/experiment_execution/history/migration_tools/`.
