**What it does**: BEV segmentation on a set of sparse BEV points instead of a dense grid. Sparse Feature Pulling: each 2D BEV point becomes a pillar of 3D points at evenly spaced heights, only the cameras that see a point are used (avoids about 84 percent of the projections on six cameras), the image feature is bilinearly interpolated, features from several cameras are averaged. No depth distribution and no depth weight (the paper says it avoids estimated depth, like Simple-BEV and BEVFormer). Coarse points are random in training and a sub-sampled grid at test time; points above tau = 0.1 are densified in a window (coarse-to-fine).

**Results that matter** (nuScenes, 224 x 480, six cameras): vehicle IoU 38.1 (ResNet-50, no visibility filter), 44.0 (EfficientNet-b4, visibility filter); pedestrian 18.5 static / 19.9 temporal; lane 49.6 IoU. Module in isolation (six cameras, 200 x 200 x 8 pillar, 128 channels): 1.9 ms forward vs 4.3 ms and 6.2 ms backward vs 26.0 ms for the standard PyTorch pull (GPU not named for this benchmark); network memory 3.50 vs 4.57 GiB and 14.84 vs 13.70 FPS at batch 1 (40 GB A100 for the ablation). GaussianLSS (2504.01957) cites PointBEV at 47.6 vehicle IoU / 32 FPS / 1.26 GiB as its projection-based reference.

**Transferable technique**: visibility mask per camera before projecting (never project into cameras that cannot see the point; for us the frustum coverage mask doubles as the valid flag); a pillar of heights per cell with a plain bilinear gather is competitive on map classes (lane 49.6); the pull is differentiable and the depth-free null for lift PD.

**Cost and fit**: plain PyTorch, MIT, the closest reusable code for a pull; the sparse coarse-to-fine scheme is an option for speed, not needed at 120 x 104.

**Doubts**: no pulling vs splatting ablation; no depth means the far range has the ray ambiguity PD removes; speed numbers use unnamed GPUs in the module benchmark.
