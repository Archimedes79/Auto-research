# Evaluation

One place for how results are measured. Rule: **do not write a private metric - use or extend these**, compare only on identical frames, run the self-tests after touching anything here (`tools/maintenance/run_all_tests.sh`).

## Evaluate a model: one command

```
wsl bash tools/env/_py14.sh evaluate.py --list
wsl bash tools/env/_py14.sh evaluate.py champion --compare control
wsl bash tools/env/_py14.sh evaluate.py recall --asm fork_prune=0.3 --tag p03
wsl bash tools/env/_py14.sh evaluate.py --golden check --cached-only     # layer 1: every golden number reproduced (7 entries, not every registry name; also in run_all_tests.sh)
wsl bash tools/env/_py14.sh evaluate.py --golden check --fresh-only      # the network path: champion re-inferred on VAL250 without the cache (idle GPU)
wsl bash tools/env/_py14.sh evaluate.py champion --route --route-tokens tok_p18_f1pr_val_clean --expect route_success=0.8991   # part: route success from stored tokens (CPU)
wsl bash tools/env/_py14.sh evaluate.py champion --failure dark,blur,cam_front3_off --series-dir e130_champion                    # part: failure series from stored graphs (CPU)
wsl bash tools/env/_py14.sh evaluate.py champion --route --failure dark,blur,cam_front3_off --timing                              # the three parts from the network (GPU; --timing on an idle GPU only)
```

`evaluate.py <name>` takes a name from `../models/registry.json` (checkpoint + config + the standard assembly settings), runs it on VAL (873 frames; `--split test` only with a `--test-id` logged in `TEST_USAGE_LOG.md`) and writes `runs/eval/<name>/<split>.json` with all metrics, the settings, the cache file and the code commit. Network outputs are cached once per checkpoint, split and inference setting (`~/exp_gcar_b123/eval_cache/`; `cache_paths`: the file name holds run, M, K0 and a digest of every other `set` field, so a new setting never re-scores an old cache), so assembly settings are re-scored on the CPU in about a minute; `--subset val250` takes its frames from that cache too (only `--fresh` or a missing cache runs the network; only a whole split computed on the GPU is written, atomically). A registry entry of kind `union` (E264) names `members` (builder entries) whose trees are joined per frame (`p16_infer.union_raw`) and assembled once; each member is read from its own cache, the members must share the ground truth, and the card's `info.members` records their entries. The cards also carry `R@1_far_inner` / `R@1_far_ring` (and `P@1_*`): the far bin split at max(|x|,|y|) = 45 m (E266). `--compare <name>` adds the paired scene bootstrap. A card also records the training `seed` of its run (the run card in `runs/e123_ladder/cards/`, when it has one) and `protocol.gt_sha`, a digest of the ground truth of the frames it was scored on: `../../autoresearch/tools/decide.py` pairs the arms by the seed and refuses cards of one comparison whose protocol differs or is missing on one side, so cards written before this field (2026-11-01) need a re-evaluation (a cached one takes about a minute; it overwrites `runs/eval/<name>/val.json`, the path the experiments read, so check with `git diff` that the metrics did not move) or `evaluate.allow: ["protocol"]` in the experiment file. An arm that lists several different models of the same seed (every model before E24 has seed 0) cannot be paired by seed: that experiment declares `"pairing": "position"`. A new model gets a registry entry, not a new evaluation script. `golden.json` holds the golden numbers (7 entries: champion, champion_noprune, control, fast, fast_recall and recall on VAL from the cache, plus the champion re-inferred on the 250-frame subset `--subset val250 --fresh`, tolerance 0.0005 each; the other 46 of the 52 registry names are NOT guarded, among them every `*_dp`, `recall_sp0`, `*_ring` and union entry; `golden.json` is protected, new entries need a grant under a decided D<n>); `--golden check` reproduces them or exits 1, `--golden write <name>` changes an entry (only together with a ledger row that says why). `--compare` between a `*_dp` name and another name warns that S is not comparable (S divides the 14.3 oracle by the node-id count that `simplify_dp` lowers) and writes `compare.s_not_comparable`: read Q. **Parts (W11, [eval_parts.py](eval_parts.py)):** `--route` (route success; keys `route_success / route_cov / route_prec / route_frames` of `drivers/p16_pipeline_eval.py`, plus `route_empty`: a frame with route points and an SD map whose assembled graph is empty counts as a failure, the denominator is `route_frames` = the frames with route points; `--split test --route` reads the data files of the part `val`: the TEST rows live in the VAL pool), `--failure <perts> [--variant single]` (graph metrics per phase, clean half `cl` and perturbed half `fail`, of the failure series of `p17_series.py`: keys `series.<pert>_<variant>.<cl|fail>.<S|Q|F1@1.0|J|topo_F1|lanes_found|vert100>`; with `--route` also `.route_success` per phase) and `--timing` (ms per frame of the whole chain through `drivers/p18_latency.py`: `ms_per_frame`, `ms.<stage>.<median|p90>`) call the code of the loop drivers (imported, not copied) on a registry entry and write their numbers into the same card (`metrics`, `better`, full per-phase cards and the latency json in `info.parts`); a card with parts without `--tag` is `<split>_parts.json`, never the standard card. They run the whole split (no `--subset`, no `--fresh`). Stored inputs need no builder run and no GPU: `--route-tokens <name>` (route tokens of `~/exp_gcar_b123/p10/`) and `--series-dir <dir> [--series-suffix _fp03]` (graphs of a stored series run in `runs/e17/<dir>/`); otherwise the part runs the network (builder entries only; route and series use the registry entry's `tau` and `asm`; the route head is `--route-head`, default `p16_f2hr_route_s0`, a route comparison needs `_s0` and `_s1`). `--timing` accepts only what the driver times (design D7 with M / K0, tau 0.7, the standard assembly with `fork_prune` / `fast`, time recursion off, a union of two builders as `--name2`) and refuses the rest; run it on an idle GPU, nothing else running. Verified without the GPU (`tests/test_eval_parts.py`): the stored tokens of the champion with fork pruning give route success 0.89915 on 823 route frames = `runs/e123_ladder/diag/pipeeval_f1_288_s0_fp0.3.json`; the stored series graphs give the cards stored in their files. **Not verified (needs the GPU, run when it is idle): the three network paths** - `evaluate.py champion --route --expect route_success=0.8991` (the CUDA-graph chain must give the pipeeval number 0.8991 up to fp16 noise), `evaluate.py champion_noprune --failure dark` against `runs/e17/e130_champion/dark_single.pkl` (S cl 0.7502 / fail 0.4236), `evaluate.py champion --timing` against the stored `runs/e18/latency/latency_M288_rec0_u2_fp0.3_*.json` (total median about 20 ms). Per-frame time of the CPU assembly in the card (`info.asm_ms`) is not the timing part. The per-loop drivers below are kept for reproducing old numbers.

Headline metrics (see `PROTOCOL.md`): **Q** at <= 14.3 vertices per 100 m, **topo F1** (connectivity), **lanes found**, **R@1 far** (beyond 40 m), route success, ms per frame; S stays for comparison with the history; FL and dup_frac as checks.

## What the checks say (2026-10-25, `evaluate.py`, VAL 873 frames, paired over 22 scenes)
- `evaluate.py` reproduces the stored cards exactly (champion with fork pruning S 0.769 / F1@1 0.870 / J 0.409 / lanes found 0.695; without pruning S 0.746 / J 0.265; recall variant Q 0.740 / lanes found 0.767).
- The new metrics respond where S and Q are blind (`METRIC_RESPONSE.md`): broken lanes (60 % broken: topo R 0.69, F1 0.996, Q 0.995), reversed direction (topo F1 0.004), parallel duplicates (dup 0.34 at 30 %, ground truth 0.011).
- Champion - control: Q -0.002 [-0.011, +0.006] (tie), topo F1 -0.022 [-0.032, -0.011], lanes found -0.105, R@1 far -0.102 [-0.117, -0.087]. Fork pruning lifts topo F1 by +0.021; the recall variant buys lanes found +0.072 and R@1 far +0.063 at the same topo F1. **The open gap to the control is coverage at range and connectivity, not J.**

## What the checks said (2026-10-24)
- The metrics respond as they should to controlled errors (shift, dropped / false / duplicated lanes, cut forks, simplification, reversed direction) - and show the blind spots of S: parallel duplicates and travel direction are nearly invisible, sparsity below 14.3 vertices per 100 m is not rewarded (Sp capped).
- On real predictions the evaluation reproduces the stored history (control S 0.725 vs stored 0.724, champion 0.746 vs 0.746).
- The champion beats the control in S by +0.021 [+0.011, +0.031] (paired, scenes resampled) - **but only through sparsity**: at equal sparsity (Q) it is 0.036 worse; the loss sits in J (-0.143) and lanes found (-0.105). The next experiments are judged by Q at vertices per 100 m <= 14.3, J, lanes found, route success, ms per frame.
Details: `METRIC_RESPONSE.md` (the example run of the old examples folder was removed 2026-11-03: `evaluate.py --compare` and `lane_suite.py` do the same).
