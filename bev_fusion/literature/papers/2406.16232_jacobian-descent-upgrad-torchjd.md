**What it does** [checked]: Jacobian descent updates the parameters from the Jacobian J (one row = the gradient of one objective) through an aggregator A(J). UPGrad (the recommended one) projects every row onto the dual cone of the rows of J (the closest vector that does not conflict with any gradient) and averages the projections; if no two gradients conflict it is the plain mean. The projection is solved in the dual: a QP with m variables (m = number of objectives) on the Gramian J J^T, which usually dominates the cost. Convergence to the Pareto front is proved for smooth convex problems. The library implements 23 aggregators (UPGrad, Aligned-MTL, CAGrad, ConFIG, DualProj, ExcessMTL, FairGrad, GradDrop, GradVac, IMTL-G, Krum, Mean, MGDA, MoDo, Nash-MTL, PCD, PCGrad, SDMGrad, Sum, ...) and 12 scalarizers (FAMO, IMTL-L, UW, DWA, STCH, COSMOS, GeometricMean, PBI, ...) behind one interface, plus an "autogram" engine that builds the Gramian layer by layer without holding the full Jacobian.

**Results that matter** [checked]: the paper's experiments are instance-wise risk minimisation (per-example losses as objectives) with small CNNs on 1,024-image subsets of SVHN, CIFAR-10, EuroSAT, MNIST, Fashion-MNIST, Kuzushiji-MNIST; UPGrad beats the mean aggregator on all six (8 runs each, no accuracy values in the text read). The NYUv2 / Cityscapes / CelebA multi-task benchmarks are NOT used, and the authors say proper multi-task benchmarks with strongly conflicting objectives are still needed. So there is no dense-prediction or BEV evidence for UPGrad in the paper.

**Transferable technique**: the API for task groups on a shared trunk: `mtl_backward([L_areas, L_lines, L_objects, L_motion], features=F)` puts each head's gradient in its own parameters' `.grad` and the K-row Jacobian in `.jac` of the shared parameters; `jac_to_grad(shared.parameters(), UPGrad())` aggregates it; then `optimizer.step()`. The same library gives FAMO, IMTL-L and UW as one-line scalarizers, so one harness covers the cheap arms and the gradient-surgery arm.

**Cost and fit**: `mtl_backward` differentiates with `torch.vmap` (it fails for compiled outputs, tensors with `retains_grad`, RNNs on CUDA; `parallel_chunk_size=1` as the fallback), requires that shared and task parameters do not overlap, and the docs give no timing. Inference [memory]: the Jacobian is K rows over the shared parameters, so about K backward passes through the trunk and K copies of the trunk's gradient memory (4 x for our four groups) plus a K x K QP: the full-trunk cost that the feature-level methods (IMTL-G, FULLER; see 2307.16617) avoid by working on the BEV feature tensor instead. The autogram engine needs "batched" modules; BatchNorm (batch statistics) is the stated counterexample [digest, docs mirror], which matters because the lane project had BatchNorm derailments. No GPU number for a 3060.

**Doubts**: no multi-task benchmark in the paper; the v4 / NeurIPS 2026 status is as printed on the page; the library API is young (the page warns the autogram interface may change); per-step cost unmeasured here.
