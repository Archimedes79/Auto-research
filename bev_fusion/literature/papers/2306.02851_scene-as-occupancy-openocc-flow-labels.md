**What it does**: OpenOcc is a nuScenes occupancy set built like Occ3D / SurroundOcc: points split into static background (accumulated in the global frame) and foreground objects (accumulated in object frames from the boxes), majority vote per voxel, holes filled in post-processing, camera invisibility by ray tracing. New: occupancy flow, a per-voxel velocity from the box velocity, given for the eight movable foreground classes, objects counted as moving above 0.2 m/s.

**Format and coverage**: paper: 16 classes (10 foreground incl. barrier and traffic cone, 6 background), [-50, 50] x [-50, 50] x [-5, 3] m in lidar coordinates at 0.5 m, 34,149 frames over 700 + 150 scenes (checked on the paper page). Repo README (`openocc_v2.1`, 2024/03/14, bug fixes of the flow): 0.4 m, [-40, -40, -1, 40, 40, 5.4], 200 x 200 x 16, 17 classes, per frame `labels.npz` with `semantics` and `flow`; files `openocc_v2.1.zip` and `infos.zip` from OpenDataLab or Google Drive; no size stated (search-snippet and repo page, checked). The shape and unit of `flow` are not stated on the pages read.

**Results that matter**: none for radar.

**Transferable technique**: parked versus moving: a voxel of a movable class with zero flow is stationary. We already have this from the boxes (speed < 0.5 m/s over the whole track in `training/gt_bev.py`), so the flow adds nothing unless we want it for voxels away from annotated boxes.

**Cost and fit**: same cut as Occ3D at 40 m for v2.1; labels derived from nuScenes lidar, non-commercial.

**Doubts**: the paper / repo grid mismatch (0.5 m +-50 m vs 0.4 m +-40 m) means a reader must check which version is on disk; flow is defined for boxes only, not for static structure; the 2024 bug-fix note says earlier flow was wrong.
