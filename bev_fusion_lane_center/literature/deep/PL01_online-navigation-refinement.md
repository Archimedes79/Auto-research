## 1. Problem and claim  [digest]
Given an SD road graph (OSM; each road = ordered directed vectors, plus connectivity) and an online-perception (OP) map (lane centre-line vectors with topology, plus road-boundary vectors) in a shared ego-centred frame, predict for every perceived centre-line the unique SD road it belongs to (multi-to-one: many centre-lines per road, one road per centre-line). With that assignment an SD *route* (a path of roads) is turned into a lane-level path on the perceived map ("online navigation refinement"). Gap closed: no public data set had lane-to-road correspondences, and classical map matching (GPS trace to road network, one-to-one) does not fit heterogeneous map-to-map association. The claim that matters: a plain transformer with path-ordered and space-filling-curve-ordered attention reaches NR-F1 78.7 on clean (ground-truth) perception maps against 72.9 for the best classical map-matching baseline, and keeps its lead on generated (noisy) perception maps; the output is **hard and road-level**.

## 2. Method as built

### Task definition (Sec. 3, digest)
- SD map: graph G_R = (R, E_R); a road r_j is a sequence of directed vectors (q_j1 q_j2, q_j2 q_j3, ...), points in R^2, obtained by uniform spatial sampling of the OSM polyline; number of points per road not stated.
- OP map: graph G_L = (L, E_L); a centre-line l_i is a vector p_i1 p_i2 (sampled at uniform intervals), E_L = topological relations of adjacent centre-lines; boundaries B = {b_j}, each a sequence of vectors like a road.
- Objective: learn f: L -> R, each centre-line to exactly one ground-truth road (uniqueness), a road may own several centre-lines (multiplicity); "multi-to-one classification" with |R| classes. The SD **route** is not an input to f; it is applied afterwards.

### Pipeline / architecture (Sec. 5, App. F/I, code; digest)
```
SD road vectors  (crop 150 x 150 m, ego-centred)  \
OP lane vectors  (crop  30 x  60 m, ego-centred)   >  per-vector feature, category flag road/lane/boundary
OP boundary vectors                                /     paper: v = [x1,y1,x2,y2,theta] -> 2-layer MLP -> C
                                                         code : 6 ch = coord(2) + vector(2) + angle(1) + category(1)
   -> voxel sampling of (x, y, theta) with grid 0.1 m x 0.1 m x pi/16, one token per voxel (training: random pick)
   -> all tokens of a scene in one flat set (road + lane + boundary), offsets for batching
   -> 5 stages, channels [96,192,384,768,1536], heads [4,4,8,8,8], MLP ratio 4, drop path 0.3, group ("patch") size 1024
        MAT-T blocks [2,2,2,2,2] (34 ms), MAT-L blocks [4,4,4,12,4] (70 ms)
        block = Spatial Attention (SA) , Path-aware Attention (PA) alternating (attention order "SA then PA") + FFN
   -> association head: lane token . mean-pooled road token / sqrt(d), softmax over roads  (Eq. 4)
   -> (inference) argmax per vector (released tester) or topology-constrained bidirectional beam search (paper)
```
- **Vector encoding.** v_i = [p_i1x, p_i1y, p_i2x, p_i2y, theta_i] with theta_i = arctan((dx)/(dy)) as written in the paper (ambiguous between quadrants; the code uses a safe arctan2 in [-pi, pi]). C (embedding width) is given in the appendix as the first channel entry, 96.
- **Path-aware attention (PA, Sec. 5.2, App. F.1).** Valid paths = complete paths from nodes with no incoming connection to nodes with no outgoing connection (root-to-leaf). The tokens of one path are concatenated in path order; a token lying on several paths is **duplicated**, attention is computed only among tokens of the same path (in windows of k = 1024 tokens; longer paths are split into groups of k), outputs are mapped back, copies of the same token **averaged** over the paths. Complexity: worst case O(k n^3) when about two thirds of the elements are path starts or ends, average O(k^2 n), versus O(n^2) for dense attention. Loop handling: not described. Group method ablation (Table 12): no grouping 78.0, grouping by category 78.2, grouping by path 78.7. Group size ablation (Table 11): 64 / 256 / 1024 / 2048 / infinity = 77.8 / 78.4 / 78.7 / 78.5 / 78.4, latency 77 / 68 / 70 / 72 / 72 ms. In the common-path sense, two tokens attend to each other iff one is an ancestor of the other (siblings on different branches are excluded).
- **Spatial attention (SA, Sec. 5.3, App. F.2).** Each vector token gets a 3-D integer coordinate (x, y, orientation bin) (grid 0.1 m, 0.1 m, pi/16); a space-filling curve (Z-order, transposed Z, Hilbert, transposed Hilbert) maps it to a 1-D index; tokens are sorted by the index, cut into groups of size k, self-attention inside each group, inverse permutation. Paper: "one curve chosen at random per training iteration". Curve ablation (Table 16): Z 77.6, Z+TZ 78.1, H+TH 78.2, all four 78.7. Complexity O(k n).
- **Boundaries.** Boundary vectors are extra tokens in the same set (+0.7 NR-F1 for +5 ms, Table 3). Their role in attention is not described beyond that.
- **Cross-attention.** The paper says road/centre-line association is "calculated through cross-attention" (Sec. 5.4); the code has **no separate cross-attention**: road, lane and boundary tokens are one set with a category flag and meet in SA windows and, for lanes, in PA windows (digest; see section 4).
- **Association head.** Road tokens of road j are mean-pooled (Eq. 3), the dot product with a centre-line token is scaled by sqrt(d), softmax over all roads of the scene (Eq. 4). Pooling ablation (Table 4): average pooling beats max by 0.2.

### Inputs, outputs
- Input: SD crop 150 x 150 m (Table 7: HD range +-15 m x +-30 m, SD range +-75 m x +-75 m); tokens per scene not stated; no ego pose, no GPS value, no image; frame = ego-normalised coordinates ("coords_norm" in the data; unit not stated, see section 6). SD input size ablation (Table 13): 60 / 90 / 120 / 150 m = 78.6 / 78.6 / 78.7 / 78.7 (67 / 69 / 69 / 70 ms).
- Output: for each lane vector a probability vector over the roads of the scene; no "no road" class (a ground-truth label -1 exists in the data, is ignored in the CE loss and counted as correct in the metric). Lane-level route: the SD path is mapped to an OP path by the road-id sequence ("topological sorting").

### Equations (numbering as seen: (4), (5), (6); the others are my labels E1-E3)
- E1 (number not seen): v_i = [p_i1^x, p_i1^y, p_i2^x, p_i2^y, theta_i].
- E2 (number not seen): road feature pool, Fbar_j = (1/N_j) sum_n F_jn, N_j = number of tokens of road j.
- E3 (number not seen): 3-D serialisation index = phi^-1(x, y, r), phi a Hilbert (or Z) curve, r = orientation bin.
- (4) Prob_ij = exp(F_i^cl . Fbar_j / sqrt(d)) / sum_{k=1..K} exp(F_i^cl . Fbar_k / sqrt(d)), K = number of roads. Closed set: sum_j Prob_ij = 1.
- (5) L_total = alpha L_CE + beta L_CTC, alpha = 1, beta = 0.01.
- (6) T_max = argmax_{l in path P_j} max_{r in R} P(l, r): start token of the beam search of each path.
- Metric (App. E): NR-P^{50:95} and NR-R^{50:95} = averages over the thresholds T in [0.5:0.05:0.95] (10 values; one passage says 11), NR-F1 = 2PR/(P+R); on val NR-R = 1 so NR-P is used as NR-F1.

### Losses
- CE over roads, weight 1.0 (code: label smoothing 0.1, ignore index -1, mean over samples).
- CTC, weight 0.01. **How the CTC is built is not described in the paper** (only cites sequence-alignment work, GraphMM and MTrajRec). In the released code the CTC call uses input length 1 and target length 1 and no log-softmax (digest, read twice with the same result); see sections 4 and 5. Ablations: Table 4 CE+CTC 78.7, CE alone 78.4, CTC alone 67.7 (the text says "+0.3 over CE alone, +11.0 over CTC alone"); Table 15 beta_ce : beta_ctc = 1:1 gives 68.4, 1:0.1 78.5, 1:0.01 78.7, 1:0.001 78.4, 1:0 78.4.
- No Hungarian matching, no Sinkhorn, no dustbin: direct dense classification against labels.

### Labels / ground truth (Sec. 4.1, App. B, D; digest)
- **SD roads:** from OpenStreetMap, cropped 150 x 150 m around the ego pose; road = polyline cut into uniformly sampled vectors with connectivity (links have input/output link fields in the data). Which OSM road classes are kept, how the geo-coordinates are converted to the nuScenes frame and how curves are sampled: **not found** in the paper.
- **OP ground truth:** nuScenes (Boston, Singapore) ground-truth map, centre-lines "scanned with LiDAR" plus road boundaries, cropped 30 x 60 m around the ego, vectors normalised "to the ego perspective".
- **Association label:** two-stage workflow (App. D.5): (1) coarse alignment from the GPS coordinates of the OSM SD map and the nuScenes ground-truth map, (2) a team of annotators links SD roads to perception-map lane vectors, specialists review. Table 8 gives "refinement" counts: Boston 2,341 of 1,205,661 centre-lines (0.194 %), Singapore 3,682 of 910,140 (0.404 %); the text says changes stayed below 1 %. The text of Sec. 4.1 says "manually annotated"; the tiny change rates indicate that the manual work is a correction of an automatic geometric proposal (my reading, not stated). Transition rule (D.6): a lane vector lying across an SD-link boundary belongs to the SD link nearest to its **start point**; the strictest metric threshold keeps a 5 % tolerance for this.
- **Per-vector label in the data:** `link_ids` per lane vector (two entries, start and end; `-1` = no road), `path_ids`/`path_idx` (membership in enumerated lane paths), `coords_norm` (ego frame) and `coords_enu` (absolute), `sample_point` (metric support points) (Hugging Face schema, digest).
- **Splits and sizes:** nuScenes "pon" (area-disjoint) split. Table 7: scene segments train 26,111 / val 5,613 / test 5,573; abstract: about 30 K scenarios, 480 K road paths, 2.6 M lane vectors (Table 8 sums to 2.1 M centre-lines for the two cities; the two numbers are not reconciled in the text). Per-scene averages (Table 7, train / val / test): lanes 81.3 / 75.8 / 310.34 (the text says 73.8 for train/val, inconsistent), lane paths 7.40 / 7.97 / 322.06, boundaries 3.48 / 3.31 / 9.65, length per lane 3.14 / 3.19 / 2.32 m, length per boundary 44.81 / 43.64 / 32.17 m, roads 15.1 / 10.8 / 10.8, road length 38.2 / 50.3 / 50.3 m, connections per lane 2.0 / 2.1 / 2.9, per road 2.0 / 1.8 / 1.8. Train and val use the **ground-truth** OP map; **test = the val scenes with OP maps generated by MapTRv2** (retrained on the pon split) and, in Table 2, by MapTR and SeqGrowGraph; the test scenes carry no association labels of their own, the val labels are used and generated paths are matched to ground-truth paths geometrically (Chamfer, 1 m). The generated test maps have four times more lane vectors per scene than the clean ones (310 against 76): over-segmentation, fragmentation, false positives, mislinked lanes (App. D.1 text).
- **Noise / offset simulation:** none during training except the random augmentations below (joint rotation, scale, flip; independent jitter sigma 0.005 clipped at 0.02). Noise comes from real perception generators on the test side. Imperfect-SD protocols exist only as **test-time** perturbations (App. G.2): global shift (one uniform random offset per sample for all road vectors, shape preserved), element noise (independent perturbation per vector), element absence (random removal of road vectors); magnitudes are given as ratios "relative to the global map range" and **not in metres**.

### Training recipe (Sec. 6.1, Table 23; digest)
AdamW, base lr 1e-4, cosine schedule with 2 warm-up epochs, 50 epochs from scratch, batch 128, weight decay 0.05 in the text and 5e-3 in Table 23 (code config: 0.02), NVIDIA A6000 GPUs (number and time not stated), mixed precision in the code. Augmentation (Table 23): random rotation about the z axis, angle [-1, 1] (x pi) with p = 0.5, scale [0.9, 1.1], flip p = 0.5, jitter sigma 0.005 clip 0.02, grid sampling [0.1, 0.1, pi/16]. MAT-T and MAT-L differ only in block counts. Data efficiency (Table 6): 1 / 2 / 5 / 10 / 20 / 50 / 100 % of the training data give val 24.9 / 64.4 / 77.1 / 77.7 / 77.3 / 78.3 / 78.7 and test (MapTRv2) 22.3 / 41.5 / 44.5 / 44.6 / 46.6 / 44.7 / 45.0. Cross-city (Table 5): Singapore to Singapore 77.5 / 49.5 (val / test), Boston to Singapore 77.3 / 48.7, Boston to Boston 79.4 / 42.9, Singapore to Boston 79.0 / 42.6.

### Inference (Sec. 5.5, App. F.3; digest)
Topology post-process: for each lane path, start at the most confident token (Eq. 6), then a **bidirectional beam search** along the road connectivity (each step extends left or right: 2|R| candidates, score = sum of log-probabilities, keep the best k, stop at maximum length T, T not stated); beam width k = 4 (Table 17: 1 / 2 / 4 / 8 = 78.2 / 78.6 / 78.7 / 78.7, latency 69 / 70 / 70 / 78 ms). Gain of the whole post-process: +0.2 NR-F1 (78.5 to 78.7) for 1 ms (Table 3). The released tester does a plain per-vector argmax (no beam search; the README still lists the post-processing code as a TODO). Hidden rule steps: argmax, beam search, road connectivity, start-token choice, topological sorting of the route into lane paths.

## 4. Paper versus code  [digest of the repository, commit 6098d25]
- **Features:** paper 5-D vector + 2-layer MLP; code 6 input channels (sum of the two end points, vector, atan2 angle, category 0 road / 1 lane / 2 boundary) and an embedding of Linear + BatchNorm + GELU. Category is an input.
- **Cross-attention:** none in code; one token set. RoPE (3-D coordinates) is used in all attention layers and FlashAttention (hard-coded fp16) is the only attention backend; RoPE is not mentioned in the text I read.
- **Path enumeration:** the loader reads a ready-made `path` list (lists of lane ids) from the JSON; lane tokens are duplicated per path. The road side is grouped per link and the link `input`/`output` connectivity fields are **not read** by the loader (digest; to verify): road-graph topology reaches the model only through the order of segments inside a link. The enumeration code (and the conversion from OSM / nuScenes to the JSON) is not in the repository; the evaluation code has a BFS path finder.
- **Serialisation:** paper "random curve per iteration"; code cycles the four curves over the blocks and randomly permutes their order at stage changes.
- **Optimiser:** weight decay 0.02 in the config (0.05 text, 5e-3 table); OneCycleLR with cosine annealing, pct_start 0.04 (= 2 of 50 epochs), div_factor 10, final_div_factor 100; label smoothing 0.1 (not in the paper); MAT-S config repeats the training set 5 times per epoch (loop = 5).
- **CTC:** paper silent; code: zero column prepended as blank (index 0), labels shifted by 1, **input length and target length both the literal tuple (1,)**, raw similarity scores fed without log-softmax, samples with any ignore label skipped. Read like this the term only touches the first element of the path and is an unbounded linear logit term; this would also fit the collapse at beta ratio 1:1 (68.4, Table 15). **This needs a check by someone who reads the raw lines 60-82 of `loss.py`**; I saw it twice through the same summariser.
- **Inference:** the released tester (`MatchTester`) takes the plain argmax per lane vector, writes `pred_link_ids` and the probabilities to JSON/CSV (the CSV has an "epsilon" column = 1 - row sum, always 0 for a softmax); no beam search, no topology constraint. The validation hook reports element-wise argmax accuracy, not NR-F1.
- **Test config** points to the val split name. Several smaller defects are listed in the code file.

### 5.1 What MAT outputs, precisely
Per perceived centre-line vector i a categorical distribution over the roads j of the supplied SD crop, trained with CE against one road id; **the route is not an input**, assignment and route are two steps. At test time: argmax (released) or beam search along road connectivity (paper). Ground truth label -1 ("no road") exists but is ignored in the loss and counted as correct in the metric, so nothing in training teaches "none of these roads". Lane-level guidance = the lane path whose road sequence equals the SD route; lanes of one road are not distinguished by the head, they are separated by topology (a lane belongs to the route if the path it lies on realises the next manoeuvre).

### 5.2 (a) Soft route probability per vertex / edge
Needed:
1. SD-side road ids and a per-road pooled token (scatter mean over the cells or vectors of road j), plus the route as a 0/1 mask m_j over the roads of the scene (known from the ADASIS-like horizon).
2. The head of Eq. 4 on our 128-d vertex tokens (d = 128): P_ij = softmax_j(t_i . tbar_j / sqrt(128)) over the valid roads (masked softmax).
3. Route marginal r_i = sum_j m_j P_ij = P_i . m, trained with BCE against the existing route label of vertex i, optionally CE on the road id of vertex i as auxiliary. No Eq. 6, no beam search, so the training path stays free of argmax and rules. For edges: evaluate P along the edge at points every <= 4 m (K185) and aggregate with the edge-wise soft weights.
4. Labels: road id per vertex from the nearest ground-truth lane (offline label construction, as the route labels are today); not part of MAT, and the part that costs the days.
5. **Lane level is not given by MAT's head.** r_i only says "this vertex lies on a route road". To separate the lanes of one road before a junction a second quantity is needed, for example a path-aware attention block (below) followed by a route head, or a differentiable forward propagation over the edges (child mass pulled back to parents with edge weights, noisy-OR at forks); training with the driven-lane label as today. This is my proposal, not MAT.

### 5.3 (b) Explicit road-level fallback when lanes are unreliable
Needed: (1) both outputs side by side: road-level r_i (above, available whenever the vertex is assigned to some road) and lane-level lambda_i (the extra quantity of 5.2 item 5); (2) a per-vertex or per-edge gate g in [0, 1] computed from the token, the entropy of P_i, the validity v_i, the edge probability and the local lane count, output p_i = g lambda_i + (1 - g) r_i together with a level flag that the planner reads; (3) training that makes the gate useful: graphs with dropped or fragmented lanes (our failure scenarios, MAT's element-absence idea applied to the *perceived* side), plus a calibration loss (route NLL of p_i, penalty for confident lane-level errors); (4) a road-level metric (road recall of the route within 1.5 m, independent of lane choice) next to route success. MAT contributes the road-level head and the evidence that road-level assignment survives bad perception (association precision falls only a few points while the generated-map test falls by half: the geometry fails first, see Table 19).

### 5.4 (c) Abstention when the SD map is wrong
MAT has none: the softmax is closed over the roads given, absent roads cost 1.2 / 2.3 / 3.2 val points at 10 / 12 / 30 % removal (Table 20) without any signal. Needed: (1) a **dustbin column** (a learned "no road" key appended to the pooled road tokens, SuperGlue style) so that P_i,0 is a proper mass; (2) labels for it: lanes whose road was removed, lanes with `-1`, and all lanes of a replaced map; (3) a synthetic wrong-map set built from MAT's three protocols (global shift, element noise, absence) extended by the cases MAT never tested (map of another place, rotated or mirrored map, route on the wrong carriageway); (4) a map-trust scalar per frame, for instance the validity-weighted mean of 1 - P_i,0 or a small classifier on pooled tokens, made persistent over time by log-odds accumulation on the vertex memory (a wrong map stays wrong, a detection flickers); (5) the decision: trust below a threshold sends the route attribute to "unknown" (flag, probability not forced), evaluated by AUROC against the wrong-map label, risk-coverage curves, and ECE of r_i. Wrong map versus registration offset must be separated by registering first and judging the residual.

### 5.5 (d) Our graph and a registration error of 0-3 m instead of an aligned frame
**MAT's alignment assumption (digest):** both maps live in one ego-centred metric frame; the SD crop is cut around the ego pose that nuScenes provides and positioned by OSM geo-coordinates (annotation step "coarse alignment from GPS coordinates"), so the offset the model sees is only the genuine OSM-versus-real-lane misfit; the model gets no pose input, estimates no pose and never saw a relative rigid offset in training (a random-shift transform exists in the code but is not in the training config; rotation, scale and flip act jointly on both maps; independent jitter is 5 mm). The paper names "spatial fluctuations such as GPS drift" as a motivation but states no magnitude. Tested only as an SD-side global shift of 10 / 20 / 50 % of the map range, metres unspecified (if the ratio refers to the 150 m crop that is 15 / 30 / 75 m, if to the 30 m width 3 / 6 / 15 m; not decidable from the text), costing 1.2 / 2.7 / 4.1 points on val.
Needed for 0-3 m:
1. **Shift training:** per-sample random translation of the SD side relative to the perceived graph (0-3 m for the target, up to about 5 m for margin), small rotation (a few degrees) and smooth local warps (OSM errors are not rigid); labels unchanged because they are topological. Cheap (S), and the first thing to try.
2. **Registration in the loop (optional):** P_ij is a soft correspondence; a weighted Procrustes / translation-only step (weights P_ij and validity, target = nearest point of the assigned road polyline) can be iterated 2-3 times with gradient, giving an offset estimate and a residual that doubles as trust (C32, OrienterNet K99 as the heavier alternative). Caution: learned localisation was worse than rule-based registration in E103 (0.78-0.71 against 0.86-0.84).
3. **Geometry encoding:** use positions relative to the SD geometry (distance and direction of a vertex to the soft-nearest road point) and relative position encodings; absolute RoPE on voxel coordinates tolerates offsets only through the augmentation.
4. **Graph tokens instead of 3 m vectors:** one token per edge (parent to child) built from the two vertex tokens and the geometry [x1, y1, x2, y2, theta] (our edges are about 7 m at 13.5 vertices per 100 m, MAT's vectors 3 m); 128-d tokens replace the 6-channel MLP; validity as key mask, loss weight and pooling weight; padding to a fixed vertex count.
5. **Forks / merges:** MAT's PA equals "attend only to ancestors and descendants" (tokens sharing a root-to-leaf path), so with N of a few hundred vertices it is a dense attention with a reachability mask (transitive closure of the parent pointers, or log edge probabilities added to the logits to keep gradient into the edge probabilities); no path enumeration, duplication, ordering or grouping needed. Hilbert serialisation is a scaling device for tens of thousands of tokens and is not needed.
6. **Train on our own perceived graphs** (builder outputs), not on ground-truth lanes: MAT never did, and its val/test gap shows what that costs.

### 5.6 Which parts of the code can be ported to PyTorch 2.8 without mmcv
The whole repository is **mmcv / mmdet free** (Pointcept based, MIT). Pure PyTorch or trivial to replace: the association head (`default.py`, 105 lines; `torch_scatter` mean/max -> `index_add_` / `scatter_reduce`), the CE loss, the 2-D augmentations and voxel sampler (`transform_2d.py`, numpy), the dataset loader (`mapping.py`, JSON), the metric scripts (`metrics/`, numpy/scipy), the Z/Hilbert code generator (`pointcept/models/utils/serialization`, MIT). Needs replacement: `flash_attn` varlen fp16 (use `F.scaled_dot_product_attention` with a path mask, or padded groups), `transformers.apply_rotary_emb` (ten lines of rotate-half RoPE), `timm.DropPath`, `torch_scatter`. Not needed at our scale: the spconv / pointops / pointgroup_ops stack of the framework, FlashAttention, serialisation, CTC. The Pointcept `models/__init__` pulls heavy imports, so copy single files rather than the package. Details and gotchas: [oma-mat](../code/oma-mat.md).
