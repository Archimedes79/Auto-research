# nuScenes - the dataset family: raw data, everything made from it, and where each lives

`data/NuScenes/` (this folder: the README, `manifest.json` and `tools/` are in git as recipes and records, the data itself never) describes the raw nuScenes data that all problems share, the folders that hold everything made from it, and the tools that download, check, link and name them. Licence: nuScenes is for non-commercial use; downloads only with Mirko's OK.

## Archives
nuScenes comes as `.tgz` archives (camera parts 1 - 10, radar parts 4 - 10 here; lidar was not downloaded). The rule since 2026-11-02 (D42): an archive is unpacked completely, then compared with the data (`tools/verify_archive.ps1`: every member must exist below the data folder with the same size and the same bytes; the SHA-256 of the archive file is taken in the same pass), then deleted (`extract_blob.sh --delete` does the comparison first and deletes only when it shows 0 differences). Nothing is lost by that: `manifest.json` keeps every archive's identity (name, bytes, S3 ETag where a log had it, SHA-256, kind, unpacked members, the result of the comparison under `on_disk_check`, `present: false` and the date it was removed), so the data can be traced to the download and the download can be repeated (with Mirko's OK: `list_nuscenes_bucket.py` gives size and ETag of the public bucket). Downloads go to `D:\Auto-research\NuScenes_zips\` (`NUSC_DL`), nowhere else.

Why the archives were bigger than the unpacked data (2026-11-02): the four camera archives of parts 7 - 10 hold six cameras, but only CAM_FRONT had been unpacked; the other five cameras are 66.1 GB (397,348 files) that exist only inside those archives. Everything else in the archives (1,606,328 files, 120.6 GB, camera parts 1 - 6, all radars, Occ3D) was compared with the data and is identical; the only differences are the six notice files `.v1.0-trainvalNN_blobs_camera.txt` ("Thank you for downloading ...") that were never unpacked. Mirko does not need the other five cameras ("I do not need the other 5 cameras btw"), so they were not unpacked. State after D42: all 17 archives and the two Occ3D download files are deleted (95 GB on 2026-11-02, then on Mirko's word the four camera archives of parts 7 - 10, 74 GB, so the five cameras are gone from this machine; the public bucket has them again, a download needs Mirko's OK). The comparison results of all 18 are in `manifest.json` (`on_disk_check`), the download logs in `manifests/download_logs/`.

## Manifest (`manifest.json`)
`manifest.json` (about 30 KB, in git) names the raw data by what cannot change unnoticed, so that a result can say which data it was made from: the SHA-256 of the metadata tables of each dataset version (`v1.0-trainval`, `v1.0-mini`: the version itself), of the map expansion, of the licence and of the stored file lists, per sensor folder the number of files, their bytes and the SHA-256 of the sorted list "path TAB size" (one missing or extra file shows), the Occ3D files with their Google Drive ids and hashes, the link targets of the two WSL views, and for every archive that was downloaded its identity as above. `data_identity` is the SHA-256 of the data part only (tables, files, file lists, folder fingerprints, Occ3D scenes and annotations): a result names the data by it (`provenance.data.manifest_hash`, `autoresearch/reproducibility.md`), and it does not change when an archive is deleted or the file is made again. The marker files the archives leave (`data_markers`) only say that an archive was once unpacked, not that its data is still there: the folder fingerprints say what is there. The GT made from the data is not copied into it: `links.gt` points to `GtGenerator/versions.csv`, the tags `autogt/v<N>` and `data/autogt/<signature>/index.json`.
`tools/make_manifest.py` writes it from the files on disk (no network; the folder fingerprints of about 2 million files come from `tools/scan_tree.ps1`, native, a few minutes; `--no-deep` skips them). It keeps the archives that are gone from the existing file (`present: false`); `--archive-check <results>` merges the result of a comparison (the folder `--OutDir` of `verify_archive.ps1`, or a JSON / JSONL file; refused when it was made on another file); `--fresh` forgets the gone archives; `--check` compares the disk with the committed file (`--quick`: sizes only); `--selftest`. Regenerate and commit it after any change of the data (a part unpacked, a file removed): old results keep naming the old version, which stays in git history.

## Tools (`tools/`)
Google Drive helpers (2026-10-26): `list_gdrive_folder.py <folder id>` lists a public Drive folder (names, ids; listing only), `gdrive_size.sh <file id>` gives a file's size from a header request, `get_gdrive_file.sh <file id> <dest>` downloads one file resumably and checks its size (and gzip integrity); `get_occ3d_labels.sh` is the recipe that fetched the Occ3D labels (the two Drive file IDs; a new download needs the user's OK).

| tool | what it does |
|---|---|
| `list_nuscenes_bucket.py [filter]` | lists the archives of the public bucket `motional-nuscenes` with size and ETag (no download) |
| `get_blob_part.sh <part> <camera\|lidar\|radar>` | downloads one part (resumes a partial archive), checks the S3 ETag, unpacks it with `extract_blob.sh`, marks it `.unpacked`; environment `NUSC_DL` (download root, by convention `NuScenes_zips`, required) and those of `extract_blob.sh` |
| `get_parts_parallel.sh <kind> <part>...` | several parts in parallel (one connection gets 1-2 MB/s, six together about 6 MB/s) |
| `extract_blob.sh <tgz> [--delete]` | path check (no absolute or `..` paths), then unpack; `NUSC_DEST` target (required, on D:), `NUSC_MEMBERS` (e.g. `sweeps`), `NUSC_WINTAR=1` unpacks with Windows `tar.exe` (fast on D:; WSL writes small files there at only about 50 per second); `--delete` compares the unpack with the archive first (`verify_archive.ps1`) and deletes only when it shows 0 differences |
| `verify_archive.ps1` | native Windows comparison of archives with the data they were unpacked into: every regular member must exist with the same size and the same bytes; prints one JSON line per archive (members, files, bytes, differences, SHA-256 of the archive file, skipped members with `-Only`); `-List`, `-Parallel`, `-OutDir`, `-SelfTest` (archives made by bsdtar and by GNU tar in gnu / pax / ustar format, long names, tampering, truncation). About 50 times faster than `tar --diff` through WSL (9p reads small files at 50 per second) |
| `verify_s3_etag.py <file> <etag>` | checks a file against a plain or multipart S3 ETag |
| `make_manifest.py` | writes / checks `manifest.json` (section above); `scan_tree.ps1` is its native folder scanner |
| `link_views.sh` | builds the WSL views (above); moves the former WSL copies to `~/_to_delete/`. It refuses while a process has a file of a view open; the guard matches the link targets (`/mnt/d/Auto-research/NuScenes/nuscenes_full/*`, `.../nuscenes_mini/*`, the additions folder), because an open file reached through a view resolves to them in `/proc/*/fd`; `--selftest` holds a mini-view file open and checks that the guard sees it |
| `link_storage.sh` | the links from the project folders to the caches and checkpoints on D: (section "Where everything lives"): `--check`, `--apply`, `--selftest` |
| `stop_downloads.sh` | stops running downloads (partial archives are kept) |
| the one-offs of 2026-10-25 | first download run, D: speed test, copy to D: / C: with manifests, `verify_copy.ps1`, `sample_checksums.sh`, self-test of `extract_blob.sh`, `move_additions.sh` (superseded by `link_views.sh`): removed from the working tree on 2026-11-01 and kept by the git tag `nuscenes/tools-history-2026-11-01` (restore: `git checkout nuscenes/tools-history-2026-11-01 -- datasets/NuScenes/tools/history`) |

## Speeds measured from WSL on D: (2026-10-25, 2026-11-02)
1 GB sequential write 4.2 s, read 4.5 s; 500 files of 200 KB: write 9.5 s, read 1.5 s. Many small files are slow through WSL (9p): `tar --diff` over the camera archives reaches 10 MB/s per stream (about 50 files per second), while the same files are read natively at 5000 files per second with 16 readers (800 MB/s): bulk checks of the raw data belong on the Windows side (`verify_archive.ps1`, `scan_tree.ps1`). Fast caches stay in the project folders.
