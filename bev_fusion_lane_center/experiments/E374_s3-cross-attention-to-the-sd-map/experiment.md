# E374 - S3: the E365 token head with a cross-attention to ROAD-LEVEL SD-map tokens (one centre line per carriageway with a lane count, simulated map errors), against the same head without it

The third stage of Mirko's design (D113): grid -> nodes -> pruning -> self-attention -> cross-attention to the past (S2, E368) -> **cross-attention to the map** -> node classification. D88 / D113 point 2: no rule step, rule-step systems are never a bar. **Mirko's correction of 2026-11-11 is the first design rule: the LANE-level map of E273 carries exactly the connections a real SD map does not have (successors, predecessors, left / right / opposite, lane index), so it never feeds this head: the block reads ROAD-level fields only.** (E273's lane-level assignment is a different job with its own map tokens; its gain, +0.071 `lane_acc_err`, is lane-level evidence and says nothing about this card.)

**The question of S3:** does ONE cross-attention block (the tokens of a frame attend to map tokens = samples every 2 m of the carriageway centre lines with position, the direction of travel and the number of lanes; a frame without a map attends to a learned 'none' key only) lift the E365 head, trained on corrupted maps (including absent, count-unknown and grossly wrong ones), over the same head without it? **The honest starting point:** E291 gave the junction pair head a GT-derived lane-count table at the junction ends (counts only, hard association): at most +0.0035 topo F1 with a CLEAN table, about +0.001 of it the count, wrong counts harmless, right ones not exploited. Here the map enters at the TOKENS (every token can look at the road under it) and carries geometry as well as counts: step 0 says the signal is larger than E291's anchor (within an existence bin the supported weak tokens are 2 - 4 times likelier to be novel nodes), but **the simulated map is derived from the very GT lane pieces that define 'true': a clean read is an optimistic bound, and the card claims nothing about a real SD map.**

## 1. Card text
- **Statement:** a head that can look at the road under every token decides weak and false tokens better than the same head without the map: topo F1 +0.006 (hit window 0.000 to +0.012) over the matched control on VAL, both seeds, with simulated map errors; the gain is scene-specific (`S` below `err`).
- **Mechanism:** a lane graph lies on roads; a token far from any carriageway, or at an angle to its direction of travel, is likelier false; the lane count says how many parallel lanes to expect; near a junction the carriageway ends and the others begin.
- **Step 0 (measured 2026-11-17 07:00, CPU, VAL 873 frames of B' seed 0, token classes as in E368 step 0: 'novel' weak = near a GT node that no delivered token found, 'duplicate' weak = near a found node, 'false' weak = near none, 'delivered' = p >= 0.5; map = `sd_lib.build_sd` on the lane GT pieces, mean 237 samples per frame (the v1 lane map had 293); `error` = `degrade_sd` (drop 0.1, sparsification 0.5 - 2 m, count errors 0.1) + a rigid shift of 1 - 2 m + yaw N(0, 1 degree), seeded by the frame token; 'supported' = within 3 m of a sample and |cos| >= 0.8 with its direction (the module reads the SIGNED direction: the carriageway's direction of travel is SD-map information, |cos| is the conservative read); scratch `temp/_session_scratch_d113/step0_map2.py`, promoted into `lane_map_data.py potential`).** Supported (exact / error / the `error` map of ANOTHER scene = the null): novel 0.927 / 0.825 / 0.203; duplicate 0.947 / 0.811 / 0.345; **false 0.600 / 0.534 / 0.230**; delivered true 0.960 / 0.818 / 0.340; delivered false 0.785 / 0.691 / 0.210 (n = 20,349 / 75,254 / 141,443 / 128,610 / 16,762). Median distance to the nearest sample, exact / error: novel 0.91 / 1.26 m, false 1.95 / 2.17 m. **Within existence bins (`error` map; weak tokens; novel-node share of the supported against the unsupported): p 0.05 - 0.10: 0.031 / 0.008; 0.10 - 0.20: 0.059 / 0.023; 0.20 - 0.30: 0.113 / 0.054; 0.30 - 0.40: 0.177 / 0.088; 0.40 - 0.50: 0.297 / 0.157** (a ratio of 1.9 - 3.9; the share of weak tokens near a GT node rises from 0.32 to 0.51 over the bins; supported if near GT / if not: 0.77 / 0.44 at p 0.05 - 0.10, 0.83 / 0.58 at p 0.4 - 0.5). **Reading, with its limits:** a real, existence-independent signal (the other-scene null is 0.20 - 0.35), but (a) the map samples the very lanes that define 'true': the exact map is an oracle for 'near a lane', and the `error` map's 1 - 2 m shift lowers the novel-node support by 0.10 and the false-token support by 0.07: the margin does NOT shrink (0.93 - 0.60 = 0.33 exact against 0.83 - 0.53 = 0.29 error: v1's 'a third of the margin' is withdrawn); (b) a false token ON the road is not separated; (c) the error model (a rigid 1 - 2 m shift, 10 % dropped side roads, 10 % count errors) is a stand-in, not a measured SD-map error distribution.
- **The map tokens (new, `training/data/lane_map_data.py`; ROAD-level fields only, a leak check refuses anything else):** from `sd_lib.build_sd(dict(pts=[lane GT piece points]), [])` (carriageway centre lines with a lane count at every vertex; the route is NOT passed), resampled every 2 m: position / 50 (+ a Fourier code), the unit direction of travel (signed), the lane count (1 - 5, / 4; 0 = unknown). **NOT given:** lane index, successor / predecessor counts, adjacency (succ / pred / left / right / opposite), piece / road ids, the kind (lane / connector / mixed), the arclength fraction, the junction turn paths, the route, the dropped list, anything of the GT piece of a node. Fixed key set (`pos`, `dir`, `count`, `valid`) asserted by the loader (the E291 kill (1) lesson). **Cap and truncation (a named hard step):** at most 512 samples per frame; when more exist the samples nearest the ego are kept; the build counts the frames that are truncated (TRAIN and VAL) and the card is revised if more than 0.1 % are (the measured maxima of the v1 lane map were 773 TRAIN / 687 VAL; the road map is smaller: to be measured by the build, not assumed). **Corruption mix of the TRAIN draws (per sample draw, a generator seeded by (init seed, frame token, the draw index of that frame from a shared counter array); a resumed run re-seeds and is not bit-reproducible: resume steps are reported):** 25 % exact, 47 % `error`-like (rigid shift U(0, 2) m, yaw N(0, 1 degree), `degrade_sd` drop 0.1, count errors 0.1), 8 % counts unknown (the geometry kept, count 0), 10 % absent (no map: the none key only), 10 % gross (a rigid shift of 4 - 8 m, or the map of another scene). VAL: `error` mode, fixed per frame. A rigid shift lets a head register itself from the exact spacing of the lanes: said; the `gross` / `S` read-outs measure how far the head trusts the map.
- **Cost of the map data:** the lane GT load (12 - 18 ms) + `build_sd` (measured by the build) run in the loader workers; at bs 8 and 4 workers about 30 - 60 ms per step against 0.2 s per step: reported with the launch gate. The map query is data for the product, not counted in the head's G-cost.
- **The module (`training/grid/jmap.py`, new, separate from `jtoken.py`; the pattern of E368's `jpast.PastBlock`):** `MapBlock(d, heads)`: pre-norm, q from the token states (LayerNorm), k / v from an embedding of the map token (MLP of the fields above -> d, LayerNorm), ONE learned none key per head, a bias MLP(7 -> 32 -> H) of the relative geometry between a token and a map sample (cos / sin of the angle between the token heading and the direction of travel, the offset along / across the TOKEN heading / 20, the distance / 20, the lane count / 4, a presence flag), padding masked, zero-initialised output projection (the block starts as the identity), 4 heads of 16; about 20 k parameters. No state, no recursion. The hook in `jtoken.py` (owner: Fable): `map_block=None` called after `layers[1]` as `map_block(x, pos, dirv, valid, maps)`; `maps = {}` = no map; defaults bit for bit unchanged.
- **Not claimed:** anything about a REAL SD map (the map is a GT-derived simulation: the gain is an upper bound on what a real map could give; real gross errors (a wrong road, a stale map) are covered by `gross`, `S`, `U` only), TEST (never touched), the lane-level assignment of E273, the combination S2 + S3 (a later card).
- **Inputs:** ready: the E365 caches and head, the lane GT store, `sd_lib.py`, `map_sim.py` (the shift / yaw error model), the E371 / E373 seed twins as an outside noise check. To build (the lane chat): `lane_map_data.py` (map tokens, leak check, loader on top of `lane_ptok_data`, `potential`, fixture), `jmap.py` (+ tests with mutants), `jmap_train.py`, `jmap_eval.py` with the map controls. To agree with Fable: the hook after `layers[1]`, the slot plan.
