## 1. Problem and claim
Input: an image (Cityscapes 1024 x 2048, ADE20K, ImageNet for pre-training), output: dense per-pixel predictions (also super-resolution, and Segment Anything). Gap: softmax attention costs O(N^2) in the number of pixels, so vision transformers either stay at low resolution or use hardware-unfriendly tricks (large kernels, shifted windows, complex topologies). The claim that matters: a ReLU-based linear attention (O(N) in time and memory) supplies a global receptive field with only matmuls and 1x1 / depthwise convolutions; because ReLU linear attention gives diffuse attention maps and weak local detail, the paper adds depthwise convolutions (in the FFN and as multi-scale token aggregation) and shows that both ingredients matter (Table 1). Reported speed-ups are against SegFormer and SegNeXt on edge GPU (Jetson Orin, TensorRT fp16) with equal or better mIoU. Nothing is shown for BEV grids, thin structures, direction fields or any non-photographic input.

## 2. Method as built

### 2.1 Pipeline / architecture (digest)
```
 image -> stem -> stage1 -> stage2 (conv/MBConv) -> stage3 -> stage4   (strides 8 / 16 / 32 for stages 2 / 3 / 4)
                                         EfficientViT blocks only in stage 3 and stage 4;
                                         each of those stages starts with a stride-2 MBConv, then d blocks
 EfficientViT block = x + MSLA(x)  ->  then  x + FFN_with_DWConv(x)        (Figure 2, left)
 head: P2, P3, P4 (stages 2, 3, 4) -> 1x1 conv to a common width -> bilinear/bicubic upsample -> add -> MBConv blocks -> output layers
```
- Repository configs (backbone file, digest): B1 widths [16, 32, 64, 128, 256], depths [1, 2, 3, 3, 4], head-dim 16; B2 widths [24, 48, 96, 192, 384], depths [1, 3, 4, 4, 6], head-dim 32; default FFN expansion 4. Segmentation head (seg file): inputs from stage4 / stage3 / stage2, head stride 8, 3 MBConv middle blocks, expansion 4, width 64 (B1) / 96 (B2), BatchNorm + hard-swish by default. The paper text itself gives none of these numbers and defers to the repository.
- Token counts in the paper's own use (mine, from strides above): at 1024 x 2048 input the attention runs on 64 x 128 = 8192 tokens (stride 16) and 32 x 64 = 2048 tokens (stride 32). The paper never applies attention at stride 4 or 8, i.e. never on 40 000 tokens.

### 2.2 Equations (digest; numbering of the paper)
- **E1 softmax attention:** `O_i = sum_j [ Sim(Q_i,K_j) / sum_j Sim(Q_i,K_j) ] V_j`, with `Q = xW_Q, K = xW_K, V = xW_V`, `x in R^{N x f}`, `W in R^{f x d}`; softmax attention is `Sim = exp(Q K^T / sqrt(d))`.
- **E2 ReLU linear attention:** `Sim(Q,K) = ReLU(Q) ReLU(K)^T` (similarity is non-negative, so the row normalisation is well defined).
- **E3 associativity form:** `O_i = ReLU(Q_i) ( sum_j ReLU(K_j)^T V_j ) / [ ReLU(Q_i) ( sum_j ReLU(K_j)^T ) ]`. The two sums have shape d x d and d x 1, are computed once, and reused for every query: O(N) time and memory. The paper states the complexity class only, no FLOP formula and no measured memory.
- **Multi-scale tokens:** Q/K/V tokens are additionally aggregated over a small neighbourhood per head with a depthwise (+ 1x1 grouped) convolution; ReLU linear attention then runs on each scale separately; outputs are concatenated along the head axis and given a final linear projection. In the implementation the paper says all depthwise convs are fused into one depthwise conv and all 1x1 convs into one grouped 1x1 conv with 3 x #heads groups of d channels each; the neighbourhood is 5 x 5.

### 2.3 Operator as implemented in the repository (digest of `ops.py`, described, not copied)
Class `LiteMLA`: arguments in/out channels, `dim` (channels per head, default 8), `heads` (default `in_channels // dim * heads_ratio`), `scales` (default one depthwise kernel size 5), `kernel_func` (default ReLU), `eps` (default 1e-15); `total_dim = heads * dim`.
```
 x [B,C,H,W]
  qkv : 1x1 conv  C -> 3*total_dim                                   [B,3T,H,W]        (T = total_dim)
  per scale s: depthwise sxs conv (groups = 3T) -> 1x1 conv with 3*heads groups   [B,3T,H,W]
  concat(original, scale branches) along channels                    [B,3T(1+S),H,W]   (S = number of scales)
  reshape                                                            [B, heads(1+S), 3*dim, N]   N = H*W   (head axis inferred)
  q,k,v = split along the 3*dim axis;  q = ReLU(q), k = ReLU(k)
  v_pad = v with one extra row of ones                               [B, heads(1+S), dim+1, N]
  kv  = v_pad @ k^T                                                  [B, heads(1+S), dim+1, dim]
  out = kv @ q                                                       [B, heads(1+S), dim+1, N]
  out = out[:, :, :dim] / (out[:, :, dim:] + eps)                    [B, heads(1+S), dim,   N]   (the ones row yields the denominator of E3)
  reshape to [B, T(1+S), H, W] ;  proj: 1x1 conv T(1+S) -> C_out followed by BatchNorm by default
```
- This function runs with autocast disabled; fp16 input is cast to fp32 inside, and the result goes back to the input dtype outside. bf16: matmul runs in bf16, the result is cast to fp32 before the division.
- A dispatch picks the quadratic form when the token count H*W is not larger than `dim`, otherwise the linear form (an odd criterion, digest).
- Block: LiteMLA (no residual inside the operator) followed by a convolutional FFN; the repository's local module, residual wiring and activation were not shown on the pages I read.

### 2.4 Cost for a C-channel grid (mine, derived from 2.3; verify by `torch.profiler` before use)
Notation: N = H*W, d = head dim, one extra scale (S = 1), heads h = C/d so T = C, in = out = C, no bias, BatchNorm after proj.
- parameters: qkv 3C^2 + depthwise 5x5 on 3C channels 75C + grouped 1x1 3C*d + proj 2C^2 = **5C^2 + 75C + 3Cd** (plus BN 2C).
- MACs: N x ( 5C^2 + 75C + 3Cd + 4C(d+1) ); the last term is the attention itself: two matmuls of N*d*(d+1) per head, 2h heads.
- memory (batch 1, activations): concat tensor 6C*N elements (fp32 copy for the matmul: another ~6C*N if the input was fp16), plus the output 2C*N before the projection. The N x N matrix of softmax is never built.
- examples:

| setting | N | params | MACs | reference 3x3 conv C -> C | concat tensor, fp32 |
|---|---|---|---|---|---|
| C = 64, d = 16, full grid 200 x 200 | 40 000 | 28.4 K (+BN) | about 1.31 G | 36.9 K params, about 1.47 G | 61 MB |
| C = 128, d = 16, 50 x 50 (stride 4 of our grid) | 2 500 | 97.9 K | about 0.27 G | 147 K params, about 0.37 G | 7.7 MB |
| softmax at the same C = 64, N = 40 000 | | | N^2 d per head = 25.6 G MAC x 2 matmuls per head, 8 heads | score matrix 1.6e9 entries per head = 6.4 GB fp32 | not usable without a fused kernel |
So by MACs the linear module costs about one 3x3 convolution of the same width; the real latency is dominated by memory traffic of the reshape / pad / ReLU / concatenation / BN, which MACs do not show. Latency must be measured on the 3060 (section 5).

### 2.5 Losses, labels, training recipe (digest)
- Losses and labels are the standard ones of each task (segmentation cross-entropy etc.); the paper has no loss of its own for the attention. No matching, no assignment.
- Recipe: AdamW with cosine learning-rate decay; the backbone is initialised from ImageNet-pre-trained weights, the head randomly (all stated in the text). Learning rate, epochs, batch size and augmentation were **not found** on the page read.
- Latency set-up: mobile CPU (Snapdragon, TensorFlow-Lite, batch 1, fp32); edge GPU Jetson AGX Orin and cloud GPU A100 with TensorRT in fp16; the reported times include data transfer. The paper's tables also carry a Jetson Nano column (digest). No desktop RTX card.

### 2.6 Inference
Plain forward pass; no post-processing step in the module. Output resolution by bilinear upsampling in the head.

### 3.4 Caveats
- Inconsistencies inside the paper as returned by the reader: abstract says up to 13.9x GPU latency reduction against SegFormer, text says 8.8x on Orin; abstract says 48.9x throughput for SAM, Table 6 text gives 182 vs 11 images/s (about 16.5x); the L1 parameter count differs between the ImageNet and Cityscapes tables (53 M vs 40 M). Treat speed-up headlines with care; the later versions mix claims of different model generations.
- All latencies are TensorRT fp16 on Jetson / A100 (or a mobile CPU). The paper gives no PyTorch eager, no desktop-GPU, no batch-1 3060 number. The speed argument rests on the operator count (matmul, 1x1, depthwise) being friendly to TensorRT fusion; eager PyTorch pays for every reshape and cast (mine).
- The ablation is at the smallest model (B0 scale); whether linear attention still adds 2 mIoU at larger scale is not shown there.

### 5.3 Test against a conv-only control at equal ms with far-range recall as target (design sketch; a proposal, nothing was run)
Question: does global context in the dense stage raise far-range coverage (R@1 far, lanes found) at the same cost per frame?

Arms (all with the same decoder path 50 x 50 -> 200 x 200 added to the full-resolution stage, same data, same loss, same budget):
1. **C0 control, conv-only context**: two 3 x 3 convolutions + BN + ReLU at 128 ch on the 50 x 50 stage (about 0.74 G MAC, 0.30 M params).
2. **C1 strong simple control**: conv-only with a larger receptive field at the same cost (dilated 3 x 3 with dilation 2 and 4, or 7 x 7 depthwise + pointwise), because a cheap receptive-field increase is the obvious alternative explanation.
3. **A1 EfficientViT block**: LiteMLA (d = 16, h = 8, one 5 x 5 scale) + convolutional FFN with depthwise 3 x 3, width chosen so that measured ms equals C0 within 0.3 ms.
4. **A2 ablation**: A1 without the multi-scale branch (paper's Table 1 logic).
5. **A3 oracle-ish reference**: softmax attention (`F.scaled_dot_product_attention`) in the same slot: with 2 500 tokens it is affordable; shows whether linear attention loses against softmax at our size. Reported as a reference, not a candidate (it must also pass the ms check).
6. **Null**: A1 with the attention output zeroed at test time (is the attention path used at all?).
Both position variants of A1: with and without two coordinate channels (metric x, y relative to the ego, scaled to [-1, 1]) added before the qkv convolution; if one wins, that one is A1.

Protocol: train the dense stage + decoder on the frozen cached features exactly as the champion's stem is trained (same loss, same fp32 settings); first stage only the dense maps (point-level far recall of the seed map, cheap, layer 3), then, only for the winner against C0, retrain the builder and measure the full graph on the frozen VAL protocol with `evaluate.py` (new registry entries, paired scene bootstrap, 2 seeds, timing on an idle GPU, batch 1). Equal ms means: A1 not slower than C0 by more than 0.5 ms measured per frame and per module (also report the full-chain ms).

Prediction (mine, a number): R@1 far +0.02 over C0 (plausible range 0.00 to +0.04), i.e. at most a quarter of the 0.10 gap; Q within +-0.005; topo F1 unchanged within +-0.01; ms equal by construction. Reason for the modest number: the gap to the trace network is probably due to its sequential, pointer-based decision process and not only to context; loss-weight fixes were already spent (PROBLEM.md gap 1).

Decision rule (written before the run): KEEP if the paired-bootstrap interval of A1 - C0 on R@1 far excludes 0 and the mean difference is at least 0.010 in both seeds, Q not lower than C0 by more than 0.010, ms within +0.5 of C0 (via `autoresearch/tools/decide.py --band 0.010 --cost-variant ... --cost-control ...`). CUT if the mean difference is below 0.005 in both seeds, or if C1 reaches the same gain (then the cheaper conv variant is adopted: tie rule). INCONCLUSIVE otherwise, add a seed, do not adopt. Kill criterion: the dense-stage stage-1 far recall does not move by 0.01 over C0 in the first proxy run -> stop before any builder retraining.

### 5.4 Numerical and implementation gotchas (digest of the code facts + my analysis)
- Run the sum over tokens in fp32 and outside autocast (the code does this by design): the sum of 40 000 non-negative products exceeds the fp16 range (65 504) easily, and the default eps 1e-15 is below the smallest fp16 number (about 6e-8), so in fp16 the division is unprotected (mine). Our training may use autocast: wrap the operator the way the repository does.
- Division: the denominator is `ReLU(q_i) . sum_j ReLU(k_j)`; it is exactly zero when q_i is zero after the ReLU (then the numerator is also zero, output 0, not NaN, thanks to eps). For small positive denominators the gradient grows like 1/den^2 (mine); a larger eps (1e-6 in fp32) or `clamp_min` is a safe deviation to test. Dead heads (all q or all k zero after the ReLU) output zero and receive no gradient: watch the fraction of zero outputs per head in a sanity run.
- The output is a convex combination of V (non-negative weights summing to one), so it is bounded by the range of V; scale does not blow up with N, but the attention is diffuse (Figure 3): for thin structures such as lane centre-lines the local convolution path must carry the detail.
- BatchNorm after the projection (repository default) interacts with batch size; with small batches use GroupNorm, or keep BN and train at the champion's batch size.
- Eager-mode latency: the chain of reshape, pad, two matmuls, divide, concat adds kernel launches; measure on the idle 3060 with CUDA events, and try `torch.compile` only after the eager number is known (no new dependency).
- Memory at full grid: 61 MB concat tensor per image in fp32 is small; the full 200 x 200 attention is feasible only because of the linear form, but the 50 x 50 slot is likely the better value (mine).

### 5.5 Novelty and relevance for our problem
The novelty is the combination of a ReLU kernel with the associativity trick (a d x d summary of all keys instead of an N x N map) and a repair of its blurry attention through depthwise convolutions, so a global layer costs about as much as one 3 x 3 convolution and uses only standard operators. For us this is a candidate for the missing long-range context in the dense stage (A2, topic F1) where the seed and direction heads currently see a 2.5 m neighbourhood on top of frozen features, and the far-range recall gap is our largest open item. The evidence is indirect: the paper shows a 2 mIoU gain on Cityscapes at tiny scale and big speed-ups on TensorRT hardware, but nothing on BEV, thin lines or direction fields, and no softmax comparison at equal accuracy; a cheaper dilated-convolution control may give the same gain.
