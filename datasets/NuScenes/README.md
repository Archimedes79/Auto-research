# nuScenes - raw data shared by all problems

This folder (`datasets/NuScenes/`: the README and the tools are in git as recipes, the data itself is not: it is on D:) describes the raw nuScenes data and holds the download / copy / check tools. Licence: nuScenes is for non-commercial use; downloads only with Mirko's OK.

## Rule (Mirko, 2026-10-25)
- RAW data only on D:, in `D:\Auto-research\NuScenes` (WSL: `/mnt/d/Auto-research/NuScenes`): exactly what the nuScenes archives contain, plus the archives themselves. Nothing generated is written there.
- DERIVED data (info files, filtered radar, GT, caches) belongs to the problem that makes it, in its project folder on C: (e.g. `bev_fusion_lane_center/data/nuscenes_additions/`, later `bev_fusion/data/`), listed in that project's `data/README.md`.
- The bird's-eye GT made from this data (map layers, objects, velocity / flow) is generated by `autogt/` (repository root): `autogt.generate("~/data/nuscenes_full")` reads a nuScenes folder and writes the GT of every keyframe to `data/autogt/<signature>/` (or `out=`).
- Existing code reads `~/data/nuscenes_full` and `~/data/nuscenes` (mini). These are WSL "views": folders of symlinks only, raw entries -> D:, the lane project's additions -> its project folder. Built by `tools/link_views.sh`; re-run it after the repository folder or the D: root moves (the links are absolute).

## Manifest (`manifest.json`)
`manifest.json` (about 26 KB, in git) names the raw data by what cannot change unnoticed, so that a result can say which data it was made from: for every archive its size and S3 ETag from the download log (and whether it verified and what of it was unpacked), the SHA-256 of the metadata tables of each dataset version (`v1.0-trainval`, `v1.0-mini`: the version itself), of the map expansion, of the licence and of the stored file lists, per sensor folder the number of files, their bytes and the SHA-256 of the sorted list "path TAB size" (one missing or extra file shows), the Occ3D files with their Google Drive ids and hashes, and the link targets of the two WSL views. The marker files the archives leave (`data_markers`) only say that an archive was once unpacked, not that its data is still there (the lidar archives of parts 4-6 left markers, no LIDAR_TOP is on disk): the folder fingerprints say what is there. The GT made from the data is not copied into it: `links.gt` points to `autogt/versions.csv`, the tags `autogt/v<N>` and `data/autogt/<signature>/index.json`. A result card names the manifest by its SHA-256 (`provenance.data` of `autoresearch/reproducibility.md`). It is written by `tools/make_manifest.py` from the files on disk (no network; the folder fingerprints of about 2 million files come from `tools/scan_tree.ps1`, native, the whole run takes a few minutes; `--no-deep` skips them); `make_manifest.py --check` compares the disk with the committed file (`--quick`: sizes only), `--selftest` tests the tool. Regenerate and commit it after any change of the data (a part unpacked, a file removed): old results keep naming the old version, which stays in git history.

## Tools (`tools/`)
Google Drive helpers (2026-10-26): `list_gdrive_folder.py <folder id>` lists a public Drive folder (names, ids; listing only), `gdrive_size.sh <file id>` gives a file's size from a header request, `get_gdrive_file.sh <file id> <dest>` downloads one file resumably and checks its size (and gzip integrity); `get_occ3d_labels.sh` is the recipe that fetched the Occ3D labels (the two Drive file IDs; a new download needs the user's OK).

| tool | what it does |
|---|---|
| `list_nuscenes_bucket.py [filter]` | lists the archives of the public bucket `motional-nuscenes` with size and ETag (no download) |
| `get_blob_part.sh <part> <camera\|lidar\|radar>` | downloads one part (resumes a partial archive), checks the S3 ETag, unpacks it with `extract_blob.sh`, marks it `.unpacked`; environment `NUSC_DL` (download root, required) and those of `extract_blob.sh` |
| `get_parts_parallel.sh <kind> <part>...` | several parts in parallel (one connection gets 1-2 MB/s, six together about 6 MB/s) |
| `extract_blob.sh <tgz> [--delete]` | path check (no absolute or `..` paths), then unpack; `NUSC_DEST` target (required, on D:), `NUSC_MEMBERS` (e.g. `sweeps`), `NUSC_WINTAR=1` unpacks with Windows `tar.exe` (fast on D:; WSL writes small files there at only about 50 per second) |
| `verify_s3_etag.py <file> <etag> [--part-size MiB]` | checks a file against a plain or multipart S3 ETag; for a multipart ETag it tries the usual part sizes (8, 5, 15, 16 ... MiB) that give the part count and says which matched; `--selftest` |
| `make_manifest.py` [`--check` \| `--selftest`] | writes / checks `manifest.json` (section above); `scan_tree.ps1` is its native folder scanner |
| `link_views.sh` | builds the WSL views (above); moves the former WSL copies to `~/_to_delete/`. It refuses while a process has a file of a view open; the guard matches the link targets (`/mnt/d/Auto-research/NuScenes/nuscenes_full/*`, `.../nuscenes_mini/*`, the additions folder), because an open file reached through a view resolves to them in `/proc/*/fd` (fixed 2026-10-31: the former guard matched `~/data/*` only and never fired); `--selftest` holds a mini-view file open and checks that the guard sees it |
| `stop_downloads.sh` | stops running downloads (partial archives are kept) |
| the one-offs of 2026-10-25 | first download run, D: speed test, copy to D: / C: with manifests, `verify_copy.ps1`, `sample_checksums.sh`, self-test of `extract_blob.sh`, `move_additions.sh` (superseded by `link_views.sh`): removed from the working tree on 2026-11-01 and kept by the git tag `nuscenes/tools-history-2026-11-01` (restore: `git checkout nuscenes/tools-history-2026-11-01 -- datasets/NuScenes/tools/history`) |
